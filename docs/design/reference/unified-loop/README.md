# Soul 统一辅助闭环：合成参考模型

这是架构讨论用的独立 Python + SQLite 模型，不是 Soul 的生产实现、数据库迁移或新契约。输入、观察、草稿和外部结果均为合成材料；没有网络调用、真实个人数据或实际系统通知。仅依赖 Python 标准库。

模型采用同一稳定 case 关联输入来源、用户目标和用途；每次重算创建新的 item generation。与整体设计术语对应：稳定的 assistance item_id 在此代码中称 case_id；设计的 revision 在此对应 generation 及该版本的 item_id。内容有效性、用户处理状态、通道交付状态、外部执行状态分别记录。来源、目标或用途修订使旧输出失效；重算不会重置同一 case 的稍后与静音。snooze/mute 必须提供当前 generation，不隐式重新打开已处理或已忽略的事项。done/dismiss 同事务取消尚未发送的通知及未执行准备、清除草稿正文；在途与未知的实际历史保持原样。复制、认为有帮助、明确已处理各有不同含义，不进行偏好学习。

执行记录的 `accepted` 表示“完成时曾被接收”的历史事实，不代表现在仍可展示。后续处理、失效或遗忘会清除正文，并由事项有效性与用户处理状态控制展示，不将过去成功接收改写成拒收；在途结果迟到且依据失效时，仍记录 `accepted=0`。

`resolved` 仅表示用户自报已处理，未实现经结果证据核验的 `resolved_verified`。模型中的 `dismiss` 是事项级关闭，不能替代生产 W5 只针对精确 bundle 的忽略语义。

真实 SQLite 事务验证两处原子边界：输入与待分析工作共同提交；本地结果、收件箱与工作完成共同提交。故障注入在事务内部抛出异常后回滚，再真正关闭并重新打开数据库验证恢复。它不模拟物理断电、磁盘损坏、文件系统乱序或 SQLCipher 密钥销毁。

通知载荷只允许固定通用文字和不透明的稳定 case ID。它只是导航：点击解析当前有效版本或失效说明，不能转移旧版本的动作或批准，遗忘后拒绝读取。模型中的 submitted 只是模拟系统接受，不能证明用户看到。发送中重启变为 unknown，不能自动重发；同一来源/目标/用途版本仅更换 item UUID 也不能绕过这一规则。真实来源变化可以产生新候选，但是否值得打断用户仍由尚未建模的提醒政策决定。E1 执行必须经过明确的准备及单次批准，批准绑定准确准备与 origin；重启不恢复批准，在途 unknown 不自动重试。外部系统的真实投递、去重、取消和已展示内容撤回不在模型保证范围。

模型先解析规范路径，再用 Linux `fcntl` 独占 lease 防止符号链接别名绕过活跃 owner；每个新 lease 只允许恢复一次，初始化失败释放资源。SQLite 条件更新避免工作被重复认领。这不替代 Soul 的 Windows lease 或生产物理工作槽实现，不覆盖硬链接别名与文件系统攻击。逻辑遗忘使本模型的来源、衍生正文与旧指针不可用，但不保证 SQLite 文件或操作系统已经安全擦除，不能当作密码学遗忘验收。

本模型只涵盖一个明确来源—目标—用途的 case 身份规则；不解决多来源语义聚类、自然语言事实冲突、采集覆盖率、长期记忆检索、LLM 效用、提醒排序、公平性、安静时段与全局提醒预算。批准 TTL、单调时钟期限、端点配置代次（包括 A→B→A）和生产唯一物理慢任务槽均未覆盖；origin 测试只验证一份准备绑定一个 origin，不验证端点配置变更。source 更新默认失效受影响项，由调用者明确安排重算；没有常驻调度器。正文是确定性合成字符串，不是人格或关系推断算法。

运行（独立 Linux 参考测试，非平台 gate）：

```sh
python3 -B test_loop_model.py
```

结果写入 `test_results.json`；全部通过后生成 `trace_examples.json` 的四条轨迹，供离线 HTML 展示。临时数据库只由合成 fixture 创建并在测试结束删除。每个矩阵测试只计为一项，不把内部故障点或重复运行累加为额外测试。
