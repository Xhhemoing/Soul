# Soul：从实际使用到框架与算法

日期：2026-10-15。审查源码：PR #66 工作分支 `6e8f3c06b7fd0cbc7920766337572301319b021a`。这是后续架构设计与可执行参考实验，**不是生产接线完成、算法解冻或正式验收**。原来的 [系统架构](../ARCHITECTURE.md) 继续描述现有实现；[交互研究页](../framework-design.html) 展示本文和可操作的反例。

## 1. 先回答：日常使用究竟缺哪一环？

目标不是让 Soul 多运行几个 agent，而是让它在用户交代事情时可靠地完成：理解本次意图 → 使用获准且当前有效的个人资料 → 展示依据 → 由用户控制生成 → 接收纠正或遗忘 → 下一次行为随之改变。

本次没有访问真实聊天、个人数据库或端点，也没有做用户访谈。下面是依据产品承诺和当前源码构造的使用场景，频率与真实满意度均未测；静态反例与已运行的参考测试分别标注。

| 使用场景 | 当前事实 / 源码定位 | 问题与研究点 | 预期可观察结果 |
|---|---|---|---|
| 第一次使用，没有数据或模型端点 | `soul-draft/src/template.rs` 是确定性骨架；`ProfileBrief::neutral` 无轴断言 | 用户是否能分清“语气骨架”与“理解消息后的回复”？ | 无数据仍可用；缺失不填零，不声称已理解其人格 |
| 粘贴 A，等待预览时又改成 B | `apps/desktop/src/routes/Draft.tsx` 的 `describe` 回调无输入代次；textarea 只 `setPasted` | 输入、预览、批准和原文豁免怎样绑定？ | A 的迟到预览不能覆盖 B；改回 A 也不会复活旧批准 |
| 起草前纠正“我希望简短、正式” | `ProfileBrief::from_view` 读取 voice/axes；`Session::set_voice` 写资料，未使已有准备失效 | 纠正如何穿过快照、生成、返回各阶段？ | 新请求采用用户生效值；旧快照结果不能被当作新纠正后的答案 |
| 希望回忆“我上次为什么拒绝这个安排” | `SoulMemory` 与 `MemoryStore` 是 CRUD/密封引用；起草 brief 没有记忆入口 | 检索什么、凭什么使用、怎样引用、无证据怎样回答？ | 先选可用资料，再生成；可查看所选记忆及来源；不足时澄清 |
| 请求较慢，用户关闭端点 | Tauri `SessionState(Mutex<Session>)`，`generate_draft` 同步到 blocking HTTP | 撤权能否绕过慢工作；派发边界是什么？ | 撤权不排在整段 HTTP 后；撤权之后不再发新许可，旧结果不被接收 |
| 忘掉一段经历，旧任务随后返回 | 已有精确 `ForgetScope`，但还没有通用任务来源版本 | 数据主键未变、正文已变，如何识别旧快照？ | 内容密钥销毁仍由 store 执行；依赖已变的任务被拒收 |
| 导入/遗忘确认后窗口丢失回执 | import 有事务，forget 有 commit/cleanup/audit 分离回执 | “未知”是否被错误显示为失败并自动重做？ | 不把未知当未执行；区分事务提交、清理、审计、UI 收到四件事 |
| 问“现在住哪里”，历史有两个地址 | 目前记忆没有完整有效时间/知识时间和适用范围契约 | 最近记录是否一定是真实最新？冲突如何处理？ | 不用文件导入时间覆盖事实时间；未消解冲突先澄清 |

现有能力应保留：问卷与纠正锁、图谱判档与证据、记忆 CRUD/遗忘、默认占位的 E1、确定性起草回退、只读文件计划。**获准记忆自动参与起草仍是后续产品能力，不是 v0.1 漏做的承诺。**

## 2. 研究问题、证据与取舍

| 研究问题 | 一手依据 | 对 Soul 的推论 | 不可外推的结论 |
|---|---|---|---|
| 长记忆该怎样评估？ | [LongMemEval](https://arxiv.org/abs/2410.10813) 分别研究提取、跨会话、时间、更新、拒答，并拆开索引/检索/阅读 | 分开测“选对证据”与“读对证据”；加入纠正、时间、无答案轨迹 | 论文分数不等于 Soul 的中文个人数据准确率 |
| 对话能否直接当人格真值？ | [LoCoMo，ACL 2024](https://aclanthology.org/2024.acl-long.747/) 用长对话、时间事件与 QA/摘要任务研究记忆 | 保留原始出处与事件关联；摘要是可撤销派生物 | 合成对话 QA 不是人格科学有效性，也不是临床结论 |
| 静态问答测够了吗？ | [AMemGym 预印本，2026](https://arxiv.org/abs/2603.01966) 研究状态演化和交互式记忆评估 | 用“创建→纠正→检索→遗忘→迟到返回”的轨迹测状态变化 | 模拟用户与自动裁判不能替代本人确认的实际效用 |
| 多路检索分数如何合并？ | [RRF 原论文](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf) 融合排序位置 | 候选试验可合并关键词/结构化结果，避免直接相加不同尺度分数 | RRF 不是可信度、真值或授权；不能替代准入过滤 |
| 换异步锁能否解决撤权？ | [Tokio shared state](https://tokio.rs/tokio/tutorial/shared-state)、[Tauri state](https://v2.tauri.app/develop/state-management/) | 分开控制状态和慢任务；改变临界区范围比换锁类型更关键 | 异步锁不会让持锁 HTTP 期间的另一个命令获得同一把锁 |
| abort 能否取消阻塞请求？ | [Tokio 1.53.1 spawn_blocking](https://docs.rs/tokio/1.53.1/tokio/task/fn.spawn_blocking.html)，与当前 Cargo.lock 解析版本一致 | 取消先使结果不可接收；物理 worker 退出前仍占并发额度 | 不能声称 abort 撤回 HTTP 或释放正在运行的线程 |
| 重试如何避免重复副作用？ | [AWS Builders’ Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) 区分请求意图与相同参数 | 操作回执标识与消息去重标识分开设计 | 不能用正文 hash 猜测用户是否希望重复导入 |
| 事务为何不能自动解决旧预览？ | [SQLite isolation](https://www.sqlite.org/isolation.html) 说明单 writer 与快照可见性 | 应用必须复验读时依据；短事务保护写入一致性 | 不应把应用一把锁描述成 SQLite 只允许一个连接 |

以上采用的是方法和故障机制；本报告不引用外部论文的提升百分比来预测本项目收益。研究读取日为 2026-10-15；LongMemEval 细节对照原论文 v1，未宣称覆盖其全部后续版本。

## 3. Brainstorm：四种整体路线

| 路线 | 实际收益 | 主要代价 / 反例 | 结论 |
|---|---|---|---|
| 全量资料塞进长上下文 | 接入看似快，少建索引 | 过量出网、旧事实冲突、遗忘派生物追踪困难、成本随全库增长 | 不采用为默认路径 |
| 向量库 + 自动记忆 agent | 同义语义召回潜力；可自动整理 | 新模型/索引/密钥生命周期，自动写入可能把误读固化；无法先解决撤权 | 保留为有实测需求后的候选 |
| 拆成微服务或多 agent 总线 | 可分布式伸缩 | 当前本机单用户更需要原子性；引入部署、消息重复、跨服务权限问题 | 当前不采用 |
| **现有模块 + 用例编排 + 证据上下文** | 复用 18 crates、冻结算法、密封存储和策略；逐用例迁移 | 需要明确任务与来源版本，处理结果未知；保守失效会增加重新准备次数 | **本轮选定的设计方向** |

检索内部也不一次定死：先“本次手动选择记忆”建立可解释闭环，再比较本地关键词/结构化召回，最后才评估本地向量召回。RRF 是多路候选的试验组合器；单路足够时不用为了架构而加第二路。自动抽取先存候选并由用户确认，不能悄悄改写档案锁。

## 4. 目标框架：在现有边界内增加三段用例

**准备 prepare → 锁外执行 execute → 校验接收 complete** 是应用层内部组织方式。不是新的 agent 产品框架，也不新增 crate 或持久化系统。

| 层 / 建议位置 | 接收与产出 | 所有权和禁止事项 |
|---|---|---|
| React 起草页 | 编辑代次、页面 ticket、预览 ID → 用户意图 | 同步准入；忽略迟到回调；不能伪造核心撤权 |
| `soulcore::commands` 用例编排 | `DraftInput` → `PreparedDraft` → `DraftOutcome` | 仍是唯一组合者；持有不可变准备体，不在发送时从 UI 重建 |
| 拟议 `soulcore::operations` | 任务 ID、epoch、deadline、状态 → 接收/拒绝 | 私有 Rust 类型；控制锁只保护短内存操作，不等 store/HTTP/审计 |
| 拟议 `soul-memory::selection` | 用途、查询、可读候选 → `ContextSelection` | 可信适配器先判用途/证据/遗忘；排序服务不能批准使用 |
| `soul-profile` / `soul-graph` / 两算法 crate | 当前生效档案、既有 T4D/A0–A3 输出 | 用户锁优先；不新增关系分数，不重算第二套判档 |
| `soul-policy` + `soul-egress` | 已审查准备、现有一次性能力与 redacted body → HTTP 结果 | 继续精确 origin、默认占位、固定指令、拒绝路径；不让模型自行授权 |
| `soul-store` + `soul-store-api` | 原始记录、密封引用、事务、遗忘 → 有来源的快照 | 单 writer 不变；密钥、事务、清理仍由 store 管；不把正文抄到审计 |

最小接口草图（**设计稿，不是新增 IPC/schema 定义**）：

```rust
struct PreparedDraft { /* existing preparation_id, body, plan_hash, origin;
                          internal source revision + expiry + operation identity */ }
enum Completion<T> { Accepted(T), Stale, Cancelled, Expired, Unconfirmed }
fn prepare_draft(input: DraftInput, deps: &Services) -> Result<PreparedDraft>;
fn execute_draft(job: OwnedDispatch, worker: &BoundedExecutor) -> WorkResult;
fn complete_draft(job: OperationId, result: WorkResult, deps: &Services) -> Completion<Draft>;
```

类型中的来源版本只在内存内跟踪已有单 writer 变更；不会新建正文 hash、schema 锁或版本基线。已有 preparation ID 继续区分“相同段数但不同正文”；已有 plan hash 不删除，不被新的通用 hash 替代。重启不恢复旧授权或旧内存任务。

## 5. 算法一：输入—预览—批准归属

状态为 `live, edit_revision, serial, active_ticket, preview_identity`。开始请求先同步占槽，再调用 IPC；不能只依赖 React 下一次渲染才禁用按钮。

1. 每次编辑递增 revision 并隐藏旧确认面板。A→B→A 仍是三个不同编辑状态。
2. 开始请求保存 ticket 和 revision；同页面已有请求则拒绝第二次准入。
3. 回调仅在页面仍存活、ticket 相同、revision 未变时可更新界面。
4. 旧回调只能释放它自己的槽；不能释放新任务。编辑不释放在途槽，避免用“视觉取消”无限启动工作。
5. 批准/原文豁免必须传入当前预览的对象身份，不能从旧闭包批准新输入。核心仍校验 preparation ID/hash/origin。
6. `discardDraft()` 当前不带 preparation ID。初步接线采用串行 drain：隐藏 UI 后等待 discard 结束才准入新 prepare；若回执未知，不自动再次 discard。以后若需要按 ID 丢弃，先决定 IPC 语义。**参考模型的 abandon 仅模拟 UI，未模拟 discard IPC 排序。**

参考实现 `DraftFlow` 每步 O(1)。它证明归属规则可执行，不意味着 `Draft.tsx` 已接线。本次发现的 A/B 错配是静态源级风险；没有把它描述为生产端点双发，因为核心现有 `pending.take()` 已防同一准备重复消费。

## 6. 算法二：可撤权的慢任务与结果接收

拟议状态：prepared → dispatched → accepted / rejected；prepared 可取消；dispatched 可标记取消，但 worker 未退出前不得释放物理槽。时间使用单调时钟的 deadline，判定 `now >= deadline` 已过期；与人脉算法的数据 `as_of` 无关。

快照 `S = (control_epoch, data_version, origin, writing=false)`。当前实现没有这个通用版本层；参考模型通过显式输入验证它，生产接线需另作决定。

**准入条件**：有 origin，来源快照与当前状态一致，未到 deadline，未使用过本次任务 ID，队列容量未满。`prepare` 接受读资料时的快照，禁止“读旧资料后再用当前版本号冒充新快照”。

**派发条件**：仍为 prepared，未取消/过期，epoch、origin、data_version 均一致。检查、现有一次性能力消费及派发资格的发放在同一个控制临界区内完成；临界区内禁止 HTTP、数据库等待和审计。不能把“检查 epoch”和“另一个线程随后发许可”拆开。

**接收条件**：确实已派发，未被取消，未过期，授权和来源仍一致，结果结构/禁止词/证据校验及必要审计处理已完成。最后接收点再次校验，再向 UI 返回。Accepted 是核心逻辑接收点，不是 UI 已显示的证明：在它之后、IPC 抵达之前发生变更，页面也必须根据核心版本/失效事件拒绝旧结果；事件先后需原生集成测试。已经展示的结果在资料变更后标注失效或清除。未来若有真正的领域写入，不能 complete 返回 ok 后放开保护再提交；必须把验证与提交纳入同一受保护边界。

**撤权的精确定义（待决定）**：撤权提交之后不再发新的派发许可，并拒收该 epoch 的晚到结果。许可已经发放的 worker 可能尚未开始网络发送，也可能已把字节送出；此时只能尽力中止，不保证撤回。若产品要求“撤权确认后绝无首字节发出”，必须把边界推进到传输层并做 socket 级测试，本模型不提供该保证。

### 锁顺序与写入版本，避免新的死锁

- 控制锁从不获取 store 锁、不等待 worker、不写审计。撤权只需控制锁。
- 读快照：读控制版本 C0 → 单独持 store 锁复制最小所需数据 → 放开 store → 再读控制 C1；只有 C0=C1 且无写入进行中才注册准备，否则重做或明确要求重新准备。
- 单 writer 的写路径：获得 store guard 后，短暂取得控制锁，置 writing=true 并递增 data_version；释放控制锁再执行事务；事务成功或失败后清除 writing。失败也保守使旧任务失效。清除必须由 Rust guard/RAII 保证；panic 后不得留下“看似可用”的错误状态。
- complete 的最后判断仅在控制锁内做；写事务从“宣布变更”起会令旧结果失效。引用读取/结果审计在最后判断之前完成，且不持控制锁做 I/O。验收必须覆盖审计阶段插入纠正/撤权。
- 当前全局 data_version 会使无关记忆编辑也让任务失效，这是第一版保守代价。确认所有写入口均参与后才考虑按依赖 ID 分版本；不能现在遗漏 import、forget、联系人/脱敏词表、profile 等入口而宣称完整保护。
- 该纪律只覆盖同进程唯一 writer。多进程/多端支持需要单独协议，不能凭内存 epoch 推广。

参考 `OperationControl` 单项查找/派发/接收平均 O(1)，准入与失效时扫描最多 Q 个排队项，O(Q)，Q 受容量限制。过期、撤权或资料失效的 prepared 项没有真实 worker，立即或在下次准入前回收；已 dispatched 的工作必须等实际结束。模型的 used-ID 集合保留至实例结束，仅用于有限实验；生产不得把它做成无限任务账本，应复用一次性准备生命周期并有界回收终态。模型没有实际线程、Socket、SQLite 或审计，穷举只检查事件线性顺序。

## 7. 算法三：先获准、后相关的证据上下文

### 7.1 数据适配先于检索

`SoulMemory` 目前没有普遍的用途许可、revision 或双时间字段；`SoulEvidence.privacy` 可为空，`source_refs` 还是领域定义的 opaque 值。因此参考模型里的 `granted, recordedAt, validFrom, validTo, claimKey, cost` **不是已落库字段**，更不能由导入 JSON 或模型自行填写后就获得权限。

第一步建议从“本次手动选择记忆”得到临时用途许可，复用已有 memory/blob/evidence ID；本次选择不授予研究用途或 E1 原文出网权。无来源的手写记忆可把本条用户记录及密封 blob 作为一手出处，不凭空制造外部证据。自动选择、长期用途许可及时间字段的持久化另行决定；未决定前不把缺失 privacy 当 allow。

查询只在本次意图确定的候选范围内执行。结构化范围（人、事情、时间）不明确时先问一个能缩小范围的问题，避免全库解密。第一阶段可本地扫描有上限的用户选中集合；加密索引/中文分词/embedding 尚未实现，不能把这里的排名输入当作真实召回。

### 7.2 可执行选择算法

输入：可信适配器提供的候选、每路去重排名、用途 p、事实时间 t（可为空）、知识截止时间 k、预算 B、条数 L、来源上限 C、试验参数 rrfK。

1. **硬过滤**：active 且可解密；本次用途明确获准；引用非空且可解引用；记录时间已知且不晚于 k；若问特定时间，则必须满足 `validFrom <= t < validTo`（null 的 validTo 明确代表无结束）。缺失时间不是 0；撤权/遗忘/孤立证据直接排除。
2. **冲突检查**：只在合格召回并集里检查同一已规范化的主体+属性+范围内、当前时间同时有效却有不同值 → 不靠分数投票，转澄清。检查在截断 top-K 之前，不能把反证排到第 K+1 名就假装没有冲突；未被召回的无关记录不能触发本题澄清。无时间问题遇到历史变化可保守澄清。若反证根本未召回，本算法无法发现，所以反证召回率必须单独评估。
3. **候选融合**：各路仅对合格 ID 压缩重排，一路中同 ID 只计一次；`RRF(d) = Σ 1 / (rrfK + rank_i(d))`。平局按稳定 ID 排序。未知 ID 忽略。RRF 只作内部选材，不展示为人格/可信度分数。
4. **预算选择**：按融合顺序遍历；达到 L 停选；同来源超过 C 则略过；累计费用加当前费用超过 B 则略过，继续尝试后面的短材料。每条保留引用；不能为塞进预算切断出处或否定词。预算须预留固定指令、分隔符和输出空间，由调用者使用真实序列化体/目标 tokenizer 计量；组装后重新核算整个请求，超限则移除完整材料并重算。单项 token 数相加不天然等于最终 token 数；演示只用抽象单位。
5. **产出**：selected + citations + exclusion reasons + context/clarify/abstain。无合格证据仍可用原有模板，但不能补写个人事实；有冲突先澄清，不让 LLM 自行选一个事实。
6. **生成前后复验**：选择只是候选结果，发送前按算法二复验所有依赖；E1 再走原有 redactor/一次批准。模型输出的引用必须属于本次选择集合且仍有效；“ID 有效”只证明出处存在，不证明正文支持主张，语义蕴含需人工样本与额外验证器研究。

复杂度：N 个候选、R 条排名项、U 个融合候选，过滤/融合 O(N+R)，融合排序 O(U log U)，选择 O(U)；参考实现还排序排除项/冲突列表，因此总时间保守为 O(N log N + R + U log U)，含召回集合的额外空间 O(N+R+U)（引用总长度另计）。来源上限是可解释的去重复近似，不能宣称等价于 MMR 或最优背包；长材料会被跳过而造成召回损失，需记录预算排除率。

RRF 的演示参数 60、来源上限 1 只是合成实验配置，不是产品常量，更不是对 T4D/A0–A3 的修改。真实方案需要比较不融合 / RRF、不同候选粒度及预算，不能从这组测试宣布最佳参数。

### 7.3 用户纠正与时间的两条独立轴

现有档案字段：`effective = locked ? user_value : supported_machine_value`；锁定但值缺失时显示 unknown，不回退机器猜测。`resolveField` 仅演示这个优先原则，未重写 A0/A1。

时间性事实：事件发生时间、有效起止、系统获知时间与任务单调超时分别保存语义；不能用导入日期代替发生日期，也不能用“最新记录”推翻限定场景的用户纠正。候选文本的 claimKey/claimValue 规范化、代词消解、否定/假设识别尚未实现；未获用户确认的抽取不能自动覆盖现有事实。

## 8. 算法四：未知结果与恢复路径

这个部分给出协议设计，**未新增数据库表或可执行持久化实现**。

| 已知事实 | 用户看到的状态 | 允许下一步 | 禁止的推断 |
|---|---|---|---|
| 准入前确定拒绝 | 未开始，附原因 | 修正后重新准备 | 不能声称已发生写入 |
| 有明确提交回执，cleanup 失败 | 已提交，清理待完成 | 现有 cleanup-only 重试 | 不能再次销毁或重导来“修复清理” |
| 提交确认，但 audit 未确认 | 已提交，审计未确认 | 保留三分结果，按既有恢复能力处理 | 不能把审计失败改成事务回滚 |
| IPC/进程中断，没有可靠回执 | 结果未知 | 查询可证明的持久事实/要求核对 | 不自动重发不可逆动作；墓碑不等于完整历史回执 |
| 未来有同事务写入的操作回执 | 可据操作 ID 查状态 | 相同意图 ID 返回已有结果 | 回执未找到也可能尚在执行，需所有权/生命周期判定 |

未来导入回执流程：接收客户端意图 ID → 查已存在回执 → 验证相同参数/相同导入意图 → 单事务写领域数据和无正文回执 → commit → 返回。事务与回执要原子；外部 HTTP 不在这个事务里，也不能假称 exactly-once。操作 ID 解决“同一点击的重试”，来源稳定消息 ID 解决“不同导出文件含同一条消息”，两者不可替代。

D55 仍为后续 P1。迁移、稳定消息键、编辑过的消息、撤回消息、遗忘后重导（允许重建、拒绝或用户再次批准）、回执保留期需先明确决定。不能用新正文哈希或保留可逆内容指纹绕开遗忘。

## 9. 评价：先测正确性，再测召回，再测实际价值

| 层次 | 应测内容与指标 | 本轮证据 |
|---|---|---|
| 状态正确性 | 重复准入次数、失效结果接收数、撤权后新许可数、物理槽占用 | 可执行模型与对抗轨迹，见验证记录 |
| 选材正确性 | 禁用资料入选数、引用可解析率、冲突漏报、时间错用、预算越界 | 合成描述符测试；不是自然语言召回或安全红队验收 |
| 检索效用 | 按人/会话留出；标注相关和反证，分别报 Recall@K、反证召回、拒答精确率/覆盖率 | 未测，需真实检索适配器；不得只用平均 QA 分数 |
| 生成效用 | 档案-only、手选记忆、关键词、混合四组；盲评事实正确/语气/是否愿采用，记录改写量 | 未测；本轮无真实 LLM 调用或用户试验 |
| 运行成本 | 同一机器候选量增长下 p50/p95、峰值内存、锁占用、撤权确认耗时、上下文字节/token | 未测；不把微型 JS 执行时间当 Windows Rust 性能 |

评估集先由合成轨迹构造：单事实、跨会话、过去/现在更新、本人纠正、否定/假设、相似姓名、第三人/研究用途、遗忘、重启/未知提交。每条同时标正证据与反证，冻结测试拆分后才调参；不要把同一人的相邻片段分到训练/测试两侧。真实数据只在另行获得授权后本地处理。

研发停止条件按具体用例判断：当前迁移不破坏既有产品承诺，新增对抗断言满足，独立审查无阻塞，再进相应原有平台验证。这里不新建 Goal 1 gate，也不替代 G-L/G-W/G-M。

## 10. 落地顺序与需要拍板的精确边界

| 顺序 | 可独立交付的切片 | 修改位置 | 验证重点 | 语义决定 |
|---|---|---|---|---|
| 1 | 起草页输入/预览归属，明确模板是骨架 | Draft.tsx 与现有请求协调模式 | A/B/A、同轮双击、卸载、原文豁免绑定、discard drain；React + 原生 IPC | 不把 UI 隐藏解释为核心取消 |
