Soul 统一辅助闭环设计 v2


2026-10-16。源码基线：Xhhemoing/Soul PR #66 / 413790daaadeab933879406b8d6c01c94c5053b9。本文是下一阶段框架与实施设计；参考模型不是生产实现。用户已明确：洞察收件箱、主动提醒、自动准备待确认草稿全部需要，三者不再作为互斥选项。


1. 一个闭环，三种出口


授权信息与用户目标 → 可核对事实 → 当前上下文 → 辅助事项 → 呈现与准备 → 用户行动 → 结果反馈 → 修正后续帮助。


每件需要帮助的事共用一份核心记录。收件箱显示它，提醒指向它，草稿从它取得上下文。改期、完成、纠正或遗忘后，三个出口同步更新；不各存一份任务、不各推断一次。


全部需要不等于每件事都弹通知和生成草稿。呈现时机和准备深度分开决策：可以安静准备，也可以只提醒；关键事实不清时询问，无需帮助时静默。


保留本地优先、用户纠正、外部材料只作数据、准确 E1 请求的单次批准。v0.1 不代发消息或执行文件写入。新模型、提醒默认值与迁移尚未接入生产；本报告不是权限已经启用的声明。

4. 目标与时间：知道过去，不等于知道现在该帮什么


个人上下文分为五类：


    

  1. 观察事实：导入记录、往来和应用时段；注明覆盖，未观察不等于零。
    2. 

  2. 自述与明确偏好：例如“给同事的回复简洁”；有场景、可修改，用户锁定优先。
    3. 

  3. 目标与已确认承诺：做什么、何时、由谁、什么算完成。
    4. 

  4. 当前情境：这次任务、用户设置的时间窗与勿扰；不从应用名称猜情绪或专注。
    5. 

  5. 工作假设：有证据与反证的候选解释，不冒充已确认事实。
    6. 



MemoryType::Commitment 目前只是分类，没有 deadline、timezone、status、事实有效时间。任务事实至少要表达：来源、主体、确认状态、原始时间说法、时区与精度、完成条件、状态、修订。


明确用户输入可确认目标；聊天导出的他人要求、玩笑、转述、旧承诺只能成为候选。一个月前的“明天”不能按导入时间解析成新的明天。含糊时间不默认午夜。


必须分开：事件发生时间、Soul 观察时间、事实有效范围、带时区的提醒时间、计算/批准的单调期限。T4D 仍用数据集 as_of；提醒使用明确任务时间，不改冻结关系时钟。

6. 决策与上下文算法


6.1 变化到结果


接收已提交变化 / 明确到期 / 用户操作 / 明确反馈
→ 根据对象 ID 找到受影响事项
→ 合并同一用例、同一事项的待办
→ 准备目标、用途与领域依赖快照
→ 锁外计算；不在每个采集 poll 上启动模型
→ 接收时复核来源 / 目标 / 用途 / 版本
→ 当前结果与工作完成状态一起提交
→ 分别决定呈现方式和准备深度



新生成的摘要是派生输出，不当成新事实重新触发同一分析器。仅新事实、用户意图或有意义的到期变化引发新决策。合并工作不丢弃事实。


撤回/失效属于控制状态，不排在长任务后。用户前台操作优先于普通背景准备；背景工作保持合并待办，不能提前释放真实 worker 假装让路。具体规模、饥饿与等待问题要测量后确定，不在此冻结任意数值预算。


6.2 先资格过滤，再选择材料


依次检查：目标仍有效/未结束且符合用户明确边界 → 用途许可 → 引用可解/未遗忘 → 对象与事实时间适用 → 用户纠正优先 → 关键冲突澄清 → 有限材料选择。


用户明确限制优先于系统推断。例如用户已说明不再联系某人，往来计数下降不能形成“催促联系”的行动建议。事实正确不等于建议符合目标。


先复用已有明确候选内检索。扩大自动召回前，测漏选、错引与解密成本；语义/向量检索是可替换能力，不先设为必需底座。自动命中不获得 E1 用途。


排序优先明确任务匹配、对象匹配、时间适用、证据直接性，并列稳定。提醒新颖性、正文预算和任务重要性分开，不先合成未经验证的“智能分数”。无关缺失不妨碍能确定的部分继续准备。

6.4 自动准备与单次批准


自动阶段保存任务简报、来源引用和本地预览，不提前占用一个长期有效的 E1 许可。用户打开或确认时重新验证事项、调用既有 memory/insight 校验、构建准确发送体，再走现有 prepare / approval / execute / complete。


已有两分钟批准不无限续期。生成结束仍核对 item revision；已发生出网照实审计，过期结果拒收。本地确定性模板仍是模板，不承诺语义理解；可选获准本地模型或用户指定 E1 增强，无模型时保留统计与材料整理。


7. 跨模块可靠性


同库事务与恢复


保留已有导入事务内 W5 创建。只有跨事务、延期、需重启恢复的工作，才新增最小同库持久意图。


三个原子边界：


    

  • 领域变化 + 待处理标记。
    • 

  • 本地结果 + 对应工作完成。
    • 

  • 来源销毁 + 相关事项、待交付、待批准准备失效。
    • 



events 不是天然队列，import operation 不是通用工作日志。本地结果用明确身份/条件更新实现重复安全，无需 Kafka、云队列或第二数据库。


OS 通知/E1 与 SQL 不是同一事务。unknown 必须保留，不承诺外部“恰好一次”。


复用现有物理慢槽


现有 E1WorkerKind 已含 Draft / PersonSummary / Scan / Import。可渐进收敛为 WorkKind / ActiveWork；保持 worker 真实结束才释放及审计责任。编排不绕过 policy、store、MemorySelection 或领域规则。


导入目前要求先停 collector；长导入时 store 入口快速 IMPORT_BUSY。首版明确显示导入期间暂停分析。自动交接采集必须确认授权仍有效、用户未撤回；不能自动恢复已撤销权限。该交接仍需实际实现。


W5 一次最多读取 100 个 bundle 并重建依赖，不宜直接接高频定时全量轮询。先用来源 ID 合并受影响事项，真正展示/投递/起草前完整复验；性能优化不能省掉最终复验。


通知只带指针


系统通知默认通用提示 + 不透明 item ID，不放联系人、聊天、人格结论或草稿。点击后核心重新取当前内容。


同一依据仅重算不增加新提醒；旧通知仍能导航同一事项的当前可用内容。若没有当前有效版本，解释失效并转到收件箱，不以重新投递弥补导航断路。完成/取消在同一事务内取消待发提醒和未执行批准；已经在途、已投递或未知的尝试保留真实历史，系统撤除另记结果。


失效时取消待投递，并按稳定 Tag/Group 尝试撤除已投递通知。撤除失败单列，不能宣称销毁 CK 就能撤回 OS 已保存明文或用户已看过的信息。


首版明确应用运行/托盘存活期间提醒。退出应用仍准时提醒需要独立 Windows 生命周期与验证，不能用 React 定时器冒充。

9. 一条三出口贯通案例


合成场景：用户明确要求“周五下午四点前给项目同学发修改稿”，并允许本次参考两条相关记忆。

    2. 

  2. 新资料提交后，关联现有事实和 A2 洞察，形成同一辅助事项。
    3. 

  3. 收件箱显示依据、缺失材料与下一步；先本地准备。
    4. 

  4. 到认可时刻只发一个指向原事项的通知。
    5. 

  5. 用户打开并选择准备回复，走记忆预览和准确 E1 批准。
    6. 

  6. 用户复制，仅记录复制，任务仍未完成。
    7. 

  7. 用户明确说已发，记为自报完成并撤回待发提醒。
    8. 

  8. 改期、纠正或遗忘使旧提醒和草稿一起失效；已发生请求如实记录。
    9.
