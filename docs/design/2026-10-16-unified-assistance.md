# Soul 统一辅助闭环设计 v2

2026-10-16。源码基线：Xhhemoing/Soul PR #66 / 413790daaadeab933879406b8d6c01c94c5053b9。本文是下一阶段框架与实施设计；参考模型不是生产实现。用户已明确：洞察收件箱、主动提醒、自动准备待确认草稿全部需要，三者不再作为互斥选项。

## 1. 一个闭环，三种出口

**授权信息与用户目标 → 可核对事实 → 当前上下文 → 辅助事项 → 呈现与准备 → 用户行动 → 结果反馈 → 修正后续帮助。**

每件需要帮助的事共用一份核心记录。收件箱显示它，提醒指向它，草稿从它取得上下文。改期、完成、纠正或遗忘后，三个出口同步更新；不各存一份任务、不各推断一次。

全部需要不等于每件事都弹通知和生成草稿。呈现时机和准备深度分开决策：可以安静准备，也可以只提醒；关键事实不清时询问，无需帮助时静默。

保留本地优先、用户纠正、外部材料只作数据、准确 E1 请求的单次批准。v0.1 不代发消息或执行文件写入。新模型、提醒默认值与迁移尚未接入生产；本报告不是权限已经启用的声明。

## 2. 最新基础：W1–W5 已接线

上一版报告基于 c1d4f8f；最新分支为 413790d。旧缺口不能继续沿用。

| 能力 | 当前实现 | 仍需连接 |
|---|---|---|
| 慢任务 | 起草、摘要、扫描、导入共享物理慢槽；准备、锁外执行、接收 | 背景工作合并、优先级、延期与恢复 |
| 记忆起草 | 明确 UUID 候选内关键词/类型选择、出处预览、受控本地/E1 使用 | 目标驱动候选、时效/冲突、洞察到草稿转交 |
| 导入恢复 | 不可变准备、ID 确认、持久计数回执；重启未完成项标 interrupted | 不是通用任务/通知恢复日志 |
| 消息身份 | 密封自然键；同键相同跳过，冲突整次拒绝；SQL schema 3 | 旧历史缺 ID 不猜；forward-only 仍有历史重叠限制 |
| 本地分析 | 导入事务生成 A2 候选；完整依赖复验、精确忽略、重算、图谱纠正 | 主动提醒、统一事项、结果反馈、转交起草 |
| 应用时长 | 本次进程授权的后台采集 | 未接目标驱动分析；导入目前要求停止 collector |
| 验证 | 提交记录：720 Rust / 437 前端等局部检查 | 本轮未重跑；原生桌面和完整平台验收仍未完成 |

现有导入链：不可变准备 → 确认 → commit_indexed → 原审计 → 图重建 → committed 回执 → create_for_import。最后五步在同一事务中，应保留。

LocalInsightBundle 绑定 operation_id、namespace_id、ImportCounts，适合作导入洞察。统一事项应引用它，不能把它硬改成所有任务的万能对象。

## 3. 八个职责，不新增八套系统

| 职责 | 做什么 | 落点 |
|---|---|---|
| 输入接入 | 来源身份、发生/观察时间、隐私、覆盖、校验 | 复用 import / collect / schema |
| 事实证据 | 加密、引用、修订、遗忘 | 复用 store / memory / graph / profile |
| 目标情境 | 已确认目标、承诺、限制、完成条件、当前任务 | 新任务事实，不塞进人格轴 |
| 工作编排 | 已提交变化、到期、反馈 → 受影响事项与合并待办 | soulcore，复用物理慢槽 |
| 上下文分析 | 合格证据 → 原因、结论、缺失项、行动候选 | 复用 A2 / memory selection / draft |
| 辅助事项 | 稳定身份、当前版本、各轴状态与依赖 | 小型应用层对象，引用领域对象 |
| 三种输出 | 收件箱、通知指针、待确认草稿 | React / Tauri / 现有 draft |
| 反馈评估 | 修正事实、更新目标、有范围偏好、效果记录 | 既有纠正锁与新增明确反馈 |

这些是职责边界，不要求新建 crate、微服务或第二数据库。助手与研究用途保持分离。

| 路线 | 判断 |
|---|---|
| 三个出口各自开发分析与状态 | 易重复提醒、结论分叉、完成不同步；不采用 |
| 每个事件启动通用 Agent 循环 | 成本、权限与错误传播难控制；不作默认 |
| 统一事项 + 具体用例编排 | 复用现有能力，能追踪版本和结果；采用 |

## 4. 目标与时间：知道过去，不等于知道现在该帮什么

个人上下文分为五类：

1. **观察事实**：导入记录、往来和应用时段；注明覆盖，未观察不等于零。
2. **自述与明确偏好**：例如“给同事的回复简洁”；有场景、可修改，用户锁定优先。
3. **目标与已确认承诺**：做什么、何时、由谁、什么算完成。
4. **当前情境**：这次任务、用户设置的时间窗与勿扰；不从应用名称猜情绪或专注。
5. **工作假设**：有证据与反证的候选解释，不冒充已确认事实。

MemoryType::Commitment 目前只是分类，没有 deadline、timezone、status、事实有效时间。任务事实至少要表达：来源、主体、确认状态、原始时间说法、时区与精度、完成条件、状态、修订。

明确用户输入可确认目标；聊天导出的他人要求、玩笑、转述、旧承诺只能成为候选。一个月前的“明天”不能按导入时间解析成新的明天。含糊时间不默认午夜。

必须分开：事件发生时间、Soul 观察时间、事实有效范围、带时区的提醒时间、计算/批准的单调期限。T4D 仍用数据集 as_of；提醒使用明确任务时间，不改冻结关系时钟。

## 5. 统一身份，四轴状态

建议的应用层结构：

~~~text
AssistanceItem
  item_id, current_revision, subject_ref, goal_ref?, purpose
  origin: ImportInsight(bundle_id) | UserTask(task_id) | Memory(memory_id)
  dependency_refs, reason, expected_help, missing_information
  validity, handling, channel_deliveries, preparation_and_execution
~~~

持久部分优先用主键、修订、时间、固定状态和计数；展示时按领域校验器取正文。敏感目标和偏好也须进入现有加密/遗忘体系。这不是照字段新建同名表的迁移方案。

| 状态轴 | 示例 | 不代表什么 |
|---|---|---|
| 有效性 | current / needs_clarification / stale / forgotten | 有效不代表用户赞同 |
| 用户处理 | open / snoozed / ignored_instance / cancelled / resolved_reported / resolved_verified | 取消不代表完成；已读、复制不代表完成 |
| 通道交付 | pending / submitted_to_os / opened / failed / unknown / withdrawn | 系统收到不代表用户看过 |
| 准备执行 | none / locally_prepared / awaiting_approval / running / received / rejected / unknown | 准备不是批准，生成不是现实成功 |

操作 ID、自然消息键、事项 ID、事项 revision、投递 attempt 各有职责。通过明确对象关系合并事项，不靠正文相同猜用户意图，不新增正文 hash。

稳定导航与有条件操作必须分开。通知只指向稳定事项，打开时定位当前可用版本或说明已失效；点击本身不能批准、完成或修改事项。稍后、完成、纠正和批准等操作必须附带当前 expected_revision。旧页面操作不能重开已完成事项；明确重开应创建新修订并重新准备。参考模型中 case_id 对应设计的稳定 item_id，模型 generation 与版本 item_id 对应设计的 revision；两者不是相同的生产数据契约。

W5 忽略继续只作用于精确 bundle。新增“这件事稍后”“此类建议少一些”是独立且有范围的选择。重算的新 bundle UUID 不得重置事项级稍后/静默；真正的新问题也不能因为过去忽略同一联系人而永远被屏蔽。

## 6. 决策与上下文算法

### 6.1 变化到结果

~~~text
接收已提交变化 / 明确到期 / 用户操作 / 明确反馈
→ 根据对象 ID 找到受影响事项
→ 合并同一用例、同一事项的待办
→ 准备目标、用途与领域依赖快照
→ 锁外计算；不在每个采集 poll 上启动模型
→ 接收时复核来源 / 目标 / 用途 / 版本
→ 当前结果与工作完成状态一起提交
→ 分别决定呈现方式和准备深度
~~~

新生成的摘要是派生输出，不当成新事实重新触发同一分析器。仅新事实、用户意图或有意义的到期变化引发新决策。合并工作不丢弃事实。

撤回/失效属于控制状态，不排在长任务后。用户前台操作优先于普通背景准备；背景工作保持合并待办，不能提前释放真实 worker 假装让路。具体规模、饥饿与等待问题要测量后确定，不在此冻结任意数值预算。

### 6.2 先资格过滤，再选择材料

依次检查：目标仍有效/未结束且符合用户明确边界 → 用途许可 → 引用可解/未遗忘 → 对象与事实时间适用 → 用户纠正优先 → 关键冲突澄清 → 有限材料选择。

用户明确限制优先于系统推断。例如用户已说明不再联系某人，往来计数下降不能形成“催促联系”的行动建议。事实正确不等于建议符合目标。

先复用已有明确候选内检索。扩大自动召回前，测漏选、错引与解密成本；语义/向量检索是可替换能力，不先设为必需底座。自动命中不获得 E1 用途。

排序优先明确任务匹配、对象匹配、时间适用、证据直接性，并列稳定。提醒新颖性、正文预算和任务重要性分开，不先合成未经验证的“智能分数”。无关缺失不妨碍能确定的部分继续准备。

### 6.3 呈现和准备分别决定

| 条件 | 呈现 | 准备 |
|---|---|---|
| 无实质变化、无未解决目标 | 静默 | 不重复算 |
| 可核对新信息，无即时行动需要 | 更新原收件箱事项 | 整理本地材料 |
| 缺少影响行动的关键事实 | 在原事项问关键问题 | 继续确定部分 |
| 已确认承诺到达认可提醒时刻 | 指向原事项的提醒 | 资料与本地草稿 |
| 勿扰 / 稍后 / 类别静默 | 收件箱保留，延后打扰 | 已获准的本地准备可继续 |
| 需要 E1 | 准确预览待批准 | 不后台出网 |
| 完成、取消、遗忘或撤权 | 更新/撤回出口 | 旧准备失效 |
| 设备恢复时已过期 | 标明“恢复后发现到期” | 重新筛选，不逐条补发 |

仅有前台应用时长不足以识别最佳中断时机。先用明确时间窗、应用内勿扰及获准系统信号，不新增截屏、窗口标题或键盘采集来凑能力。

优先顺序：明确到期要求、显式优先级、当前目标相关性、可执行性、新变化；并列稳定。新提醒默认值属于待验证产品设置，不冒充科学定律。

### 6.4 自动准备与单次批准

自动阶段保存任务简报、来源引用和本地预览，不提前占用一个长期有效的 E1 许可。用户打开或确认时重新验证事项、调用既有 memory/insight 校验、构建准确发送体，再走现有 prepare / approval / execute / complete。

已有两分钟批准不无限续期。生成结束仍核对 item revision；已发生出网照实审计，过期结果拒收。本地确定性模板仍是模板，不承诺语义理解；可选获准本地模型或用户指定 E1 增强，无模型时保留统计与材料整理。

## 7. 跨模块可靠性

### 同库事务与恢复

保留已有导入事务内 W5 创建。只有跨事务、延期、需重启恢复的工作，才新增最小同库持久意图。

三个原子边界：

- 领域变化 + 待处理标记。
- 本地结果 + 对应工作完成。
- 来源销毁 + 相关事项、待交付、待批准准备失效。

events 不是天然队列，import operation 不是通用工作日志。本地结果用明确身份/条件更新实现重复安全，无需 Kafka、云队列或第二数据库。

OS 通知/E1 与 SQL 不是同一事务。unknown 必须保留，不承诺外部“恰好一次”。

### 复用现有物理慢槽

现有 E1WorkerKind 已含 Draft / PersonSummary / Scan / Import。可渐进收敛为 WorkKind / ActiveWork；保持 worker 真实结束才释放及审计责任。编排不绕过 policy、store、MemorySelection 或领域规则。

导入目前要求先停 collector；长导入时 store 入口快速 IMPORT_BUSY。首版明确显示导入期间暂停分析。自动交接采集必须确认授权仍有效、用户未撤回；不能自动恢复已撤销权限。该交接仍需实际实现。

W5 一次最多读取 100 个 bundle 并重建依赖，不宜直接接高频定时全量轮询。先用来源 ID 合并受影响事项，真正展示/投递/起草前完整复验；性能优化不能省掉最终复验。

### 通知只带指针

系统通知默认通用提示 + 不透明 item ID，不放联系人、聊天、人格结论或草稿。点击后核心重新取当前内容。

同一依据仅重算不增加新提醒；旧通知仍能导航同一事项的当前可用内容。若没有当前有效版本，解释失效并转到收件箱，不以重新投递弥补导航断路。完成/取消在同一事务内取消待发提醒和未执行批准；已经在途、已投递或未知的尝试保留真实历史，系统撤除另记结果。

失效时取消待投递，并按稳定 Tag/Group 尝试撤除已投递通知。撤除失败单列，不能宣称销毁 CK 就能撤回 OS 已保存明文或用户已看过的信息。

首版明确应用运行/托盘存活期间提醒。退出应用仍准时提醒需要独立 Windows 生命周期与验证，不能用 React 定时器冒充。

### 恢复纪律

| 工作 | 重启处理 |
|---|---|
| 本地纯计算 | 复验来源后认领重算 |
| 提醒 | 核对当前目标、时效、稍后/静默与投递历史；积压重新筛选 |
| E1 准备 | 重新准备/确认，不复活旧批准 |
| 已开始但结果未知的 E1 | unknown，不自动重发或切换端点 |
| UI 旧入口 | item_id + expected_revision 条件更新 |
| 采集与用途 | 不恢复本次采集授权；助手/研究不互相继承 |
| 已遗忘依据 | 不从历史计数、缓存或新 UUID 恢复正文 |

## 8. 反馈修改正确的对象

| 用户行为 | 更新 | 不推断 |
|---|---|---|
| 查看 / 打开 | 通道交互 | 不代表采用或完成 |
| 复制 / 编辑 | 当前草稿操作 | 不代表已发送、有效、永久偏好 |
| 忽略这份摘要 | 精确 bundle | 不改事实、不训练人格 |
| 这件事稍后 | 事项提醒时间 | 不代表不重要 |
| 此类建议少一些 | 指定类别/情境策略 | 不影响所有任务 |
| 事实不对 | 对应事实/纠正锁及依赖 | 不只藏起错误提示 |
| 这不是我的目标 | 目标关联/确认状态 | 不因旧文本再次确认 |
| 取消这个目标 | 该目标及其派生事项取消，撤回待交付和旧准备 | 不改写来源事实、长期偏好或其他关联目标 |
| 以后用这种语气 | 有范围、可撤销偏好 | 不泛化单次编辑 |
| 我已完成 | 自报结果 | 不冒充独立核实 |
| 可核对完成证据 | verified 及来源 | 不把缺反馈当失败 |
| 无反馈 | 未观察 | 不算满意或拒绝 |

先适应提醒时机、呈现形式、明确偏好与准备习惯；人格轴/关系规则保持独立。未来学习算法必须有离线比较、实际试用与回退，不能以点击率替代用户目标。

## 9. 一条三出口贯通案例

合成场景：用户明确要求“周五下午四点前给项目同学发修改稿”，并允许本次参考两条相关记忆。

1. 保存已确认承诺与时区；含糊时只澄清关键时间。
2. 新资料提交后，关联现有事实和 A2 洞察，形成同一辅助事项。
3. 收件箱显示依据、缺失材料与下一步；先本地准备。
4. 到认可时刻只发一个指向原事项的通知。
5. 用户打开并选择准备回复，走记忆预览和准确 E1 批准。
6. 用户复制，仅记录复制，任务仍未完成。
7. 用户明确说已发，记为自报完成并撤回待发提醒。
8. 改期、纠正或遗忘使旧提醒和草稿一起失效；已发生请求如实记录。

若没有已确认承诺，同样的导出只能支持观察或候选机会，不能自行催促联系。此例展示目标框架，不代表当前已有截止任务、系统提醒或发送连接器。

## 10. 分块实施：先规划验证，再编码

所有工作包都服务完整目标；顺序体现依赖，不删任何出口。

| 包 | 交付 | 编码前决定 | 验收 |
|---|---|---|---|
| U1 统一事项 | 外壳、revision、跨页打开、草稿转交 | 事项身份、来源类型、何时新建 | 三入口同身份；旧动作拒绝；不复制正文 |
| U2 目标承诺 | 确认/候选、时间时区、完成取消 | 歧义时间、完成定义、遗忘单位 | 旧“明天”不变新截止；外部文本不授予权限 |
| U3 触发恢复 | 受影响范围、合并、持久待办 | 迁移、状态、采集导入交接 | 回滚无候选；提交不漏本地工作；不复活批准 |
| U4 收件箱提醒 | 同事项投递、稍后/静默、通知指针 | 退出语义、频率、系统权限 | 无重复打扰；改期/完成撤回；unknown不冒称送达 |
| U5 任务准备 | 事项→证据→本地准备→批准→草稿 | 候选范围、重新准备条件 | 未批零E1；失效拒收；物理槽不早释放 |
| U6 结果适应 | 明确反馈、完成、场景偏好与撤销 | 作用范围、证据等级 | 复制不算完成；忽略不改事实；偏好不越界 |

参考模型也不验证生产批准的两分钟期限、单调时钟、端点配置 A→B→A 修订以及生产物理慢槽。Linux 独占租约仅用于合成模型；恢复必须每个新持有期只执行一次，并统一数据库与租约的规范化路径，不能通过别名打开第二个逻辑持有者。

| 效果 | 指标 | 限制 |
|---|---|---|
| 事实可靠 | 无依据断言、错引、纠正残留、可追溯率 | 有引用不等于引用支持结论 |

先合成故障，再经许可的真实任务试用；报告分母、样本、未知与覆盖。没有数据不承诺精准度或节省比例。“完美”转化为可验证的一致、可恢复、可纠正；实际帮助持续测量。
