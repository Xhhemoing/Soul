# DATA-01：迁移、恢复与遗忘边界设计草案

日期：2026-10-19。状态：**设计候选，已完成独立只读评审；产品决定待定，实施未启动**。

本草案最重要的限制是：遗忘当前库中的 CK，不能追溯销毁已经复制到离线旧备份中的 CK。若数据库、根密钥和同库遗忘记录一起回滚，仅凭旧包内部信息无法判断备份后发生过哪些遗忘。不得把“增加墓碑”写成绝对保证，也不得为解决此问题自动增加出网或跨设备协调。

## 1. 范围与依据

源码可行性核于 `2e37a6e`。本轮密钥并发锁修复不构成备份、迁移或跨机恢复实现。

目标是形成可以评审的现状/差集、反例、选择及未来验收。非目标包括：新增生产 API、schema、锁文件、哈希、baseline、gate 或冻结 contract；批准任何密钥方案；实现备份；读取真实库/密钥/导出；开启研究输出或网络；新增 Goal 1 关闭条件。

权威关系：[ROADMAP](../ROADMAP.md) 第 5、8 节安排 DATA-01/02，DATA-01 依赖 M1、RES-01；[PRODUCT_LOCK](../PRODUCT_LOCK.md) 的 v0.1 砍/留表将本人全量导出与研究落盘列为 v0.2；[SECURITY](../SECURITY.md) 保留 CK 遗忘、无正文审计和既有威胁模型。作者已授权提前设计，未豁免 Goal 1/Q2/M1 实施前置。正式 G-L 暂缓、系统 G-M 后置，均不改写为通过。

证据等级：`[V-source]` 为本轮直接阅读到的源码/规范，非运行验证；`[H]` 为基于这些机制的推导；`[T]` 为候选设计或尚待决定/验证项。本文所有未来验收均**未运行**。

## 3. 必须正面回答的反例

### 3.1 旧 CK 随旧库回滚

`[H]` 在合成时刻 t0，库中有 Memory M、CK K、包装 K 的 KEK 和可打开库的 DEK，制成完整备份 B0。t1 在当前库明确遗忘 M：删除 K、写墓碑、使引用失效，并完成 WAL 清理。t2 若恢复逻辑直接用 B0 替换当前库及密钥材料，B0 仍有旧 K，且没有 t1 的墓碑；在原 DPAPI 上下文或未来可解包的迁移密钥下，M 可重新读取。

这不是现有公开恢复功能的已复现 bug：本轮没有执行备份/恢复，现有 v0.1 也未提供 DATA-02 入口。它是新增恢复能力必须处理的具体设计失败路径。当前库完成 CK 销毁的承诺继续成立；对外部旧副本的追溯销毁不能伪称已实现。

两段历史可向恢复程序呈现完全相同的 B0：历史 A 在 t0 后没有遗忘；历史 B 在 t1 遗忘后丢失全部最新状态。若恢复程序只得到 B0 和同样的解密材料，两者输入相同，不可能据此区分。即使 B0 的内部审计链完整，也只说明备份时的链，不能证明没有后来操作。

| 现有手段 | 能解决什么 | 为什么单独不能解决该反例 |
|---|---|---|
| Git/源码 SHA | 标识读取逻辑版本 | 不记录个人库在备份后发生的遗忘 |
| schema/包版本 | 决定能否解释结构 | 相同版本可以对应两段不同删除历史 |
| UUID/主键/唯一约束 | 限制库内身份与冲突 | 旧行与旧 CK 本来就是合法且唯一的 |
| 事务 | 避免一次写入半提交 | 可以原子地恢复一整份已经过时的状态 |
| 类型 | 禁止结构或状态误用 | 无法制造已经丢失的删除事实 |
| 普通回归测试 | 显示并约束已定义恢复行为 | 不能让只持旧包的程序获得缺失历史；应验证它拒绝超出可知范围的恢复 |
| 同包墓碑/校验摘要/链 | 发现部分缺失或篡改，保留包内已知删除 | 包和删除状态一起回滚时仍一致；新增 hash 不解决新鲜度 |

因此本文不提出新增 hash、baseline 或 gate。即使将来采用独立删除状态，也只能约束受管理恢复入口；已离线持有可解密旧副本的人不在可追溯销毁能力内。

### 3.2 换机器与错误的“修复”

`[H]` 将合成库与 `keys.dpapi` 从账户/机器 A 复制到 B：现有 provider 没有跨机恢复协议，DPAPI 解封可能失败。换成 TestKeyProvider 或生成全新 KEK 不会让原 CK 解开；换新 DEK也不会让旧页正确解密。当前密钥并发锁修复仅解决完整读写竞争，不产生可携带恢复密钥。具体 DPAPI 凭据迁移/域环境行为需 Windows 实机验证，不能推广为所有环境都一样。

### 3.3 合并、重新编号与用途洗白

`[H]` 两个独立库都使用固定 owner UUID，直接合并可能误认同一人；UUID 冲突按覆盖处理可能丢失纠正、证据或审计。给旧内容换 CK/行 UUID 还会使原墓碑匹配失效，且 AAD 绑定要求真实重新密封，不能只改 JSON 指针。个人备份中的 third/mixed 或研究 deny 行若被恢复为 self/bucket，则是用途升级，不能由“本人点了恢复”自动授权。

## 4. 恢复承诺的三种候选

以下均是 `[T]` 选项，尚无产品决定。建议先评审 A 的可支持范围；若主要用例是原设备全损，必须先回答 C 的信任前提，不能悄悄把 B 包装成完整恢复。

| 候选 | 接受/拒绝边界 | 收益 | 代价与未解决项 |
|---|---|---|---|
| A：保留当前删除权威的受限恢复 | 只在仍有可信、未随源包回滚的删除状态，且能核对原库范围和全部删除依赖时，恢复未撤销部分；无法核对则不解封/交付正文 | 可先限定同一受管理数据来源的局部损坏恢复；不默认 merge | 当前没有跨库来源/删除状态完整性契约；仅有一份旧包或本机全损时不能承诺内容恢复；需要决定如何确认“可信且完整” |
| B：拒绝内容恢复或仅恢复可证明安全的部分 | 没有可信删除状态时拒绝正文恢复；若以后允许恢复有限元数据，必须证明它不包含已遗忘内容或敏感引用，否则也拒绝 | 行为诚实，避免错误承诺 | 不满足全量灾难恢复需求；元数据也不天然安全，不能默认释放人物、来源或明文摘要 |
| C：依赖独立、可存续的删除状态 | 在数据库/包之外选择受信删除权威或密钥撤销机制，并定义其断连、回滚、丢失和恢复规则 | 可能覆盖更广的受管理恢复情形 | 多一次不可失的信任依赖；若该状态也一起回滚，问题重现；硬件、用户离线记录或设备协作各有恢复/撤销代价，必须单独决定与评审；本文不选供应商、不启网络 |

“用户确认恢复到旧时间点，并承认遗忘内容会回来”改变 DATA-02 现有“不重生”要求，不能作为默认绕过。若作者希望这种能力，需显式重审产品/安全决定；本草案不授权该改变。

受限恢复仍需注意：只并入 `destroyed_content_keys` 表不足以处理重编号或历史无墓碑。未来必须先在原来源身份下核对删除范围，再做任何重包装/重密封；不能以先解密展示、后筛除来达到“不交付已忘内容”。如何在损坏/缺失元数据时核对必须有明确拒绝路径。

## 5. 数据、密钥与身份的候选边界

### 5.1 replace 与 merge

建议首个设计增量只讨论 replace 到**隔离候选目录**，最终替换仍需用户看到明确影响并确认；不是立即覆盖活动库。merge 应为独立后续能力，依赖来源身份、冲突及遗忘传播决定。两者均不能越过第 4 节的删除可知范围。

| 方面 | replace 需要决定/验证 | merge 额外需要决定/验证 |
|---|---|---|
| 活动数据 | 停止新慢任务、等待物理 owner 结束，取得正确规范路径所有权；保留目标当前删除状态 | 同时保护来源和目标，明确固定锁顺序与事务范围，禁止两个存储互等 |
| 一致快照 | 使用可验证的一致备份路径，评估实际 SQLCipher/驱动支持；不能在活动 WAL 下只复制主库 | 跨库读取快照与目标提交边界，避免读取期间来源变化 |
| 失败与切换 | 在隔离副本做兼容/解密/证据检查；DB、平台密钥和必要配置不得新旧错配 | 冲突整次拒绝或明确部分规则，禁止静默最后写覆盖；需可判定提交回执 |
| 原子性 | Windows 多文件切换不是一个 SQLite 事务；需将安装态和崩溃恢复设计清楚，未证明前不声称原子替换 | 目标事务不能证明源授权/删除状态始终有效；提交前须重新核对 |
| 回滚 | 失败保留当前可用库与删除事实；切换后发生新遗忘不能用旧副本回退而重生 | 已提交合并与后续遗忘必须分开；撤销合并不恢复已销毁密钥 |
| 审计 | 原链作为来源历史独立验证、标明范围；本地恢复动作只写允许的元数据 | 不拼接两条独立链、不改写既有历史；映射来源与本地结果的语义需决定 |

### 5.2 解密与密钥携带

候选 K1 是同平台上下文内保留现有 DPAPI 材料，适合受限本机恢复，但不能宣传跨机。候选 K2 是未来由用户持有的恢复凭据保护可携带密钥材料，到目标平台验证后重新保护；候选 K3 是逻辑导出受许可内容，在目标生成新密钥与 CK 后逐条重密封。K2/K3 均需独立密钥评审，确定恢复凭据丢失、错误、暴力尝试成本、撤销、内存清理及损坏处理；本文不挑算法/参数或创建明文根密钥文件。

K2 只换根包装不能消除旧包中的 CK；K3 可能为旧内容生成新 CK，若未先核原始删除范围，反而绕过旧墓碑。两者均不是遗忘约束的替代品。任何恢复工作日志、审计和错误提示不得携带密码、密钥、正文或原始端点凭据。

### 5.3 跨库身份与用途

未来需明确“同一个人”“同一条数据来源谱系”“同一份导入账号 namespace”三种关系。固定 `OWNER_PROFILE_ID` 仅为本地约定，不能证明这三者相同；不得从文件名、显示名或相同账号字符串猜身份。首次恢复/合并如何建立来源关系、原对象 ID 是否保留、旧证据及 CK 身份如何映射，都须在修改 schema 前决定。

行 ID、字段 AAD、CK 包装 AAD、evidence 引用必须一起核验。恢复后重新跑现有领域验证与受支持 rebuild；无法解引用的材料不得展示为有效证据。机器推断与用户纠正保持分离，不借迁移重算覆盖用户锁。导入旧数据的索引覆盖缺失继续明确显示，不能补造全历史去重。

建议未来恢复只交付数据，不恢复旧 E1 批准、采集同意、文件根许可、运行中 worker、自动研究同意或提醒的旧派发许可。此处是恢复入口的候选规则，不描述当前正常重启对已存配置的全部行为。来源变化后重新准备/确认，已有 unknown 的网络与通知历史保留事实，不自动重放；具体设置与偏好哪些可搬迁仍待逐字段决定。

### 5.4 本人备份与研究聚合分离

个人备份属于本地个人资料的受控保存/恢复；其中是否包含合法持有的 third/mixed 数据须单独定义，不因“本人”一词自动排除或授予第三人出网许可。研究输出另用研究许可、字段最小化和聚合规则；不得含可恢复 CK/DEK/KEK、原文或稳定个人身份索引，不得用个人恢复包转格式来绕过 RES-01 的逐行用途限制。

v0.1 继续研究预览且不落盘。后续设计需先解决档案轴派生许可、独立同意与缺测/截断说明，不能把当前预览的技术过滤直接当正式导出授权。即使研究聚合文件将来获准，也不用于还原个人库；两种入口、请求类型、预览、确认和测试应明确分开。本人备份同意不继承到研究或训练，研究同意也不授予备份内第三人正文出站。

## 6. 决策清单

这些是应交作者/主会话收敛的问题，不是实现者可以自行填入的默认值。

| 问题 | 必须选定的范围 | 未决定前的候选行为 |
|---|---|---|
| DQ1：优先恢复哪种故障 | 同库局部损坏、同账号重装、原设备全损或跨机迁移 | 只设计，不创建恢复入口 |
| DQ2：删除权威由谁保有 | 当前存续状态、另行受信状态；各自丢失/回滚如何识别 | 无法证明范围时拒绝内容恢复；不默认使用包内删除表作最新权威 |
| DQ3：首版是否只 replace | 隔离目录、切换确认、失败状态；merge 是否后置 | 不提供自动 merge/upsert 或活动目录覆盖 |
| DQ4：密钥可携带方式 | K1/K2/K3 及恢复凭据、威胁模型和平台矩阵 | 不把 DPAPI blob 当跨机包，不输出明文根密钥 |
| DQ5：跨库来源身份 | 独立库识别、同人关联、旧 ID/AAD/CK/引用映射、历史无索引处置 | 不根据固定 owner UUID、名字或路径建立关联 |
