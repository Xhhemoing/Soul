# 沟通材料的有界检索对照

日期：2026-10-21。候选起点：`codex/soul-rebuild-20261019` @ `6a56d852d23a051c7c4e9845642791295c541105` + dirty。接续[共同准备](2026-10-21-communication-joint-preparation.md)的独立代码审查；该片最后的 Rust 回归期间只准备仓库外实验草稿，完成收尾后才应用并运行本实验。当前状态以 [STATUS](../STATUS.md) 为准。

## 问题与范围

[首批诊断](2026-10-21-communication-material-diagnosis.md)揭示硬词面筛选漏掉改写和更新，但三条材料全部放入不能证明通用检索改善。本片检验：在原有显式候选和预算内，软词面排序或交错补选能否稳定改善必要材料覆盖，代价是多少无关材料。不改变生产选择器、授权、D72、schema、T4D 判档或冻结常量。

只读调查确认：`soul-memory/src/selection.rs` 的 query 按空白切词并要求所有词命中；非空 query 再按标题命中数排序，无 query 保留候选顺序。默认 32 候选、8 条输出和 16 KiB 上下文；实际起草另有 64 KiB 请求预算。Memory 没有可直接使用的事项／联系人／事实有效时间索引，非空外部来源关联目前会被选择器排除。因此本片不把候选位置、UUID 或相似标题冒充同来源或修订关系。

## 实验设计

新增默认 ignored 的 `communication_retrieval_probe`，复用真实临时 Session、SQLCipher 与受控 loopback；不改旧 15 卡及其历史期望值。三类沟通各有词面正常、未见改写、更新反证三种新卡，候选规模 3／8／16／32，各作必要记录前／中／后三种顺序，共 108 卡、432 条件。每卡有两条人工标注的必要材料；更新卡另标其中一条更新。其他材料明确属于别的事项，较大候选池包含足够词面噪声以挤占 8 条预算。

| 条件 | 选择方法 | 能回答的问题 |
| --- | --- | --- |
| 人工必要集 | 仅从同池给出人工真值 IDs，再走真实无 query 选择 | 同样预算能否保留必要材料；不能算自动检索能力 |
| 当前生产筛选 | 全池、原 query、现有真实 selector | 当前漏召回与噪声挤占 |
| 实验软排序 | 仅看 query／标题／摘要的词面命中数排序，未命中排尾；真实无 query selector 执行预算 | 从硬排除改为排序能改善多少；噪声多时是否仍失败 |
| 实验交错补选 | 词面匹配与未匹配两列 1:1 交错，再走同一 selector | 留位置给未命中的收益及挤掉匹配材料的代价 |

排序器不得访问 required、update 或 scene 标签；固定规则不针对观测结果调词典、配额或真值。真实选择后核对引用／摘要／IDs；独立明确允许所有已选 Owner excerpts 后作真实准备，核对最终 retained IDs、完整材料与请求预算，批准及网络请求均为零。这里只准备，不执行模型生成。

记录必要／更新保留数、无关条目与其字节、选择到准备保留、候选顺序敏感性。输出只含固定标签、索引和统计，不带正文或 UUID。阶段计时注明范围：实验排序直接读取合成 fixture 文本，不声称测到生产读取／解密／端到端性能；单次固定次序也不用于排序性能优劣。无更新卡的可用更新数量为 0、更新保留结果为 null，不计算其更新覆盖率。真实用户效用、模型质量和费用仍未测。

## 决策规则

- 若 16／32 候选时只增加噪声，不能稳定保留更新，就不将软排序或交错补选设为默认；保留失败位置与分母。
- 不因为无 query 能填满上下文就认为资料充分；材料存在不证明事实最新、无冲突或可承诺。
- 若要生产化补选，须先明确 query 从硬筛选变为偏好的产品语义及展示，再实现。当前不暗改 D72 或授权范围。
- 无可靠来源／事项／修订关系时，先设计显式关系或受限语义重排的独立对照；不直接新增持久向量库或依赖大模型来遮盖候选范围问题。

主线程持有构建通道；实验作者只写新 probe，评审者只读审查实验与原始结果。没有真实资料、生产端点、采集、安装、提交或发布。

## 实际结果

## 解释限制与下一步

**本实验未向检索规则提供完整的任务范围。** query 只有“样机 交接”等两个词；人工真值依据明确的“本事项甲组／其他事项乙组”区分，规则并不知道当前目标组。它测量的是指定相关性标准下的两词检索覆盖压力，不是系统已经理解用户任务后的准确率。人工必要集掌握答案，只是材料与预算可达的参考。不能由本结果推断向量或语义重排自然能猜出缺失的任务范围。

据此保留生产 query 行为，**不将软排序或固定交错配额上线为默认**，也不增加场景同义词表、扩大输出预算或继续调这批卡。下一近期验证点先补足“本次任务是什么、对象／事项范围是什么、哪些材料明确相关”的本地输入，再在同一个范围内比较词面排序与受限语义候选；保留人工明确选料作参考。若需要更新关系，采用可追溯的显式关联设计，不从 UUID、顺序或“最新”猜测。任何生产语义改变仍应明确记录 D72 的变化和 UI 解释。

性能比较继续放在材料覆盖达到同等水平之后。本片没有引入外部依赖、模型调用、持久索引、额外多 agent 运行链或生产存储成本；已经排除了两种实现很便宜但在大候选池不稳健的默认方案。缺失事实判定、完整语义推理、真人沟通效用和模型费用仍未验证。
