# 固定取材数量与任务需求停止：实施计划及回执

日期：2026-10-21。起点 `codex/soul-rebuild-20261019` @ `6a56d852d23a051c7c4e9845642791295c541105` + dirty。用户已授权本轮实现、同候选合成对照与独立评审，之后再推进缺口识别和澄清。沿用[六任务三条件对照](2026-10-21-retrieval-controls.md)的候选、真值及两种排序，不调整旧材料来适应新策略。当前进度只在 [STATUS](../STATUS.md) 维护。

## 目标、方案选择与边界

比较固定前缀 2、3、4、8 条与按机器提取的任务信息需求停止。保留 BM25＋精确分组＋MMR 和上一轮已经取得的受限语义完整排序：18 case × 2 排序 × 5 策略，共 180 个条件。两个排序在同一 case 使用相同候选和同一份机器需求／支持映射；策略只决定前缀长度，不重排、不跳过不喜欢的前列材料、不读取池外内容。

固定 K 无额外模型依赖，但可能漏事实或取太多。逐条在线调用模型判断充分性更接近线上停止，却需要不同数量的额外调用和完整成本实验。本轮先实施可复核的两阶段离线方案：六次仅看任务的信息需求抽取，加十八次不看排名的全池支持映射，再由纯 Rust 按固定排名累计支持。这能比较选取量与实际准备字节，不能宣称减少了模型读取量、在线延迟或总费用。规则、prompt 和上限在取得任何本轮预测或评分前确定，不根据成绩修改。

本轮不实现生产检索、缺口类别识别、澄清生成或起草发送。只使用已有合成 fixtures、临时 SQLCipher 库及受控未使用 loopback；不读取真实聊天、真实库、凭据或采集源。无新依赖、hash、冻结 contract、baseline 或 gate；普通类型、完整排列校验、真实快照及测试承担本次验证。

## 不读取人工真值的停止策略

第一阶段每任务一个新的无历史代理，只获得 `task_id` 与 scope / intent / constraints，提取完成任务必须有证据支持的信息需求，不得看到候选、旧排名、评分或人工事实。输出形状：

```json
{"task_id":"t0","needs":[{"need_id":"n0","description":"一个需要材料回答的具体问题"}]}
```

需求数量 1–8、ID 唯一、描述非空有界。它们是机器预测，可能漏掉重要约束或增加不必要需求。空需求列表在这些需检索任务中记为提取不可用，不利用空集真值在零条宣布满足；不人工补需求、不选择性重试。同一份需求原样用于该任务的三个候选条件。

第二阶段每 case 一个新的无历史代理，只获得任务、该机器需求和原候选；不提供任何排名或固定 K 成绩。输出每个需求的充分支持组：

```json
{"case_id":"q00","supports":[{"need_id":"n0","groups":[["sourceA"],["sourceB","sourceC"]]}]}
```

**组内 AND、组间 OR**：A 单独充分，或 B 与 C 共同充分；不能把需要共同支持的材料误作任取一个。每个需求恰好一项，组非空、ID 不重复且只能来自可见候选。`groups: []` 表示映射器未确认充分支持，格式仍合法；不等于真实材料缺失。对象、阶段、更新、撤回与许可必须适用于本任务；不能只因文本提及相关词而宣称支持。重复正文不能被要求凑齐多个副本；未解决冲突不能任意择一当充分。

Rust 从第一条开始累加前缀：当所有需求至少一个充分支持组完整落入前缀时停止，最多八条。没有满足则取八条，原因 `budget_cap`；不把它改称真实证据不足。记录每需求的首个满足位置、触发支持组与最终满足状态。两排序共用同一份映射，不给语义排序额外信息。

机器支持映射是可能犯错的全池辅助判断。它可能借助后面的更新判断前面来源的有效性；本轮只要求被选前缀包含其宣称的完整支持组，不声称只读该前缀即可作出相同决定。原始需求、映射错误原样保留并事后分析，不把它们当正确 oracle。结构解析与合法 ID 检查也不证明语义支持正确。

## 真实准备与可比较指标

共用测试 Harness 增加 `observe_prefix(snapshot, full_rank, k, allow_owner)`。先复验本次目标、全部可见候选及 compact14 的隐藏来源，验证完整排名，再限制实际交给 Session 的前 k 条。拒绝 k=0、超过八条或超过候选数；无有效预测记不可用，不伪造零字节请求或准备成功。旧 `observe` 继续提交完整候选，不改成前八条，以免改变原来的预算跳过行为。

所有准备继续使用真实 `prepare_memory_context` 和 `prepare_draft_with_memory`，保持相同 paste、query=None、类型、授权选择、脱敏及现有 16 KiB／64 KiB 上限。仅允许实际选中前缀的 Owner 正文；尾部、隐藏 aliases 与任务目标不自动进入请求。原始 citation 与来源复验保持，邮箱等标识正常占位。所有条件零批准、零执行、零生成请求。

分别记录 requested_k、实际 selected 和 retained。当前短材料应真实保留所请求的前缀；通用 helper 不从第 k+1 条补足预算排除项。请求字节直接读取真实 prepared.encoded_bytes，不用摘要长度相加替代，不假定字节与条数线性。

需求满足状态在实际 retained IDs 上复算，不能只因计划前缀足够就把实际准备标为充分。该判断仍以支持来源是否保留为口径，隐私脱敏可能替换联系方式等细节，不据此宣称最终回复能完整传递所有原文信息；`false_sufficient=0` 也只表示没有漏掉本批预标事实，不排除未知约束或映射错误。

每个条件报告：

- 人工必要事实覆盖、遗漏数、完全覆盖任务；any-of 支持只计一次。
- 不适用条目、辅助条目、精确正文重复占位、选取及保留数。
- 实际准备请求字节、引用丢失和出站请求数。
- 自适应的机器需求满足数、停止位置、停止原因；尤其记录**机器宣称全部满足，但人工必要事实仍缺失**的条件。
- 预测不可用及原因；分母保持 180，其中固定 K 144、自适应 36。缺失映射不令固定 K 不可用，非法语义排名则其五个策略均不可用，不能借 MMR 补全。

人工事实及类别只在最终评分使用。决策模块不依赖 fixture 的 Case/Fact 或人工接受来源集合；手工构造的普通单测只验证规则，不把测试答案传入真实预测。

## 说明了什么及下一研究范围

1. **最先暴露的是需求粒度与充分性判断。** 步道婉拒任务中，机器要求活动及个人安排的“具体时间”，材料只说明同日的毕业典礼冲突；照片跟进任务中，机器要求三张照片“分别是什么”，材料只确认三张小样已交付。人工必要事实在这两类任务中可以全保留，映射器却未确认该细化需求，导致两个排序在这五个有效 case 共十次取满八条。这是机器提出了过细需求或映射未确认，不能直接标为真实缺口并去问用户。
2. **停止不能代替召回。** `q11` 的材料收件／反馈截止条件在 MMR 排第十，固定八条和自适应均遗漏；这次预算耗尽对应真实前缀缺事实。应区分“池中有、当前前缀没取到”和“候选池本来没有”，不能把增加无关材料或直接澄清当唯一办法。受限语义在同池前两条已有这项条件。
3. **前两三条也不总够。** 钱包任务有找回位置、停止代问、钥匙仍待找三项必要事实。语义固定两条三种条件均缺一项；duplicate32 的前三条含辅助材料，钥匙事实在第四，固定三条仍漏一项。新研究保留任务复杂度与高排名辅助材料反例，不据本批固定四条 39/39 直接改生产默认。
4. **本批没有观测到错误的充分声明，但不证明其可靠。** 有效自适应中，MMR 十一次、语义十二次在八条前宣称满足，共 23 次，均未漏掉预标事实；其余十一次预算耗尽（MMR 六、语义五），另两次结构不可用。机器需求和支持仍可能有未评分的语义问题。固定 K 行里的 `false_sufficient` 只是后验映射审计，固定策略本身没有宣称充分。
5. **格式可靠性本身也有成本。** 单次映射失败造成 2/36 自适应条件不可用；生产若采用回退或有限重试，必须计入成本及覆盖，不能从本轮悄悄借固定 K 补成成功。本轮保留失败，没有实现新回退行为。

独立评审收口后，下一研究先围绕“哪些缺口会改变这次回复”设计新的未见合成任务：保留固定四条／八条与两种排序为对手，分别构造排序窗口遗漏、池内缺失、冲突／过期、授权或来源不可用、机器额外需求及结构失败。运行时只见任务和可用材料，gold 仍仅事后评分；测必要缺口漏报、不必要澄清、澄清能否改变可执行回复，以及包含检测调用在内的总成本。先比较单次本地判断、在现有范围内补取和向用户澄清的适用条件，再决定生产检索／性能顺序。本批只提出这一步研究范围，尚未实现缺口识别或澄清。

这些是六个合成任务的三种候选变体，39 事实不是 39 个独立真实任务。候选和语义排序沿用上轮，固定四条的选择是在本批结果后提出，需在新任务上验证。没有测最终生成回复、真人效用、部署后端费用、稳定延迟或峰值内存；全池离线支持映射也不能代表在线只看前缀的停止算法。
