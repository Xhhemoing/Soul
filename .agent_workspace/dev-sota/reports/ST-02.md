## 3. 两个身份:为什么 `root_id` 被拆成了两个字段

ST02_IMPLEMENTER §3 要求 `plan_json` 含 `root_id`,§5 又要求同一棵树扫两次的 plan hash
相同。两条同时成立,`root_id` 就必须是**从路径派生的稳定值**,不能是 `Uuid::now_v7()`。
一开始就是这么写的:SHA-256 前 16 字节做成 UUID。它在真库上撞了两堵墙。

1. **冻结 schema 不收。** `audit.schema.json` 的 `subject_refs` 是
   `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`,版本位必须是 7。
   派生值的版本位是摘要的一部分。把版本位强改成 7 能过,但那是拿一个「时间戳位是哈希」
   的东西冒充 UUIDv7。
2. **更要紧的一条**:哪怕过得了 schema,一个由路径派生的 128 位值进了审计链,就是一个
   **路径验证器**——拿到链的人可以逐个猜路径去比对。派工单第一条红线就是「审计无路径/
   文件名」,单向摘要不是路径,但它是对路径的承诺,一样不该进链。

所以拆成两个,各归其位:

| 名字 | 是什么 | 去哪 |
|---|---|---|
| `ScanReport::scan_id()` | 真的 `Uuid::now_v7()`,每次遍历新铸一个 | **审计链**(`subject_refs`)。它命名的是这次扫描,不是那个目录,链里因此没有任何路径信息 |
| `ScanReport::root_fingerprint()` | 规范化目录路径的 SHA-256 十六进制 | **计划 JSON 的 `root` 字段**。它保证同一目录两次扫描的 plan hash 相同,也保证一次批准只对一个目录有效 |

计划 JSON 本身从不落库、从不进审计;用户看的预览里本来就是他自己的相对路径,一个摘要
在那里比已经显示的内容更弱。`the_audit_chain_carries_no_file_name` 里加了一条正面断言:
序列化后的整条链**不含** `root_fingerprint` 的字面值。

其余字段与 §3 一致:`entry_count`、按动作的三个计数、`entries` 逐条 (source_rel, action,
target_rel)、显式排序、路径按组件用 `/` 连接(不依赖平台分隔符,不用 `{:?}`)。

## 4. 授权判定与拒绝矩阵

`AuthorizedRoots::authorize` 的顺序就是安全属性,写在模块头注释里:

1. roots 在 `canonicalized` 里一次性 canonicalize、验目录、去重(空表合法,授权不了任何路径);
2. 空 roots → 直接拒;
3. 请求目标 `fs::canonicalize`,**失败即拒**(证明不了在根内就不算在根内);
4. `Path::starts_with`(组件级)对任一 root 命中即过——字符串前缀会让授权 `/data/a` 放过 `/data/ab`;
5. 遍历用 `WalkDir::new(base).follow_links(false).min_depth(1)`;entry 是 symlink 就
   canonicalize 其目标,不在被扫目录内(含解析不了的悬空链)→ `skipped_escaping_links += 1`,
   不进 entries、不进计划。

拒绝一律返回同一个 `PathNotAuthorized { roots }`,不带请求路径:「在根外」「不存在」
「读不了」三者的差别正是攻击者用来测绘磁盘的差别。`refusal_names_no_requested_path`
对 `Display` 和 `Debug` 两种形态都断言了「含授权根、不含 B 的路径 / 文件名 / 正文」。

10 条拒绝用例逐条覆盖:空 roots、绝对路径 B、`A/../B`、A 内 symlink→B、父目录、
同前缀兄弟 `/data/a` vs `/data/ab`、大小写与 NFD 变体、拒绝消息、B 树前后快照一致、
以及对照用例「授权请求仍然通过」。每条都数了请求数 == 拒绝数,没有部分成功。

**头一轮有三条变异活了下来,是真的测试漏洞,已经补上**:

1. *排序*:原先只断言「两次 hash 相同」,把 `sort()` 换成 `reverse()` 照样相同——同一进程
   里目录顺序是稳定的,这条断言测的是「可复现」而不是「已排序」。补了对
   `ScanEntry` 与 `PlanEntry` 的直接有序性断言。
2. *hash 覆盖面*:原先只从 JSON 副本上改字段再比 hash,这证明不了真 target 进过 hash。
   补了「JSON 逐条 == 预览逐条」的忠实编码断言(source / action / target 三个字段都比)。
3. *空 roots*:删掉 `is_empty` 早退后测试仍绿——因为空表上 `find` 本来就返回 `None`,
   两条路都拒。改用「空 roots 直接返回 Ok」的变异确认了测试确实敏感。

## 8. 手动清单(Linux CI 覆盖不到的)

1. **Windows 上的 symlink / junction 逃逸**。Linux 上
   `a_symlink_escaping_the_root_is_refused` 是真建链真扫的;Windows 建链要提权,该测试
   在 `cfg(not(unix))` 下是一条带 `#[ignore]` 与理由的空壳。**需要在 Windows 上手工验**:
   `mklink /J A\outside B` 之后,扫 `A\outside` 整体拒、扫 `A` 时 `skipped_escaping_links == 1`
   且 B 的内容零出现。junction 与 symlink 在 `fs::canonicalize` 下的行为不同,这条不能靠
   Linux 结果外推。
2. **大小写不敏感的文件系统**。`a_case_or_nfd_variant_outside_the_root_is_refused` 里
   「授权根的大写拼法被拒」那一段带 `cfg(target_os = "linux")`。在 Windows / macOS 上同一个
   请求会 canonicalize 到同一个目录并**被放行**——那是对的,它就是同一个目录——但这个决定
   应该有人在真机上看一眼,确认没有别的后果。
3. **NFD 目录名**。macOS 会在文件系统层规范化,Linux 不会。测试里的两种拼法在 Linux 上是
   两个不同目录,在 macOS 上可能是一个。v0.1 不发 macOS,记在这里备查。
