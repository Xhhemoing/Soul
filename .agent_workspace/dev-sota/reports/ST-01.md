## 5. 两处取舍(需要父代理知情)

### 5.1 `LeakageChecker::with_min_ngram(4)` 对 ASCII 语料是系统性假阳性

派工单第四节要求 `the_audit_chain_serialises_clean` 用 `with_min_ngram(4)`,语料
= 全部正文 + 姓名 + 草稿文本。**照字面实现会红,而且红得毫无信息量。**

实测出来的命中(七条,全部来自 `fixtures/injection/paste_injection.txt` 的英文行):

```text
injection-2/12  matched "prev"     ← 命中审计字段名 prev_hash
injection-3     matched "ctio"     ← 命中 action / injection.blocked
injection-5     matched "capa"     ← 命中 capability_token_id
injection-9     matched "llow"     ← 命中 decision 值 allowed
injection-6/7   matched "e\":\"" / "\":{\""  ← 命中 JSON 结构本身
summary         matched "2026"     ← 命中 64 位十六进制摘要里的四位数字
```

原因是阈值与字母表不匹配。`leakage.rs` 自己的模块文档说得很清楚:
`DEFAULT_MIN_NGRAM = 8` 是 PRODUCT_LOCK 的 `≥8` 规则,`with_min_ngram` 存在是为了
兜住**短于阈值的中文短句**(fixture 里的边界样例正是 5 scalar 的「好的没问题」)。
四个 scalar 的中文是一个词组;四个 scalar 的英文是 `prev_hash` 的前四个字母。把英文
行压到 4,断言的内容就不再是「没有正文泄漏」,而是「审计链里不许出现 action 这个词」。

处置(两条,都写在测试文件的文档注释里):

1. **只查值,不查字段名。** 新增 `audit_values()`:把链序列化成 `Value` 后递归收集
   叶子值、逐行 join,字段名不进候选串。这一步在语义上不损失任何东西——泄漏只能藏在
   值里,字段名是 `additionalProperties: false` 钉死的闭集,`FORBIDDEN_FIELDS` 另有
   递归检查兜底。它解决的是 `capability` 这个英文单词在注入行和审计字段名里各出现
   一次的撞车。
2. **按字母表分流阈值。** `ChainCorpus` 把语料拆成两个 checker:不含 ASCII
   alphanumeric 的(中文正文、姓名、模板草稿)走 `min_ngram(4)`,含 ASCII 的(英文注入行、
   带日期数字的摘要)走默认 `≥8`。两个 checker 都对同一候选串断言,所以**每一行语料都被查了**,
   区别只是多长的连续片段才算泄漏。中文永远不会和纯 ASCII 的审计链撞车,所以紧阈值
   在它该管的地方一分没松。

牙齿还在,并且是可证的:测试里加了三个对照,一个断言抽出来的值确实是链(含
`draft.create` 与 `injection.blocked` 的 serde 拼写,拼写从 serde 现取而不是手抄,
`rename` 改了会红),另两个把「真泄漏了一条正文 / 一行注入」拼进候选串,断言同一个语料
**仍然报得出来**。没有这三个对照,一个返回空串的 `audit_values` 也能过。

如果父代理认为必须逐字照搬 `with_min_ngram(4)` 于全部语料,那需要改的是
`soul-testkit`(例如让 checker 跳过 JSON 键名、或给语料标注字母表)——那是共享文件,
按红线 10 属于越界,我停在这里上报。
