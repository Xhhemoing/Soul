# C2R2：`(size, extension)` 重复分组 vs 全量内容哈希金标准

## 结论

本轮没有得到“零读分组 precision ≥ 0.90，因此永远不必读正文”的证据。

- 在最接近当前 fileplan 扫描语义的源码目录样本中，`(size, extension)` 给出 2 个候选对，
  两个都是误报；该样本没有真实重复对，所以 recall 不可定义。
- 在故意把本机研究产物摊平成一个目录的压力样本中，42 个候选对里 26 个内容相同：
  pairwise precision = `26/42 = 0.619`，recall = `26/26 = 1.000`。
- `MIN` 不能从这两个样本冻结。压力样本把 `MIN` 提到 512 B 后 precision 恰好变成 1，
  但只找回全部真实重复对的 `5/26`；源码样本在同一阈值下仍是 `0/2`。阈值只是选择
  哪些错误恰好被删掉，尚未显示可迁移性。
- 本机样本没有“相同内容、不同扩展名”的自然样例；构造的反例确认这会成为必然漏报。

因此 S2 Tier 0 可以保留为**可复算的候选生成器**，但 UI 只能说“大小和扩展名相同，
可能重复”，不能说“内容相同”，也不能触发移动或删除。若用户明确要求确认精确重复，
全量哈希仍是有独立同意、当次计算、不持久化的可测选项；它不是 v0.1 默认路径。

## 1. 预注册口径

### 1.1 被测算法 S2-0

- **输入**：同一授权根最外层的普通文件；只用父目录、非零 `size_bytes`、文件名最后一个
  非空扩展名。扩展名转小写；`.gitignore`、`Makefile`、`notes.` 的扩展名均为 `None`。
- **输出**：键 `(parent, size_bytes, extension)` 下成员数至少为 2 的候选组。
- **判定单位**：组内所有无序文件对。若三件文件同键，就产生 3 个候选对，而不是含糊地
  把整个组算“一次命中”。这会如实惩罚一个大组里混入多个不同内容的情况。
- **可数性**：候选组数、候选文件数、候选对数、`TP/FP/FN` 都是整数；没有置信分。
- **读取边界**：产品候选只读目录元数据和名称，不打开文件。

本实验不加入副本文件名模式，否则无法单独回答“`size+ext` 相对哈希金标准如何”。名字
模式应另做消融，并继续排除 `v2`、`final`、`最终版` 等人工版本名。

### 1.2 金标准 S2-H

- 对所有非空普通文件按 `(parent, size_bytes)` 先分桶；只有同大小桶可能产生精确重复，
  因而只对桶内至少两件的文件读取全量并计算 SHA-256。
- 金标准键是 `(parent, size_bytes, sha256)`；同键且成员至少为 2 才是精确重复组。
- 同哈希组在实验中再作逐字节相等检查。SHA-256 是索引，不把“理论上不可能碰撞”偷写成
  证明。
- 符号链接跳过；0 字节文件按 S2 约束排除，否则所有空文件都会制造无价值的真阳性。
- 文件在读取前后若 `(device, inode, size, mtime_ns)` 改变，整次运行应作废。本轮没有
  发生该情况。

定义：

```text
TP = 候选对中，金标准内容相同的对数
FP = 候选对中，金标准内容不同的对数
FN = 金标准内容相同、但扩展名不同或被 MIN 排除的对数
precision = TP / (TP + FP)
recall    = TP / (TP + FN)
```

没有候选对时 precision 记 `N/A`，没有金标准重复对时 recall 记 `N/A`，绝不把空分母写成
1。`MIN` 曲线的 recall 分母始终是所有非空文件中的 26 个金标准对；若随 `MIN` 一起删掉
gold 分母，会虚造“precision、recall 都是 1”的结论。

## 2. 离线执行

实验使用 Python 3 标准库，一次性运行，不写产品 crate、不安装依赖、没有网络调用。排除
任何路径分量为 `.git`、`target`、`node_modules`、`.next`、`dist`、`build` 或
`__pycache__` 的生成/依赖目录。

### 2.1 源码树：按父目录分别模拟授权根

范围是 `/workspace`，另排除顶层 `.agent_workspace`、`target`、`node_modules`。递归枚举
只是为了取得许多独立目录；候选和金标准都**不跨父目录配对**。

```text
非空普通文件       431
总字节数           3,667,145
实际全量哈希文件   4
实际哈希字节       4,674
金标准重复组       0
金标准重复对       0

候选组             2
候选文件           4
候选对             2
TP / FP / FN        0 / 2 / 0
precision           0/2 = 0
recall              N/A（没有 gold 对）
```

两个误报都来自同一目录、相同大小和 `.json` 扩展名，但内容不同：

```text
1098 B  docs/schemas/contact.schema.json
        docs/schemas/soul-import-v1.schema.json

1239 B  docs/schemas/inference.schema.json
        docs/schemas/memory.schema.json
```

这不能估计真实个人目录的 precision，但已经证伪“相同大小和扩展名蕴含内容相同”。

### 2.2 研究产物：摊平压力样本

范围是 `/workspace/.agent_workspace`，使用同一排除表。这里故意忽略父目录，把 276 件文件
视作一个扁平根，以制造足够多的重复和同尺寸碰撞。它模拟“许多实验副本被放进一个目录”
的压力条件，不模拟一般用户分布。

```text
非空普通文件       276
总字节数           2,325,507
实际全量哈希文件   36
金标准重复组       11
金标准重复文件     28
金标准重复对       26

候选组             13
候选文件           36
候选对             42
TP / FP / FN        26 / 16 / 0
precision           26/42 = 0.619
recall              26/26 = 1.000
```

主要误报不是随机哈希问题，而是结构化同尺寸文件。例如三份 157 B 的 `Cargo.lock` 产生
3 个候选对却 0 个真阳性；三份 159 B 的 `Cargo.lock` 同样产生 3 个误报；两份 154 B
的 `Cargo.lock` 再产生 1 个误报。相反，多个轮次复制的 `.rs`、`.toml` 和 `.gitignore`
给出真阳性。也就是说，此处的好坏高度依赖“复制实验目录”这一采样机制。

本样本的 26 个 gold 对恰好都具有相同扩展名，所以观察到 recall 1.000；这不是算法保证。

### 2.3 `MIN` 曲线

压力样本：

| `MIN` | 候选对 | TP | FP | 对全部 gold 的 recall | precision |
|---:|---:|---:|---:|---:|---:|
| 1 B | 42 | 26 | 16 | 26/26 | 26/42 |
| 512 B | 5 | 5 | 0 | 5/26 | 5/5 |
| 1 KiB | 5 | 5 | 0 | 5/26 | 5/5 |
| 4 KiB | 4 | 4 | 0 | 4/26 | 4/4 |
| 16 KiB | 1 | 1 | 0 | 1/26 | 1/1 |
| 64 KiB | 0 | 0 | 0 | 0/26 | N/A |

源码目录样本在 `MIN = 1 B / 512 B / 1 KiB` 都保持 `TP=0, FP=2`；到 4 KiB 才因两个候选
都被排除而变成无输出。故不能根据压力样本把 512 B 冻结成通用门槛。若目标只是避免空文件，
当前证据只支持 `MIN=1 B`；更高门槛需在目标目录分布上重新证伪。

### 2.4 合成 sanity check

临时目录放入 4 件非空、均为 4 B 的文件：

```text
report.txt       = ABCD
report (1).txt   = ABCD
same.bin         = ABCD
collision.txt    = WXYZ
```

另放一个 0 B 文件验证排除。`size+ext` 对三个 `.txt` 产生 3 个候选对；gold 对三份 `ABCD`
产生 3 个真重复对。交集只有两个 `.txt` 之间的 1 对，因此：

```text
TP / FP / FN = 1 / 2 / 2
precision = 1/3
recall    = 1/3
```

两个 FN 都来自相同内容跨 `.txt`/`.bin`，两个 FP 都来自同尺寸同扩展的不同正文。该检查
确认评测器同时能发现两种失败，不把当前自然样本的“无跨扩展重复”误当成实现定理。

## 3. 产品锁与实验边界

### S2-0：零读候选

- **输入**：授权根内名称、类型、大小；不读正文。
- **输出**：只附注候选组及整数依据 `same_size=true`、`same_extension=true`。
- **锁冲突**：不新增正文读取或网络，但文件名仍不得写入无遗忘路径的审计；v0.1 仍只预览。
- **证伪线**：在按真实授权根分别统计、预先冻结的独立样本上，pairwise precision 的
  预注册下界若达不到 0.90，就不得升级为“内容相同”。本轮观察值没有过线。

### S2-H：全量哈希确认

- **输入**：用户另行同意的授权根内文件全量字节；先按大小缩小读取集合。
- **输出**：当次计划内的精确重复组、读文件数和读字节数；UI 不显示哈希值。
- **可数性**：每个组的成员数、逐文件实读字节、总 open 数、总读字节和中途变化数。
- **锁冲突**：全量读取突破 v0.1 零正文契约；哈希是内容派生数据，不能持久化、进审计或
  出网。确认重复也不授权删除。计划获批后执行前仍须在同一文件身份上复核，防 TOCTOU。
- **证伪线**：任何未同意读取、运行时下载、哈希落库、跨授权根配对、0 字节成组、文件
  变化后仍沿用结果，或把“内容相同”直接变成 delete，均淘汰该实现。

## 4. 下一次能决定产品档位的实验

1. 用户明确选择若干真实候选根后，**逐根**运行一次性 evaluator；不跨用户、不跨根摊平。
2. 在看 hash 结果前冻结 `MIN` 候选、扩展名口径和副本名字表。分别报告
   `size-only`、`size+ext`、`size+ext+copy-name`，不能只展示最好一档。
3. 同时报组数与 pairwise `TP/FP/FN`；按目录聚类重采样，避免把同一大组的相关文件对
   当成许多独立证据。
4. 报告“有至少一个候选的根占比”。即使 precision 高，若绝大多数根从不输出，S2 也
   可能不值得进入默认预览。
5. 若零读档在独立根上达到预注册的 precision 门，只能证明“可能重复”候选够纯；若要说
   “内容相同”，仍须 S2-H 或逐字节比较。precision 门不能改变词义。

当前裁决：**保留 S2-0 作为弱提示研究候选；拒绝“它已足以替代内容确认”的结论；S2-H
继续是 opt-in 金标准，不进入默认产品路径。**
