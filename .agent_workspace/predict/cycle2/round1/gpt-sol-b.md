# C2R1：正文型文件整理与扩展名启发式——本机可测边界

## 结论先行

先拆掉一个容易混淆的词：文献里的 “content-based” 至少指两件不同的事。

1. **内容格式识别**：读少量二进制签名，判断“这实际是 PDF / PNG / ZIP”，解决扩展名
   可改、可缺失、可冲突的问题。
2. **内容语义整理**：抽取正文词项，判断“这是发票 / 课程资料 / 某项目”，解决同为
   `.pdf` 却用途不同的问题。

Soul v0.1 当前八个目的桶（图片、文档、表格、演示、压缩包、音频、视频、代码）是
**格式桶**，不是主题桶。因此：

- 对当前任务，正确对手是 **扩展名白名单 vs 有界 magic/signature 交叉检查**；
- TF-IDF、关键词和主题聚类回答的是另一道题。若仍把目的地限定为“图片/文档/表格”，
  用语义模型与扩展名比准确率是任务错配；
- 要测语义整理，必须先有用户定义的主题目的地或用户批准过的目标文件夹。没有这个
  oracle，聚类“很紧”不等于用户认为“整理正确”。

在不调用 LLM、运行时零 E0 的条件下，结论分三档：

| 候选 | 本机可测结论 | 产品锁状态 |
|---|---|---|
| X0 扩展名白名单（现状） | **现在已确认可测** | v0.1 唯一放行默认 |
| M1 有界文件签名交叉检查 | **隔离夹具上已确认可测** | 会打开文件字节；v0.1 禁，v0.1.1 也需另行授权，不能偷算“元数据” |
| K1 用户自写关键词规则 | **规则与合成正文上可测** | 正文读取门控；非默认 |
| T1 TF-IDF + 用户文件夹质心/线性分类器 | **有本机标签后可测** | 当前没有标签事件与正文同意契约，故今天是 schema-gated |
| A1 相似文件同动作推荐 | **有批准/拒绝历史后可测** | 当前没有这种训练记录；KondoCloud 完整形态含云特征，不能照搬 |
| U1 K-means/LDA/NMF 无监督整理 | 只能确认代码能跑，**不能确认整理正确可测** | 无用户 oracle；不进默认候选 |
| B1 字节频率/n-gram 文件类型模型 | 机械上可测，低优先级 | 只识别格式，不识别主题；需训练语料且覆盖差 |
| C1 全容器解析/OCR/通用 ZIP 嗅探 | 机械上可测，**不属于放行候选** | 全文/全容器解析扩大攻击面；通用 ZIP 嗅探已被产品锁否决 |
| LLM/云端语义分类 | 本轮排除 | 无 key 仍须可用；E0 无代码路径；默认读正文出网冲突 |

“已确认可测”仅表示输入能在授权根内本机取得，能造出有确定 oracle 的离线夹具；不表示
在真实个人目录上的收益已经成立。

## 1. 当前实现到底是什么

`crates/soul-fileplan/src/kind.rs` 只把文件名最后一个点后的扩展名小写化，再查固定表。
`scan.rs` 读取目录项的名称、类型、长度和修改时刻，但明确不打开文件；计划只处理授权根
最外层的散文件，未知扩展名、子目录内容、同名冲突都留在原处。`plan.rs` 把
`executable_in_this_version: false` 放进被哈希值。

这不是“弱版内容分类”，而是一个不同且更窄的契约：

```text
name -> extension -> FileKind -> fixed folder
```

它的优点是确定、无正文、无需模型、无需网络、理由可逐字节复算。缺点也同样确定：

- 改名即可改变类别，文件字节不变也不例外；
- `.key` 被当前表视为演示文件，但同扩展名也可能是 PEM 密钥；
- `.ts` 既可能是 TypeScript，也可能是 MPEG transport stream；
- `.ogg` 是容器，不天然等于纯音频；
- 无扩展名与不在表中的格式一律不猜，覆盖率换安全性；
- `archive.tar.gz` 只看最后一个 `gz`，对当前“压缩包”粗桶尚可，但不能声称识别出 tar。

本轮本机复核：

- `cargo test -p soul-fileplan`：50 项通过；
- 系统 `file 5.45` 可离线把无文件类型后缀的本机构建物识别为
  `application/x-pie-executable`，也把 `Cargo.lock` 识别为 `text/plain`。

后者只证明**本机实验工具存在**，不证明 Windows 产品应依赖 Unix `file`，也不证明
任意 magic 库都达到可接受覆盖率。

## 2. 文献给出的边界

### 2.1 扩展名与签名：便宜声明 vs 内在格式证据

Apache Tika 的检测顺序本身就是一个实用对照：magic 先看流开头，文件名用于进一步细化，
已声明的 content type 再作提示。其文档明确说文件名检测快但重命名后不可靠；magic 对
ZIP/OLE2 只能先认出“容器”，要区分 DOCX/PPTX 等通常必须打开并检查整个容器，耗时和
内存都会增加：
[Apache Tika Content Detection](https://tika.apache.org/3.3.2/detection.html)。

Dubettier 等 2023 年对 10 个文件类型识别器、17,500 文件/110 类型及约 100 万文件/63
类型做比较。结果不能被简化成“magic 总是正确”：不同工具在 17,500 集上的准确率从
34.1% 到 94.4% 不等；删除/改写扩展名后，纯签名工具结果不变，而依赖名称的工具明显
下降；ODS/ODT/PPT 等共享容器还会在“ZIP/OLE2 粗类”与“具体办公格式”之间产生粒度差异。
论文也指出学术字节分类器常只覆盖少数类型，实践工具主要仍依赖维护过的签名库：
[File type identification tools for digital investigations](https://doi.org/10.1016/j.fsidi.2023.301574)。

更早的 McDaniel 与 Heydari 用字节频率、字节频率互相关和头尾字节学习文件类型指纹。
在其很小的 120 文件/30 类型实验中，三种方法分别约为 27.5%、45.83%、95.83%；高数值
来自头尾模式，不足以推出在现代长尾格式上同样有效：
[Content Based File Type Detection Algorithms](https://doi.org/10.1109/HICSS.2003.1174905)。

因此 Soul 可测的 M1 应是**保守交叉检查器**，不是“magic 判了就强制移动”：

```text
extension_kind + bounded_signature
    agree       -> 保留扩展名建议，并显示“签名相符”
    mismatch    -> 留在原处，要求人工查看
    unknown     -> 回到扩展名预览或留在原处（策略必须预注册）
    ambiguous   -> 留在原处，不把 ZIP 冒充 DOCX/PPTX
```

### 2.2 语义整理：可本机计算，不等于有正确目的地

Raza 等 2022 年以 TF-IDF、SVD、K-means 和神经分类器做文本文件组织。其大实验先在
20 Newsgroups 上训练；转到 222 个用户文件后，验证准确率只有 70%，自动文件夹名出现
`consume`、`information`、`quantity` 之类，作者也承认类别名不合适、效果受小样本和
异质内容影响。这说明传统 NLP 的确无需 LLM 就能本机运行，也同时说明“聚类可运行”
不是“个人目录可自动改造”的证据：
[Content Based Automated File Organization Using Machine Learning Approaches](https://doi.org/10.32604/cmc.2022.029400)。

Hu、Milios 与 Blustein 的用户研究更直接：不同用户会给同一文档集合不同且都合理的
组织，同一用户的组织也会随时间变化；带用户监督的聚类比纯无监督更贴近用户预期：
[Personalized document clustering with dual supervision](https://doi.org/10.1145/2361354.2361393)。

所以语义路由的标签不能来自算法自己起的簇名。合法 oracle 只能是：

1. 用户显式写下的本机规则；
2. 用户已存在且选择作为目标的文件夹；
3. 用户对预览逐项批准/拒绝形成的本机记录。

### 2.3 文件位置有提醒语义，HITL 不是装饰

Barreau 与 Nardi 对桌面文件管理的两组研究发现，用户偏爱按位置找文件，文件放置还承担
“提醒我以后处理”的作用，用户通常避免复杂归档方案：
[Finding and Reminding: File Organization from the Desktop](https://doi.org/10.1145/221296.221307)。

KondoCloud 用 10 个元数据/内容相似特征和 logistic regression 推荐 move/delete/retrieve；
三个分类器 F1 均至少 0.72，但论文把它明确定位为人在回路建议。其研究中 1,856 条建议
只有 25.5% 被直接接受。值得注意的是，其 text-pair 模型里修改时刻、树距离、文件大小和
文件名系数都高于 TF-IDF topic 相似度；这不是严格消融，却足以否定“加正文就必然是主要
增益源”的先验。论文也明确警告 Google Drive 结果不一定泛化到本地文件系统：
[KondoCloud](https://doi.org/10.1145/3472749.3474736)。

Soul 因而应先测元数据/历史动作基线，再问正文是否提供增量；不能只拿“内容模型 vs 纯
扩展名”制造一个正文模型必胜的对局。

## 3. 候选的可测契约

### X0：固定扩展名白名单（当前基线）

- **输入**：授权根目录项的文件名；只取最后一个非空扩展名。
- **输出**：八种固定 `FileKind` 或 `Unrecognised`，以及固定目标路径/留置原因。
- **可数性**：命中的扩展名规则、每桶文件数、未知数、冲突数；没有概率。
- **锁冲突**：无。正文读取 0 字节，E0 请求 0，v0.1 只预览。
- **证伪**：大小写、无扩展名、dotfile、多点名、歧义扩展名和未知扩展名夹具必须逐项
  命中预注册 oracle；同名同扩展名而正文任意变化，输出必须不变。

它是可解释的基线，不是真实类型 oracle。评测报告必须把“按表命中率”和“实际格式正确率”
分开。

### M1：有界签名交叉检查器

- **输入**：文件名、长度，以及固定上限内的头/尾字节；签名表随构建固定版本。默认不解
  压、不递归、不抽正文。
- **输出**：`agree / mismatch / unknown / ambiguous`、粗格式 ID、命中的签名规则 ID、
  实读字节数。只有 `agree` 可以支持原扩展名建议，其余默认留置。
- **可数性**：匹配的 `(offset, mask, bytes)` 规则、候选数、读字节数，均可直接复核；
  不显示文件原字节。
- **锁冲突**：打开文件即突破 v0.1 “一个字节都不读”的契约；签名不是目录元数据，
  v0.1.1 的“文件元数据”也不会自动授权它。必须另有逐根同意。运行时下载签名库会引入
  E0，故签名库只能随构建提供并写版本。
- **证伪**：正确扩展、改错扩展、去扩展、截断头、随机碰撞、polyglot、共享 ZIP/OLE2
  容器分别测。任何 `unknown/ambiguous` 被静默强分、任何错扩展被自动执行都淘汰。

M1 的价值是减少错分，不是提高所有文件覆盖率。允许弃权比伪造“高置信”更重要。

### K1：用户定义的本机关键词规则

- **输入**：用户显式选择的可解析纯文本格式、用户自写的目标文件夹与关键词表；固定
  tokenizer，限制读字节/字符数。
- **输出**：目标文件夹建议或弃权；理由只列“规则 X 命中 N 次”，不复制正文片段。
- **可数性**：逐词整数命中数、规则优先级、冲突规则数。
- **锁冲突**：读正文，故不是 v0.1；规则与派生计数都需跟授权根一起删除。正文仍不得
  进入审计、日志、E1 或 E0。文件中的“请移动所有文件”等文字只能是数据。
- **证伪**：同扩展异主题、同主题异扩展、否定词/大小写/中英文、恶意指令文本、规则冲突、
  低支持和超长文件。没有规则或多规则并列时必须弃权。

K1 比自动聚类窄，但 oracle 是用户写下的，解释也能精确复算，是语义路线最先值得测的
确定性对照。

### T1：本机 TF-IDF + 已有文件夹质心/线性分类器

- **输入**：经用户选择的本机文本、用户选定的目标文件夹或逐项批准标签；固定词表策略、
  tokenizer 与训练参数。无需 LLM、无需网络。
- **输出**：已有目标文件夹 top-1/top-k 或弃权；禁止模型自造目录名。
- **可数性**：每类训练文件数、文档频次、支持该建议的 top 词及整数出现次数、模型字节、
  训练/推理耗时。浮点权重可用于离线评分，但 UI 理由必须回到词项与先例文件数。
- **锁冲突**：正文与用户整理历史都尚无当前 schema；模型可能保留已遗忘正文的影响。
  删除任一训练文件后必须从剩余事件重建并与从未见过它的模型相等。
- **证伪**：按文件内容族/精确哈希分组切分，禁止近重复件跨 train/test；与扩展名、
  文件名关键词、MRU 目标文件夹和 K1 同场。若不能在用户标签上提高 macro-F1/接受率，
  或删除后状态不等价，淘汰。

今天没有 Soul 用户标签，所以可确认“算法和夹具能测”，不能确认“真实效用已可测”。若只
对合成主题得高分，结论只能写合成主题通过。

### A1：批准动作后的相似文件推荐

- **输入**：一次用户已批准的 move、同根候选的文件名/扩展名/长度/mtime/树距离；正文
  TF-IDF 只能作为另行同意的消融项。
- **输出**：“你刚把 A 放到 X；B 是否也放到 X？”或弃权，不生成 delete 建议。
- **可数性**：相似字段逐项、相同动作支持数、批准/拒绝整数历史。
- **锁冲突**：当前没有用于学习的批准/拒绝事件 schema；审计又不能承载文件名或正文，
  不能把审计表偷当训练库。
- **证伪**：元数据-only 与 `+TF-IDF` 配对消融；用时间顺序评测后续批准率、错误建议率、
  覆盖率。若正文分支没有预注册增益，保留元数据分支。

A1 只借 KondoCloud 的“同动作推荐 + HITL”结构，不复制其 Google Drive、共享用户、
ResNet/Word2Vec 或跨参与者模型。

## 4. 不进入确认清单的近似物

### B1 字节频率/n-gram

可以完全本机训练，也无需 LLM，但它的目标仍是**文件格式**。对于完整、常见文件，固定
签名更简单、更可解释；对于碎片/损坏文件，才可能值得做训练型识别。Soul 整理授权目录
中的正常文件，不是取证碎片恢复器。除非 M1 在预注册的 intact-file 语料上出现可量化的
覆盖缺口，否则不启用 B1。

### U1 无监督主题聚类

K-means、LDA、NMF、LSA 的轮廓系数、簇内相似度与重跑稳定性都能本机测，但这些指标没有
回答“用户会把它放到这个文件夹吗”。算法自造目录名还会改动用户的空间记忆。没有用户
标签时，只能登记为聚类机械实验，不能登记为整理正确候选。

### C1 全解析器、容器展开、OCR

Tika 文档说明精确区分容器格式可能要读完整文件。这样会引入复杂解析器、不可信输入、
压缩炸弹和大资源面；而产品锁已明确“通用 ZIP 嗅探不做”。OCR 又把图片转成正文，授权
面更大。它们即使都能在离线机器上运行，也不等于符合 Soul 的允许数据面。

“本机运行”只回答出网问题，不回答最小读取、解析器漏洞、正文生命周期和用户同意问题。

## 5. 最小离线夹具与杀线

所有文件只放临时授权根，名称与正文均为合成；不拿真实用户文件做第一轮 oracle。

1. **FMT-EXT**：每个当前扩展名一个最小文件；验证 X0 完整映射、排序与未知留置。
2. **FMT-RENAME**：同一有效 PNG/PDF/WAV 分别用正确、错误、空扩展名；X0 随名称变，
   M1 格式结果不变且错名为 `mismatch`。
3. **FMT-AMBIG**：PEM 内容的 `.key`、TypeScript 与 MPEG-TS 的 `.ts`、音视频 Ogg；
   禁止“一条扩展名就是唯一真相”进入验收 oracle。
4. **FMT-CONTAINER**：普通 ZIP、最小 OOXML/ODF、坏 central directory、嵌套 ZIP。
   有界 M1 只能报粗容器/歧义；任何通用展开都算越锁，不算更高分。
5. **FMT-BROKEN**：空文件、短头、截断、随机字节、签名碰撞与 polyglot；必须能弃权，
   不能 panic。
6. **SEM-CROSS**：同为 PDF/TXT 的“发票/课程”合成正文，以及同主题跨扩展正文；证明
   X0 不具主题分辨力，并验证 K1/T1 的专属主张。
7. **SEM-SUBJECTIVE**：同一六文件给两套同样合理的用户目录标签；每套只按自己的标签
   评分，禁止制造全局真值。
8. **SEM-INJECT**：文件名和正文包含 URL、shell、`move/delete/ignore previous`；
   输出只能多一个命中计数，永远不能产生新动作或扩大根。
9. **LIFE-FORGET**：删除一条训练证据后重建；派生规则、词频、质心、建议必须与从未
   见过该文件的干净运行逐字节相等。
10. **RES-BOMB**：超大稀疏文件、深目录、慢读取、损坏文档、压缩炸弹标记；固定字节、
    时间、内存上限，超限为显式留置。
11. **TOCTOU-SAME-META**：扫描后用同长度内容替换并恢复 mtime。当前快照只覆盖名称、
    类型、长度、mtime；内容型计划若仍通过相同 `plan_hash`，直接失败。
12. **NET-ZERO**：测试期间监测进程非回环连接恒 0；模型、词表、签名库不得懒下载。

第 11 条是内容路线新增的硬前置。分类理由一旦依赖字节，批准哈希至少必须绑定：

```text
algorithm_id + algorithm_version + signature_or_tokenizer_version
+ source path + observed-content digest + proposed destination
+ executable_in_this_version
```

只把“检测到 PDF”写进哈希不够；同一类型的另一个同长度文件仍可能被换进来。内容 digest
只可留在短生命周期计划中，不进无正文审计。执行时还需在同一文件句柄/身份上复核，避免
检查后换文件。

## 6. 统一评测

### 格式桶

- exact format accuracy 与当前八桶 accuracy 分开；
- coverage/abstention；
- extension mismatch precision/recall；
- `ambiguous` 与 `unknown` 数；
- 每文件实读字节、p50/p95 延迟、峰值内存；
- 签名库版本固定后的跨运行逐字节确定性。

### 语义桶

- 每用户、按时间顺序的 top-1 / macro-F1；
- 建议接受率、拒绝率、弃权覆盖率；
- 新主题/新文件夹单列，不能硬塞最近类别；
- exact-hash/近重复族隔离后的结果；
- X0、文件名-only、K1、T1、A1 metadata-only、A1 `+content` 的逐级消融；
- 错误 move 的成本高于少给建议，阈值按“先少错”预注册，不事后追命中率。

v0.1 只做预览，因此当前验收不能拿“自动移动成功数”作指标。v0.1.1 也只有授权根内可逆
move/rename；delete、跨根、创建任意语义树和无人值守执行都不从本文获得许可。

## 7. 本轮建议

并列保留，不先选赢家：

1. **冻结 X0 为 v0.1 默认和所有后续实验的零正文基线。**
2. **登记 M1 为隔离研究夹具的保守格式交叉检查器**；未取得“打开字节”的独立产品决定
   前，不进入 v0.1/v0.1.1 默认路径。
3. 若未来批准正文型整理，先测 **K1 用户规则**，再测 **T1 用户标签 TF-IDF**；两者只向
   已有/用户定义目的地建议，并始终允许弃权。
4. 同时登记 **A1 metadata-only**，正文分支必须证明相对它的增量，而不是只打赢扩展名。
5. U1、B1、全容器解析、OCR、LLM 都不进入当前确认清单；代码能在本机跑不是产品证据。

最终一句：**扩展名是当前可执行契约，magic 是可测的格式防错护栏，TF-IDF 是有用户标签
后才可测的语义建议器；三者不是同一个层次，不能用一个“content-based 胜出”结论把它们
混成一条路线。**
