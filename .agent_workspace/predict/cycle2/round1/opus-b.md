## 0. 本轮的一句话结论（先说，后证）

**「最近已批准的计划种类」这条序列，在今天的仓里根本不存在。**

不是「难取」，是三层都不存在：`check_action` 的批准结果 `ApprovedAction` **谁也没存**；
唯一留痕的审计链**不可被遗忘**（而 Cycle 1 已把「拿审计链当特征」判为造遗忘旁路，无复活条件）；
而且审计链上的动作枚举与 HITL 的动作枚举**不是同一个闭集**，从前者反推后者是有损的。

所以本轮交出的不是「哪个模型好」，是三样东西：
一是**动作轴的数据面事实与四个新缺口**（§1、§5）；
二是**闭集 token 词表，以及「预测集 ≠ 建议集」这条不对称**（§2）；
三是**九条候选规范**（§3），其中跨面组合 `x2`（硬编码 `code.exe → plan.files`）
按 Cycle 1 已冻结的否决条款（「`MFU/MRU` 之外的人群先验，无复活条件」）**在产品面直接出局**，
只剩离线研究轨一条命——这正是任务给它加「只作研究」的形式理由，本文件把它写成可执行的形状（§3.8、§6.3）。

还有一条本轮想提前钉住的元规则，它比任何一个候选都重要：

> **动作轴的诚实默认是沉默。** 支持度不够时，输出必须是弃权 token，不是「猜一个最常见的」。
> 动作轴的事件量比 app 轴少三个数量级（§1.5），所以「数据不够 ⇒ 不出建议」不是保守，是唯一站得住的默认。

所以「本次启动以来批准过哪些动作」是一个**不需要任何新持久化**就能有的整数环。

### 1.5 量纲：动作轴比 app 轴少三个数量级

app 轴：一天几百次前台切换（`ADV-flood` 甚至造到 1000 次/天）。
动作轴：一次起草、一次人事分析、一次整理预览——**一天个位数，`plan.files` 可能一生几十次**。

Cycle 1 的空虚保护是 `n < 200` 或 `a < 20` ⇒ `inconclusive`，且 `inconclusive` 按不过处理
（`cycle1/round3/opus-b.md` §0.2）。**照搬到动作轴，结果是每一条判据永远 `inconclusive`。**
按 C1 §0.5 的元规则，恒 `inconclusive` 的杀线是坏杀线，**换判据，不许放宽 200**。本轮的换法见 §4。

### 1.6 `plan_hash` 是内容派生的一次性值，不是「计划种类」

| 事实 | 坐标 |
|---|---|
| `PlanHash::of` = 计划规范 JSON 的 SHA-256 | `hitl.rs:126-133` |
| 整理计划的 JSON 里**含文件名**（`moves[].from` / `moves[].to`）与逐文件字节数 | `soul-fileplan/src/plan.rs:164-192` |
| 目录里出现一个文件，`snapshot_hash` 变，plan_hash 就变（这是 AC-19 的中间格） | `plan.rs:18-20` 模块注释 |
| 「文件名是数据」是一条独立验收 | `soul-fileplan/tests/file_names_are_data.rs` |

**后果**：任务里的「计划种类」**只能读成 `ActionKind`，绝不能读成 plan_hash**。
把 plan_hash 记进预测状态，等于把用户目录内容的指纹存进一张派生表——
既没有区分度（近乎唯一值，条件在它上面 = 条件在一个 nonce 上），又踩「文件名是数据」。
本轮为此立一条**全候选通用门**：动作历史状态里不得出现 plan_hash 字段，且改文件名不得改变状态一个字节（§4 门 D3）。

允许作为条件特征的，只有从计划里提炼出的**闭集、粗桶、非内容**的量：
`moves_count_bucket ∈ {0, 1-9, 10-99, 100+}`（分桶边界与 `AuditCounts.items` 已上链的口径同源）、
`truncated: bool`、`root_index: usize`。**不含**文件名、扩展名分布、字节数、目录路径字符串。

### 1.7 授权根：有，但它在遗忘覆盖不到的地方

| 事实 | 坐标 |
|---|---|
| `authorized_roots: Vec<PathBuf>` 持久化在配置文件里，不在加密主库里 | `soulcore/src/config.rs:41`；`commands/fileplan.rs:67-77` `from_config` |
| 会话内可枚举根，并能报出「已授权但现在打不开」的根 | `FilePlanSession::roots()`；`Session.unavailable_roots` |
| 路径解析产出 `root_index` + 相对路径，refusal 一律不泄露根外信息 | `soul-fileplan/src/authorize.rs:139-170, 250-301` |

**后果**：「建议对 Downloads 出整理预览」里的 Downloads **可以指名**，因为它是用户自己声明的常驻配置
（与同意开关同类），不是行为推断。但建议 token 里**只许带 `root_index`**，渲染时再由授权表取显示名——
与 Cycle 1 `F5-10`（token 里只有 `contact_id`，无姓名）同款纪律。路径字符串里有用户名（`C:\Users\罗伊\Downloads`），
它不该进任何计数表、不该进审计、不该进研究导出。→ 缺口 **G20**。

### 1.8 「刚离开 code.exe」这个触发器的真实形状

Cycle 1 冻结的采集常量（`cycle1/round3/opus-a.md` §2.4）直接决定了它：

- 同 app 去抖合并 `MERGE_GAP_S = 5`：**「离开」最早也要 5 秒后才可知**；
- `MIN_SESSION_S = 3`：过短段被丢弃，所以「离开 A 进入 B」里的 B 可能根本不落库；
- `SESSION_GAP_S = 1800`：≥30 分钟无事件是 `boundary`，转移链断开——**此时不存在「刚离开」**；
- 段身份在密封体里（`SealedSessionBody::FIELDS = ["app","duration_ms"]`），读它必须持钥在线。

**所以 `left(a)` 必须先被定义成一个可测的事件，而不是一句白话**：

> `left(a)` 在「app ≠ a 的一段合法会话开始」且「其**紧邻前一段**合法会话的 app == a」且
> 「两段之间未跨 `boundary`」时触发，触发时刻 = 后一段的 `started_at`（不是前一段的 `ended_at`）。

三个后果，全部要写进任何用它的候选的已知代价：
(a) **建议永远出现在用户已经进入下一个 app 之后**——如果下一个是全屏应用，这是打扰不是提示；
(b) 跨 `boundary` 的「离开」不可见，而「下班前关掉编辑器」恰恰大多跨 boundary；
(c) 触发率上限必须有（`ACT-FLOOD`），否则一天 1000 次切换就是一天 1000 张卡片。

## 2. 闭集词表（本轮冻结的输出面）

### 2.1 预测 token（predictand）

```
next_action(k)   k ∈ ActionKind::ALL          // 8 个，字符串一律取 as_str()
```
附带整数：`hits`（该格计数）、`n`（该行/桶总数）。**不输出比值、不输出概率、不输出分数。**

**词表同步纪律（源码级门）**：预测器侧不得自建动作字符串表，必须 `match` 在 `ActionKind` 上且**禁 `_ =>` 通配**。
新增第 9 个动作时，编译必须失败，直到它同时登记：可建议性（§2.2）与轴亲和（§4 门 D5）。
这是 Cycle 1 `F6-6`（新候选必须同时提交轴亲和登记）在动作轴上的形式。

### 2.2 建议 token（suggestand）：**建议集 ⊊ 预测集**

这条不对称是本轮的产品面主张，必须写死：**能预测不等于能建议。**

| `ActionKind` | 可预测 | 可建议 | 理由 |
|---|---|---|---|
| `draft.reply` | 是 | 是 | 只起草不发送（产品锁「出站消息 v0.1 只起草」） |
| `analyse.people` | 是 | 是 | 只读已存证据 |
| `scan.directory` | 是 | 是（与下一条打包） | 只读 |
| `plan.files` | 是 | 是 | 只读预览，`executable_in_this_version: false` |
| `forget.preview` | 是 | **否** | 主动提示用户「要不要看看忘掉 X 的代价」= 诱导删除。不是能力问题 |
| `forget.execute` | 是 | **否** | 不可逆 |
| `research.preview` | 是 | **否** | 研究轨是第三条轨道，不该由助手轨主动拉人进去 |
| `egress.generate` | 是 | **否** | 出网 + 花用户的钱 + 需令牌 |

**可建议性的源码级判据（比上表更强，因为它不依赖人记得维护上表）**：

```
suggestable(k)  ⇒  !k.needs_capability_token()      // 硬蕴含，单测断言
```
今天 `needs_capability_token()` 恰好挡住 `forget.execute` 与 `egress.generate`（`hitl.rs:74-79`）。
`forget.preview` 与 `research.preview` 挡不住，所以它们**必须**在白名单上显式排除，
并附一行注释说明排除理由不是「未实现」（这两条与 G19 撞车，实现补上后排除仍然成立）。

### 2.3 弃权 token（闭集；弃权计入分母、按未命中处理，继承 C1 §0.3）

```
abstain.no_history          // 本次启动尚无已批准动作（进程刚起）
abstain.thin_support        // 该行/桶支持 < 阈值
abstain.not_suggestable     // 预测出来了，但它不在 §2.2 白名单
abstain.ambiguous_root      // 建议整理但已授权根不止一个（§3.9）
abstain.root_unavailable    // 唯一根现在打不开（Session.unavailable_roots 非空）
abstain.consent_off         // 采集未同意 ⇒ 事件 0（继承 C1 F0-4）
abstain.axis_locked(axis)   // P6 锁门（继承）
abstain.budget_exhausted    // 今天的打扰额度用完（SG9，今天不存在 ⇒ 恒不可达，见 §5）
```

### 2.4 「建议不是动作」的类型级保证

Cycle 1 已否决预取/代启动（「输出类型系统里没有『动作』，只有建议卡片」）。动作轴上同样一条，且更容易违反，
因为这里的建议**恰好命名了一个真实可执行的 `ActionKind`**。三条门：

1. **建议器 crate 不得构造 `ActionRequest`**：`rg 'ActionRequest' <suggester>/src` 命中数恒 0。
2. **卡片 → 磁盘的调用链上恰好一次 `check_action(scan.directory)`**，且它发生在**用户点击之后**。
   建议阶段不得预扫描、不得预算 plan_hash——否则「未授权路径 100% 拒绝」的证明面被绕过一次。
3. **`origin` 只能是 `RequestOrigin::User`**，且它之所以是 User 是因为用户点了卡片，不是因为机器生成了卡片。
   机器自己生成的建议如果能自我授权，它在语义上等同 `ExternalContent`——`hitl.rs:461-463` 那条闸门的整个意义。

**第 2 条有一个不显然的后果，本轮认为它是决定性的**：既然建议阶段不许碰磁盘，
卡片上就**说不出**「你的 Downloads 里散着 37 个文件」这类数字。
而 Cycle 1 的可数性要求是：每个上屏结论都要有一句「N 次里有 M 次」的可手数解释。
于是动作轴上唯一合法的可数句，只能来自**用户自己的历史计数**：

> 「你最近 5 次看完整理预览之后，有 3 次接着起草了回复。」

**没有历史 ⇒ 没有可数句 ⇒ 不许上屏。** 这一条自动杀死一切硬编码规则的渲染面（§3.8 用它作 `x2` 的处决书）。

## 3. 候选规范

统一格式：`algorithm_id` · 状态 · 输入 · 输出 · 状态量 · 可数句 · 锁冲突 · 杀线（整数） · 夹具 · 阻塞。
🚫 = 今天不可执行。**并列，不选赢家**（CONSTRAINTS「不要强行选一个赢家」）。

### 3.1 `n0.action_marginal.v1` — 动作边际频率（COMPARATOR）

- **输入**：本次启动以来的已批准动作序列（字母表 5，§1.2）。**输出**：`next_action` ×3 + 计数。
- **状态量**：`O(8)` 个 `u32`。**可数句**：「你今天用得最多的是整理预览，8 次里 5 次。」
- **锁冲突**：无。**阻塞**：无。**状态**：`COMPARATOR + TESTABLE-NOW`。
- **杀线**：`FN0-1`（主）动作轴上任一候选 `laddered` 下 top-1 必须 > `n0`，否则出局；`n0` 自身不可被证伪。
  `FN0-2`（门）`ACT-DENIED`：**被拒绝的请求不得计入**（`HitlDenial` 不是批准）。混入即全表数字作废。
  `FN0-3`（门）`ACT-RESCAN`：同一目录连扫三次，plan_hash 三次不同，`n0` 的计数必须 `plan.files += 3` 且状态里无 hash。
- **已知缺陷**：它几乎必赢，因为动作分布极度偏斜（一个装了 E1 的用户几乎只有 `draft.reply` + `egress.generate`）。
  **它赢只说明动作轴没有可学的东西**——这恰恰是本轮预期的最可能结局，不是失败。

### 3.2 `n1.action_mru.v1` — 重复上一个动作（COMPARATOR，第二地板）

- **状态量**：**1 个 `ActionKind`**。**阻塞**：无。**状态**：`COMPARATOR + TESTABLE-NOW`。
- **为什么它可能很强**：`scan.directory` 与 `plan.files` 在 `preview()` 里是**背靠背两次 `check_action`**
  （`preview.rs:96` 然后 `:103`）。也就是说序列里天然含大量 `scan.directory → plan.files`，
  而重扫一次目录会立刻再产生一对。任何「学到了」的转移，很可能只是学到了这个实现细节。
- **杀线**：`FN1-1`（红）`ACT-SEQ`：若 `n1` 在合成序列上 top-1 > 0 而合成器**没有**造连续同动作，说明夹具或规范化管道错。
  `FN1-2`（门，**本轮最重要的一条**）：**`scan.directory` 与 `plan.files` 的这一对必须在规范化阶段合并成一个
  `plan.files` 事件**，否则动作轴的一半信号是 `preview()` 的函数调用顺序。合并规则要先写死再实现。
  `FN1-3`（主）：合并之后 `n1` 仍赢 `n0` ≥3 点 ⇒ 保留为地板；否则退为纯探针。
- **已知缺陷**：`ACT-RESTART` 上恒弃权。

### 3.3 `n2.pending_state_rule.v1` — 待决状态确定性规则（COMPARATOR，**本轮认为它是真对手**）

- **输入**：会话的**当前待决状态**，只读，非历史：有没有一个已展示未确认的整理预览；
  有没有一个 `prepared` 但未生成的起草（`draft.rs` 的准备/生成两段）；有没有已展示未执行的遗忘影响预览
  （`Session` 里那个「最后一次遗忘影响」槽，`session.rs:384-389`）。
- **输出**：`next_action` ×1（规则表，无计数）。**状态量**：0（读现成字段）。
- **状态**：`COMPARATOR + TESTABLE-NOW`。**阻塞**：无。
- **理由**：工具类软件里「下一个动作」大部分由**未完成的事**决定，不由历史偏好决定。
  展示了预览 ⇒ 下一步是确认或丢弃；准备了请求 ⇒ 下一步是生成。这条零状态规则很可能吃掉全部可预测量。
- **杀线**：`FN2-1`（主，**动作轴的存废线**）：`a1`/`a3`/`x1` 中任一条若不能在**同一机会集**上赢 `n2` ≥5 点，
  **整条动作轴的学习类候选全部出局**，v0.2 只留 `n2` 这条规则表。
  `FN2-2`（门）：`n2` 的规则表必须 ≤ 6 行且逐行可用一句话陈述；超了它就不是「零状态规则」而是另一个模型。
- **这一条为什么必须先立**：没有 `n2`，`a1` 打赢 `n0` 就会被当成「学到了用户习惯」，
  而真相可能只是「学到了软件的流程图」。**对照缺席 = 杀线是空话**（C1 §3 纪律）。

### 3.4 `a1.action_markov1.v1` — 一阶动作转移

- **输入**：进程内已批准动作序列（规范化后，见 `FN1-2`）。**输出**：`next_action` ×3 + 行计数/行总。
- **状态量**：`trans[8][8]`，`u32` 满打满算 256 字节。**没有驱逐**（闭集 ⇒ 无重击者问题，
  这是动作轴相对 app 轴的唯一便宜之处：Cycle 1 那些 `evictions == 0` 前置断言在这里**由构造成立**）。
- **可数句**：「你最近 5 次看完整理预览之后，有 3 次接着起草了回复。」
- **锁冲突**：无轴亲和（§4 门 D5 登记为「无」）。**阻塞**：G17（跨启动）/ 无（进程内）。
- **状态**：进程内版 `TESTABLE-NOW`；跨启动版 `TESTABLE-AFTER-GAP`（G17）。
- **杀线**：
  `FA1-1`（主）赢 `n0` ≥10 点，且赢 `n2` ≥5 点（`FN2-1`）。
  `FA1-2`（门）不变式 F：`replay(E \ {e}) == decrement(replay(E), e)` 逐格相等。**闭集无驱逐 ⇒ 这条应当平凡通过；
  若不通过，是规范化管道（`FN1-2` 的合并）有状态残留，先修工具。**
  `FA1-3`（门）`ACT-RENAME`：目录内文件全部改名后重跑，状态表逐字节相同（§1.6）。
  `FA1-4`（门）`ACT-RESTART`：重启后立即 `abstain.no_history`，**不许从配置或审计续命**。
  `FA1-5`（红）`ACT-SEQ` 已知转移矩阵：与贝叶斯上界差 ≤5 点。
  `FA1-6`（门）确定性 1000 次，并列按 `ActionKind` 的 `as_str()` 字典序升序。
- **已知缺陷**：字母表 5、每天个位数事件 ⇒ 一行 25 格的表要攒很久才有支持；进程内版**大概率终生弃权**。
  这不是可以靠调 `MIN_ROW_SUPPORT` 修的——调低它只是把噪声当信号。

### 3.5 `a2.action_prefix2.v1` — 二阶动作前缀（NAMED-ALTERNATE，不点名不启动）

- 与 `a1` 同形，`MAX_ORDER = 2`，阶梯 2→1→0。状态量 `8×8×8 = 512` 格。
- **杀线**：`FA2-1`（主）赢 `a1` ≥3 点**且** `order_used == 2` 的查询占比 ≥5%（沿用 C1 `F2-6c` 死重线）。
- **本轮的判断**：`a1` 都攒不够支持，`a2` 只会更空。**登记，但预期它永久留在备选位。**
  写出来的唯一理由是防止它日后作为「新想法」重新混进来（同 C1 对 `APPM-lite` 的处置）。

### 3.6 `a3.plan_shape_conditioned.v1` — 条件于计划的**粗形状**（不是 hash）

- **输入**：`a1` 的上下文 + 上一次已批准计划的闭集粗特征：
  `moves_count_bucket ∈ {0, 1-9, 10-99, 100+}`、`truncated: bool`。
- **动机（唯一一条有先验道理的）**：`moves == 0` 的整理预览（没什么可整理）之后，用户的下一步
  与 `moves == 87` 之后**应当**不同。这是「计划种类」这四个字在本仓里唯一站得住的读法。
- **状态量**：`trans[8][8] × 8`（4 桶 × 2 布尔）= `a1` 的 8 倍。
- **锁冲突**：`moves_count` 是目录内容的计数。它**已经**在审计链上了（`preview.rs:69-72` 的 `AuditCounts.items`），
  所以分桶后进内存计数不是新采集面；但**桶边界必须与审计那处同源**（单点常量，沿 T4D 纪律与 C1 `Fd-1`）。
- **杀线**：
  `FA3-1`（门，源码级）分桶常量表单源，禁第二处字面量。
  `FA3-2`（主）`ACT-PLANSHAPE`（造出 `moves==0` 与 `moves>>0` 后继不同的序列）上赢 `a1` ≥3 点。
  `FA3-3`（主）状态条目 ≤ 8× `a1`，且 `REAL-*` 上低支持格占比 < 50%（沿 C1 `Fd-4`）。
  `FA3-4`（红）`moves_count` 恒定的夹具上 `a3 ≈ a1`（差 ≤1 点），否则分桶自己制造了噪声。
  `FA3-5`（门）状态里**不得**出现 plan_hash、文件名、扩展名分布、字节数（`rg` + 序列化快照双查）。
- **状态**：`TESTABLE-NOW`（进程内）。

### 3.7 `a4.refusal_conditioned.v1` — 条件于上一次拒绝（NAMED-ALTERNATE）

- **输入**：上一次 `HitlDenial` 的 `ReasonCode`（21 值闭集，`soul-policy/src/audit.rs:62-114`）。
- **动机**：`PLAN_HASH_MISMATCH` 之后最可能的下一动作是**重来同一个动作**（目录变了 ⇒ 重扫）。
- **杀线**：`FA4-1`（主）必须赢 `n1`（MRU 已经免费预测「重来一次」）≥3 点，否则它是零收益的第二实现。
  `FA4-2`（门）拒绝事件本身**不得**进 `n0/a1/a3` 的计数（`FN0-2`），`a4` 只把它当**上下文**读，不当样本。
- **本轮判断**：`FA4-1` 很可能打不过。登记为备选。

### 3.8 `x2.exe_to_action_prior.v0` — 硬编码「离开 code.exe ⇒ 建议整理 Downloads」（**产品面 REJECTED；仅研究轨**）

这是任务点名的那条规则。本轮的处置是：**它在产品面出局，出局理由有三条，每条独立成立。**

| # | 出局理由 | 依据 |
|---|---|---|
| 1 | 它是**人群先验**：`code.exe` 的语义、「写代码的人的 Downloads 很乱」都不是这台机器的计数得出的 | C1R3 opus-b §5：「`MFU/MRU` 之外的人群先验 — 无人群数据面 — **复活条件：无**」 |
| 2 | 它**没有可数句**：硬编码规则的解释只能是「因为我们觉得程序员该整理了」。而 §2.4 已证明动作轴的可数句只能来自用户自己的历史 | C1 可数性要求 + `CONSTRAINTS.md`「预测输出必须可向用户解释、可纠正」 |
| 3 | 「`code.exe` 是编辑器」需要一张 **exe → 软件类别**的映射表。那张表是第二个人群先验，而且它把「这台机器上装了哪类软件」编码进了产品 | 同 1；另见 C1 「读窗口标题/正文」被否的同类理由：不扩采集面也不扩语义面 |

**复活条件（写出来，否则这是偏见不是裁决）**：三条全要——
(a) 该规则改由**本机计数**产生，即降级为 `x1`；
(b) 有 `x1` 在 `REAL-*` 上打赢「从不建议」的整数证据（§3.9 `FX1-2`）；
(c) exe 名的展示面裁决落地（C1 §7 遗留第 8 条：exe 名是否算正文，本文件同样倾向从严）。

**研究轨里它还剩什么（这是「只作研究」的可执行形状）**：

- **只在影子模式**（§6.3）里活着：算出「此刻会不会建议」，**不渲染、不落库、不进产品 crate**。
- 记录的量恰好三个整数：`fired`（触发次数）、`agreed`（其后 15 分钟内用户**自发**执行了 `plan.files` 的次数）、
  `opportunities`（`left(code.exe)` 事件总数）。
- **对手是 `c0_never`（从不建议）**，不是 `n0`。「从不建议」在这条轴上的精确率无定义、召回为 0，
  所以判据必须是成对的：`20·(agreed) ≥ fired`（**至少 5% 的卡片被印证**）**且** `fired ≤ 3/天`。
  两条任一不过 ⇒ 该规则在研究轨也记为墓碑，不再重提。
- **禁止**：把 `agreed` 写进任何持久化表；把它折算成百分比上屏；把它当作「用户人格倾向」的证据（C1 `F6-8` 单向玻璃）。
- **阻塞**：G18（无法把动作与前台会话对齐到同一时间轴，见 §5）⇒ 🚫 **今天连影子模式都跑不起来**，
  只能在 `ACT-PAIR` 合成夹具上跑。

### 3.9 `x1.exe_to_action_learned.v1` — 本机学习的 exe → 动作（`TESTABLE-AFTER-GAP`，🚫）

`x2` 唯一的合法后裔。**形状选择本轮就要裁，因为两种形状的代价差一个数量级**：

| 形状 | 说明 | 裁决 |
|---|---|---|
| (i) **门**：exe 转移只决定**何时**建议，建议内容由动作轴模型（`n2`/`a1`）给 | 状态量 = app 数 × 1 计数 | **采纳** |
| (ii) **特征**：把 `prev_app` 并进 `a1` 的上下文 | 状态量 = app 数 × 64；而 `a1` 本来就没支持 | **否决**：支持度被撕碎，且不可归因 |

采纳 (i) 的后果要写明：**这条候选属于「何时」轴**，因此它继承 Cycle 1 何时轴的全部纪律
（`Fc-1`：何时轴与 next-app 轴分两张表；`Fc-7`：打不过多数类常数 `c0` 就整体记 `inconclusive`）。
这里的 `c0` 是 **`c0_never` = 从不建议**。

- **输入**：`left(a)` 事件（§1.8 的精确定义）+ 进程内动作历史。
- **输出**：`suggest(plan.files, root_index)` 或 `abstain.*`。**建议 token 里只有 `root_index`，无路径字符串**（§1.7）。
- **选哪个根**：`roots().len() == 1` ⇒ 用它；`== 0` ⇒ `abstain.root_unavailable`；
  `> 1` ⇒ **`abstain.ambiguous_root`**。
  **不做**「按历史使用频次给根排序」——那是一张新的、按路径分格的行为计数表，
  它会把「你常整理哪个文件夹」变成一条可导出的画像行，且踩 G20。若日后要做，另立 `x3` 具名备选，先过 G20。
- **可数句**：「你最近 8 次离开 {a} 之后，有 5 次开了整理预览。」（`a` 是 exe 名 ⇒ 受 C1 §7-8 遗留裁决约束。）
- **杀线**：
  `FX1-1`（门）触发器定义逐条对上 §1.8：`ADV-flood` 上一天 1000 次切换，触发**上限**必须生效且上限值先写死。
  `FX1-2`（主）对 `c0_never` 的整数线：`20·agreed ≥ fired` 且 `fired ≤ 3/天`（同 `x2`，但这里是学出来的）。
  `FX1-3`（主）对 `n2` 的线：在 `n2` 已经给出建议的机会上，`x1` 不得改变答案（它只管**何时**）。改了 ⇒ 形状 (i) 没落实。
  `FX1-4`（门）支持 < 10 ⇒ `abstain.thin_support`，不得用全局分布顶上（沿 C1 `Ft-5`）。
  `FX1-5`（门）`ACT-NOROOT`：唯一根被删除后，建议必须当场消失（不是报错，是 `abstain.root_unavailable`）。
  `FX1-6`（门）遗忘：被计入的前台会话被遗忘后，该建议当场 orphan 且计数减回去。
  **闭集无驱逐，所以这条应当平凡通过；不通过就是实现有状态残留。**
  `FX1-7`（门）源码级：建议器不引用 `ActionRequest`（§2.4 门 1）。
- **阻塞**：**G17**（动作历史）+ **G18**（对齐）+ SG9（打扰账）⇒ 🚫。

## 4. 全候选通用门（在杀线之前，过不了不用比命中率）

继承 C1 §6 的七条，另加动作轴专有五条：

| # | 门 | 不过 ⇒ |
|---|---|---|
| D1 | **只吃 §1.1 的闭集**：动作字符串一律经 `ActionKind::parse`，`match` 禁通配 | 词表与实现会各走各的（G19 就是这么来的） |
| D2 | **拒绝 ≠ 批准**：`HitlDenial` 的任何分支都不得进计数（`FN0-2`） | 「用户想做但被拒」被学成「用户偏好」 |
| D3 | **内容无关**：状态里无 plan_hash / 文件名 / 路径 / 字节数；`ACT-RENAME` 下状态逐字节不变 | 踩「文件名是数据」 |
| D4 | **不读审计链**：候选源码对 `list_audit` / `AuditAction` 的引用数为 0 | 造遗忘旁路（C1 已裁，无复活条件） |
| D5 | **轴亲和登记**：`n0/n1/n2/a1/a2/a3/a4 → 无`；`x1/x2 → orderliness`（「建议你整理」离「你很乱」只有一句话） | P6 锁门对未登记的越界不会响（C1 `F6-6`） |
| D6 | **禁词面**（渲染层拦截，进 COPY 冻结流程）：你的下载文件夹很乱 / 你该整理了 / 你总是拖延 / 你不够自律 / 你效率低 | D22 非临床 + C1 `F6-7` |

**关于 §1.5 的量纲问题，本轮的换判据方案**（不放宽 `n ≥ 200`）：

1. **命中率类判据**（`FN0-1`/`FA1-1`/`FA3-2`）保留 `n ≥ 200` 且保留 `inconclusive` 按不过处理。
   后果诚实写出：**这些判据在真实日志上多半长期 `inconclusive`，因此这些候选长期不得晋级。这是正确结果，不是障碍。**
2. **主判据改为成对胜场**（同一机会集逐次比对，`20·(w_a − w_b) ≥ N`，沿 C1 `Ft-2` 形状）——
   它对小 N 更稳，且天然只在两者都有输出的格上比。
3. **打扰类判据**（`x1`/`x2`）沿用 C1 `F5-6` 的形态：**唯一硬指标是用户没把它关掉**，本机统计、不出网。
4. **在 `n < 200` 之前，动作轴只许输出弃权 token。** 这一条是产品默认，不是评测口径。

## 6. 夹具与评测

### 6.1 新增 `ACT-*` 夹具族

| ID | 内容 | 谁需要 |
|---|---|---|
| `ACT-SEQ` | 合成动作序列，已知一阶转移矩阵 + 精确 oracle | `a1` `FA1-5` |
| `ACT-EMPTY` | 零历史 | `abstain.no_history` |
| `ACT-DENIED` | 批准之间夹入 unknown action / plan 变更 / 令牌重放三类拒绝 | `FN0-2` `FA4-2` |
| `ACT-RESCAN` | 同目录连扫三次，plan_hash 三次不同、种类不变 | `FN0-3`、D3 |
| `ACT-RENAME` | 目录内文件全部改名，其余不变 | `FA1-3`、D3 |
| `ACT-RESTART` | 进程重启 | `FA1-4` |
| `ACT-PLANSHAPE` | `moves==0` 与 `moves>>0` 的后继不同 | `FA3-2` |
| `ACT-PAIR` | 前台会话与动作交错的时间轴，含 `code.exe` 组与对照组 | `x1`/`x2`（🚫 G18） |
| `ACT-FLOOD` | 一天 1000 次 exe 切换 | `FX1-1` |
| `ACT-NOROOT` | 授权根被删除 / 变成符号链接 | `FX1-5` |
| `ACT-LOCKED` | 五轴全锁 | P6 双向（行为 token 照出、轴向句被挡） |

**`ACT-*` 一律经真实闸门构造**：动作事件必须由 `check_action` 实际返回 `Ok(ApprovedAction)` 产生，
**禁止手插一行「假装批准过」**——沿 C1「夹具一律走真实采集/会话路径」（gpt-sol-b R1）。
这条不是洁癖：`FN1-2` 那个 `scan.directory`+`plan.files` 成对现象，手插夹具**永远造不出来**，
于是最重要的那条杀线会恒绿。

### 6.2 评测协议

沿用 C1：预顺序 prequential（test-then-train，单遍，禁打乱、禁用未来）；`as_of` 显式传入；
常量与种子在看结果**之前**冻结；先报整数分子分母再报派生小数；指标只活在评测器内部，永不上屏。

**动作轴专有的一条**：`laddered` / `bare` 双模式（C1 R3-12）在这里同样强制，
但**主杀线的 `laddered` 阶梯必须包含 `n2`**——因为动作轴上真正的回退不是「退到边际频率」，是「退到待决状态规则」。

### 6.3 影子模式（`x1`/`x2` 的唯一合法评测形态）

定义（本轮提出，请 R2 攻）：

1. 建议器照常计算，**输出不渲染、不落库、不进任何用户可见面**；
2. 只在内存里累加三个整数 `fired` / `agreed` / `opportunities`；
3. `agreed` 的判定必须是**用户自发**执行了该动作——若卡片没显示过，就不存在「点了卡片」这条路径，
   这正是影子模式的价值：它测的是**预测**，不是**说服**；
4. 进程退出即清零，不写盘（这既是遗忘友好，也意味着**它永远攒不出统计功效**——如实登记为已知代价，
   不许用「先存起来以后再删」绕过）；
5. 研究轨约束照旧：只吃 derived/aggregate，第三人行数恒 0，无单独同意不得出本机。

**影子模式解决不了的那个问题，本轮明说**：它测不出「如果真的弹了卡片，用户会不会接受」。
接受率只能靠真弹卡片测，而真弹卡片就是打扰。**这个循环无解**，只能靠一个显式的、默认关的、
用户自己打开的「让 Soul 试着给建议」开关来打破——那是产品决策，不是算法决策，本轮不裁，交 R2/父代理。

## 9. 留给 R2 的争点（本轮不裁，且不要在 R2 之前被默认掉）

1. **`FN1-2` 的合并规则**：`scan.directory` + `plan.files` 合并成一个事件，还是把 `scan.directory` 整个排除出动作轴？
   两种都能消除实现细节污染，但前者保留「用户看了一次目录」这个信号，后者更干净。**必须选一个并写死。**
2. **G17 的表要不要存在**：补一张可遗忘的动作历史表，是给用户增加价值，还是给用户增加一张「你都干了什么」的表？
   本轮倾向：**只有当 `FN2-1` 已经证明学习类候选打赢 `n2` 之后，才值得为它开这张表。** 顺序反了就是先建表再找用途。
3. **exe 名的展示面**（C1 §7-8 遗留）：`x1` 的可数句要念出 `code.exe`。本文件倾向从严但没有裁。
4. **「让 Soul 试着给建议」的开关**：§6.3 末尾那个死循环的唯一出口，属产品决策。
5. **动作轴要不要进研究导出**：动作序列是「这台机器的主人怎么用这个软件」，比 app 名更接近使用画像。本轮倾向**不进**，未裁。
6. **`abstain.budget_exhausted` 是不是应该阻塞 `x1` 的晋级**（而不只是登记 SG9）：
   本文件倾向**是**——一个没有打扰总账的建议器，它的「每天 ≤3 张」只是自己对自己的承诺。
