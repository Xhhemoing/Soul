### 2.2 组合代数（本轮唯一的新结构主张，也是把七条冻在一起才看得见的东西）

设 `C₀ = moves(build(scan))` —— 今天五级短路走完之后的候选移动集合（即 X0 的输出）。

> **冻结规则（分级独立性）：目录 A 里每一条后继的谓词，只能是 `C₀` 加上它自己的私有证据的函数。**

于是：

```
moves  =  C₀ \ ( D_magic ∪ D_supk ∪ D_recency )
reason(f)  =  冻结顺序里第一个成立的谓词
```

三条推论，每条都可以直接写成测试：

1. **复合不变式（一条测试覆盖整个目录 A）**：`moves(catalog(P)) ⊆ moves(X0(P))`。
   S1-V、S3a、SUP-K 都只收缩，S2-0 只注解 ⇒ **无论开哪几个、按什么顺序开，移动集合只会比今天更小。**
   这是 v0.1.1 执行面能安全继承整个目录 A 的形式理由：**执行器写得更少，严格更安全。**
2. **谓词彼此不看对方**：`SUP-K` 的支持计数取在 `C₀` 上，**不取在「过了幻数与近因之后剩下的」上**。
   代价是 SUP-K 的计数里可能含一个稍后被撤回的文件；收益是**开关 magic 不改变 SUP-K 的任何判定**，
   开关近因也不改变。没有这条，三个开关就有 2³ 种耦合行为，而杀线是逐条写的。
3. **顺序只影响理由归属，不影响移动集合**——但 `left_alone[].reason` 在哈希里（`plan.rs:188`），
   所以顺序仍是被批准的值的一部分，必须冻结（§2.3）。

**这条代数把 fable-a R2 的插入稳定性讨论安置到了正确的位置**：churn 度量的是
「一个文件出现后，预览里有多少行改变了含义」。SUP-K 的 churn = 2（新增一个 Sheet，
原本孤单的 `budget.csv` 与新文件同时改变归属）。**这是诚实的 churn**——它由一次真实的盘上改动引起，
而那次改动本来就已经改了 `snapshot_hash`。它的代价是复审成本，不是假拒绝，
所以它进 `FSK-1` 的用户面判据，不进准入门。

### 2.3 短路顺序（冻结）

```
1. is_dir?          → depth==1 ⇒ Directory ；depth>1 ⇒ 什么都不产出        continue
2. depth > 1?       → AlreadySorted / Nested                               continue
3. folder()==None?  → UnrecognisedKind                                     continue
4. 目标被占?        → DestinationTaken                                     continue
──────── 以上是 C₀ 的定义，以下三级是 Cycle 2 的新增，一律追加 ────────
5. 幻数与桶不相容?  → KindDisputed        （S1-V；只吃字节，与时间无关）   continue
6. 同类支持 < K?    → TooFewOfKind        （SUP-K；只吃 C₀ 的计数）        continue
7. 太新?            → RecentlyModified    （S3a；**唯一吃 as_of 的**）     continue
8. 否则             → claimed.push(dest); ProposedMove{...}
```

**为什么吃 as_of 的那一条必须排最后**：能在午夜改变输出的文件集合，恰好是
「除了近因之外没有任何其他理由不移动它」的那些文件，而这个集合在所有排列里**最小**。
一个既 `UnrecognisedKind` 又「太新」的文件，如果先报近因，它在午夜会从 `recently_modified`
变成 `unrecognised_kind`——**哈希变了，而这个文件从头到尾都不会被移动**。

**为什么 SUP-K 排在近因之前**：SUP-K 的支持计数取在 `C₀` 上（§2.2 推论 2），
所以它的判定不含 as_of。若反过来让近因先跑、并把被抑制的文件排除出支持计数，
午夜的一次翻转就能改变整个类别的支持度，从而连带翻转别的文件——**把单文件的午夜漂移放大成类别级的**。

三条新变体一律追加在 `LeaveReason` 末尾（`Ord` 是排序次键），各配一句中文 `explanation()`
（`everything_the_plan_leaves_alone_says_why` 会断言它非空）：

| 变体 | `as_str()` | 用户看到的话 |
|---|---|---|
| `KindDisputed` | `kind_disputed` | 扩展名说是这一类，文件开头看起来不是；不猜 |
| `TooFewOfKind` | `too_few_of_kind` | 这一类只有这一个，单独建个文件夹不值当 |
| `RecentlyModified` | `recently_modified` | 它的修改时间太新，这次先不碰 |

`RecentlyModified` 而非 `RecentlyActive`：mtime 不是「用户在用它」的代理
（`cp -p`、解压、`git checkout`、下载器都会保留或重置它）。**理由名是用户会读到的词，
它不许宣称数据支撑不了的东西。**

### 2.4 哈希面的冻结形状

三条后继各要一个开关，各要几个计数。**分散加键会让 `to_json` 顶层长出一片互不相关的字段**，
所以冻结成一个 `policy` 子对象（嵌套安全：`serde_json` 无 `preserve_order`，每层都是 `BTreeMap`）：

```json
"policy": {
  "magic":      { "mode": "off" },
  "recency":    { "mode": "off" },
  "duplicates": { "mode": "off" },
  "support":    { "mode": "off" }
}
```

打开时各自展开，例如：

```json
"recency":    { "mode": "utc_day", "within_days": 1, "unknown_mtime": 0 },
"magic":      { "mode": "dispute_only", "detector": "prefix512", "rule_version": 3,
                "opened": 4, "bytes_read": 2048, "disputed": 1, "not_sniffed": 0 },
"support":    { "mode": "min_count", "k": 2 },
"duplicates": { "mode": "tier0", "groups": 2 }
```

**准则（本轮冻结，C2R2 opus-a 提出、本轮沿用并推广到全目录 A）**：

> 一个值应当进入被哈希的计划，**当且仅当**它能在「计划的其余可见内容一字不变」的前提下改变执行的后果。

逐个判：

| 值 | 判定 | 理由 |
|---|---|---|
| `executable_in_this_version` | **进**（今天已进，有钉测） | 一个会执行的构建产出的 JSON 其余部分完全一样 |
| 三个 `mode` 与它们的常量（`within_days` / `k` / `rule_version` / `detector`） | **进** | 常量，永不因时间漂；且让「用户批准的这份计划是由一个开着某开关的构建做的」写在值里 |
| 读取账本（`opened` / `bytes_read`） | **进** | 这是第 6 个必要条件（§0.1）的落点：**「这次有没有读你的文件」必须在用户批准的那个值里面** |
| `unknown_mtime` / `groups` / `disputed` | **进** | 只由 scan 与字节决定，永不因时间漂；让元数据缺口在批准值里可见 |
| **`as_of_day`** | **不进** | 它的全部影响都已体现在 `moves`/`left_alone` 上。放进去 = 让「跨零点但计划内容一字未变」从无事发生变成一次假拒绝 |

**一次性代价，明说**：加了 `policy` 键之后，全关档的哈希与今天的 v0.1 哈希**不相等**。
考虑过「全关时不出这个键」以保住逐字节相等，**否决**：键的有无是隐式编码，
读 JSON 的人无法从缺席区分「这个构建没有这些功能」与「有但关着」。
计划不跨版本持久化（本 crate 无 `soul-store` 依赖），实际代价是**一条钉测改数**。

**签名面的冻结**：`preview()` 今天 6 个位置参数，三条后继各要一个开关会让它变成没人读得懂的东西。
冻结 `PreviewOptions { limits, magic, recency, support, duplicates }`。
（C2R2 opus-a 把这条登记为「不做定论」的备选，理由是当时只有一条候选要开关；**R3 冻结目录之后有四条，理由消失。**）

### 3.2 面的裁决（C2R2 opus-b §10 争点 1，本轮裁）

> **裁：`n2` 只在命令面（面 B）上有意义，且面 B **仅用于离线评测，永不上产品**。`n2A` 从对照席退位。**

三条理由，各自独立成立：

1. **面 A 上 `n2` 不可分于 `n1`，这是一个证明不是一个观察。**
   `has_prepared_draft()` 为真 ⟺ `prepare()` 成功过而 `generate()/discard()` 还没跑；
   而 `prepare()` 自己发出的动作事件就是 `allow(policy, ActionKind::GenerateWithUserEndpoint, ...)`（`draft.rs:197`）。
   所以只要条件成立，事件流里紧邻的上一个事件**必定**是 `egress.generate`——正是 `n1` 的输出。
   `n2A` 是 `n1` 的更弱子集：在 A1 上给同一答案，在其余机会上弃权而 `n1` 仍答。
2. **一个已被证明不可分的对照必须撤下，不能「留着也不亏」。** 留着它，
   「打赢了待决状态规则」这句话在面 A 上就永远为真且永远没有信息量，
   而 C2R1 立 `n2` 的**全部**理由是「没有它，`a1` 打赢 `n0` 会被误当成学到了用户习惯」。
   一个恒等于 `n1` 的对照提供不了这个保护——`n1` 自己提供。
3. **面 B 不上产品，是因为它的字母表守不住。** 面 A 的 8 个 token 由 `ActionKind` 闭枚举守着，
   加第 9 个动作会编译失败；面 B 的约 32 个 `pub fn` 没有枚举，加一个不会让任何东西红（G22）。
   门 `D1`（词表同步、禁 `_ =>` 通配）**在面 B 上失效**。
   离线评测器可以承受一张要人维护的清单；产品面不能。

**连带后果（照实登记）**：`FN2-1`（C2R1 立的「打不赢 `n2` ⇒ 学习类全体出局」）**作废**，
理由与 C2R2 opus-b §0 第 1 条相同——它的红绿由机会集的构成决定，不由模型质量决定。
替代它的是 §3.3 的上界处决。

### 3.3 上界处决程序（冻结；`K1`–`K6`）

**总纪律：这几条只能向下杀，不能向上抬。** 上界不处决 ≠ 学习有价值；上界处决 = 学习一定没价值。

| 步 | 式 | 处决条件 | 今天可跑 |
|---|---|---|---|
| `K1` 粗上界 | `U₁ = (\|C\| − hits_n2_C) + \|F\|` | `20·U₁ < \|O\|` | 是（不需实现任何模型） |
| `K2` 细上界 | `U₂ = \|O\| − hits_b0`（即基线错误数） | `20·U₂ < \|O\|` | 是 |
| `K3` 可分性 | `D = { i ∈ C : n2(i) ≠ n1(i) }`，要求 `\|D\| ≥ 20` 且 `20·\|D\| ≥ \|C\|` | 不满足 ⇒ `n2` 退位 | **是，面 A 上已红** |
| `K4` 优待夹具 | `F` 上对 `n0` 成对胜出 ≥10 点，`N_paired ≥ 200` | 不过 ⇒ 当场墓碑 | 是（合成语料造得够） |
| `K5` 真实语料 | a/b/c 三式同时成立（C2R2 opus-b §4.6） | 不过 ⇒ 不晋级 | 否（G17+G18+G21） |
| `K6` 饥饿 | 真实语料上 `\|O\| < 200` 或 `\|F\| < 200` | ⇒ `K5` 恒 `inconclusive` ⇒ 按不过 ⇒ **不进产品且删代码** | — |

`K2` 一句话：**「基线一共才错这么几次，任何模型至多把这几次全改对。改对了也不到 5 点，那就别做。」**

**`K6` 的落槌时点（C2R2 opus-b §10 争点 3，本轮裁）**：不绑日期，绑事件——
**首个向用户输出任何动作轴建议的版本**。在它之前语料不达标，学习分支不进那个版本且实现删除。
绑日期会被「再等一个循环」无限推迟；绑发布事件不会，因为发布是要发生的。

**C2R2 opus-b 手算普查的三类剖面（E1 重度 / 均衡 / 离线用户）上，`K1`/`K2` 一条都没打响**，
所以按预注册的处置规则（三类全处决 ⇒ 墓碑；两类 ⇒ 冻结；≤1 类 ⇒ 存活），**学习分支在这一关活下来**。
但那份普查的权重是编的（G23），**在 G23 之前它是一份形状检查，不是一份判决**——这一条要一起冻结，
否则「0 类处决」会被当成学习分支的通行证。

### 3.4 建议面的三分法（C2R2 fable-b，本轮冻结）

**可建议集 ≠ ¬令牌门控集。** 8 个 `ActionKind` 分三类：

- **S（可建议，4 个）**：`draft.reply` / `analyse.people` / `scan.directory` / `plan.files`。
- **U（免令牌但仅限用户自发，2 个）**：`forget.preview`（销毁压力）、`research.preview`（同意压力）。
  排除理由**不是**「未实现」——G19 补上生产者后判定一个字不变。
- **T（令牌门控，2 个，v0.1.1 起 +1）**：`forget.execute` / `egress.generate` /（文件执行）。

两个谓词不许合并：`suggestable(k) ⇒ !k.needs_capability_token()` 是硬蕴含，
但反向不成立（U 类是活反例）。实现成 `!needs_capability_token()` 一行，
明天加一个无害的免令牌 preview 动作，它就**自动**变成可建议，而没有任何测试会红。
`suggestability()` 的 `match` **禁 `_ =>` 通配**。

**卡片载荷里没有 `plan_hash` / `preparation_id` / `token_id` 字段——不是「不填」，是类型上没有槽。**
理由（回声论证，本轮认为是决定性的）：令牌铸造以批准屏原样 echo `preparation_id` + `plan_hash` 为前提，
而这两样只在用户看过那一屏之后存在。一张没让用户看屏的卡片没有可 echo 之物，
于是「指向 T 类动作的建议捷径」要么等价于导航卡（省零次点击），要么是 TOCTOU（AC-19 现有测试直接拒）。
**中间态在机器上不存在，所以这条禁令的产品代价恰好是零。**

## 4. 目录 C：进程身份 —— 诚实的空

Cycle 2 的第三个主题（`cycle2/CONSTRAINTS.md`「进程身份」）**没有产出任何新的可测算法**。
把这件事写清楚，比凑一条出来重要。

**它产出的是三样别的东西，本轮一并冻结**：

1. **一条边界**（C2R1 fable-b 的 X1–X7 整族非法清单）：无人值守代理循环、任意 shell / 生成脚本再执行、
   键鼠粒度采集与合成、屏幕与 UI 树采集、外部内容变成建议、置信度放行 / 永久允许、批准后计划可变。
   **这不是「推迟」，是采集面与执行面本身被锁。** RPA 文献里的「next action」大半落在这七条里。
2. **一个可测的事件定义**（C2R1 opus-b §1.8）：`left(a)` 在「app ≠ a 的一段合法会话开始」
   且「紧邻前一段合法会话的 app == a」且「两段之间未跨 `boundary`」时触发，
   触发时刻 = **后一段的 `started_at`**。三个已知代价：建议永远出现在用户已经进入下一个 app 之后；
   跨 `boundary` 的「离开」不可见（而「下班前关掉编辑器」恰恰大多跨 boundary）；必须有触发率上限。
3. **一条留给后面的裁决**：exe 名（`code.exe`）算不算「正文」、能不能上屏。
   C1 §7-8 遗留，Cycle 2 两个槽都倾向从严，**两轮都没裁**。
   x1 的可数句要念出 exe 名，所以这条不裁，x1 就没有合法的上屏形态。

**为什么是空的**：v0.1 的进程身份数据面只有密封体里的 `app` + `duration_ms`（Cycle 1 已冻结），
而 Cycle 1 已经在这个面上把 P0–P8 做完了。Cycle 2 能加的只有「把它接到动作轴上」，
那就是 x1/x2 —— 而它们双双阻塞于 G18（动作事件与前台会话对不到同一条时间轴上）。
**一个主题在一个循环里的正确产出可以是「这里今天没有算法」**，前提是把为什么写下来。

**唯一的例外是被证明不可分的对照——那要撤下，不是留着**（§3.2 的 `n2A`）。

### 7.1 G25 的粒度裁决（C2R2 fable-a §11 争点 1，本轮裁）

> **裁：两个主题，不是一个。**

```
fileplan.read_header    // 打开这次预览里你看得见的那几个待移动文件，各读开头 ≤512 字节
fileplan.read_full      // 打开授权根内文件的全部字节
```

理由是**读取账本差三个数量级、且面的形状不同**：

| | 打开的文件数 | 每文件读入 | 读什么 | 能上卡片的同意句 |
|---|---|---|---|---|
| `read_header`（S1-V） | ≤ `moves.len()`（**用户此刻正看着的那几个**） | ≤512 字节 | 格式签名（`%PDF-`、`PK\x03\x04`） | 「打开了你看到的 4 个待移动文件，各读开头 512 字节，核对签名与扩展名一致」 |
| `read_full`（S2-H） | O(同尺寸桶内的全部文件) | 全长 | 全部字节 | 「为了确认这几组是不是真的重复，读了 36 个文件的全部内容」 |

**头字节是格式证据，不是语义正文**——S1-V 读的是「这实际是不是 PDF」，读不到「这份 PDF 讲什么」。
它越的是 v0.1 的「一个字节都不读」承诺，但它**不越**「不读第三人正文语义」那条更硬的第三人锁。
把两者塞进同一个主题，等于让用户为了一次头字节核对而授权全文读取——
按 `kind.rs:1-7` 自己那句「a read-only promise that still opens every file is a smaller promise than it sounds」的逻辑，这两个承诺不对称。

### 7.2 G23 与门 D4 的边界（C2R2 opus-b §10 争点 2，本轮裁）

争点：一次性离线普查读审计链，算不算「拿审计当特征」？
C2R2 opus-b 给的区分是「运行时输入 vs 一次性建造决策」，并自陈「我不认为这个区分是显然的」。
**本轮认为它确实不够——正确的分界不在时点，在于那个数字最后住在哪里。**

> **裁：分界是「一个从不可遗忘的表里导出的数，会不会活进一个用户删不掉的产物」。
> 于是：普查只许杀，不许标定。**

| 普查的用途 | 产物 | 判定 |
|---|---|---|
| 决定某个候选是否出局 | 产物是**一段不存在的代码** | **允许。** 用户遗忘之后，这段代码仍然不存在——但「不存在的东西」不携带他的信息，也不作用于他 |
| 标定一个会随构建发布的常量（阈值、桶边界、`within_days`、`K`） | 产物是**二进制里的一个数** | **禁止。** 那个数是从他删不掉的表里算出来的，并且永远留在产品里。这正是 D4 要防的东西，只是绕了一圈 |

这条界线与 §3.3 的既有纪律严丝合缝：`K1`–`K6` 本来就**只能向下杀，不能向上抬**。
所以「普查只许杀，不许标定」不是新加的约束，是把那条纪律的**理由**补上——
它之所以只能向下，不只是因为上界数学是单向的，也是因为**向上用会把审计链变成产品常量的来源**。

**连带后果**：§9 常量表里任何标「猜」的数，都**不许**用一次真实语料普查来「定下来」。
定它们只能靠合成夹具的参数扫描，或者承认它是约定。这条对目录 A 同样成立
（`within_days`、`K`、S2 的 `MIN` 都在这条线上）。

2. **U 类连导航都不给是否过严**（C2R2 fable-b §7-1）。遗忘的可发现性只剩记忆管理界面自身。
   这是产品判断不是机器判断。
3. **`b0` 值不值得成为 v0.2 要发的东西**（C2R2 opus-b §10-6）。一个「只在你准备好回信时提醒你还没生成」的功能，
   值不值得占一个位置，是产品决策。
4. **离线用户身上根本没有对照这件事**（C2R2 opus-b §4.4 读数 3 / 门 `S7`）：某类用户上 `|C| = 0` 时，
   「学习候选打赢了对照」这句话从来没有被检验过。为这类用户单立一条对照，还是承认动作轴对他们整体不适用？
5. **语义聚类的分离建议流要不要存在**（C2R2 fable-a §11-2）：是给用户价值，还是给用户增加一张
   「机器怎么看你的文件」的面？顺序反了就是先建流再找用途。
6. **v0.1.1 的执行面要不要要求 `CapabilityScope::FileWrite` 令牌**。
   与 S3 无关，但 S3 使它变得紧要：`plan.files` 今天不需要令牌（`hitl.rs:74-79`），

   有了两分钟 TTL，那个窗口才被 `120 / 86 400 = 1/720` 约束住。**这是产品面的决定，本文件只登记它的算法后果。**

## 12. 交给父代理的一句话

Cycle 2 的结论不是「哪个程序算法好」，是**程序算法与 Cycle 1 的行为算法受不同的东西约束**：
Cycle 1 的瓶颈是数据面（密封的 exe 名 + 时长，所以只能做整数计数上的 Markov 与时段桶），
Cycle 2 的瓶颈是**同意面**——`plan_hash` 要求分类器是「(目录快照, 带版本的规则表)」的纯函数，
`ConsentTopic` 里没有「打开你的文件」，`LeaveReason` 要求每一条判定都能落成一句用户读得懂的中文。
于是活下来的四条（S3a 近因抑制、SUP-K 支持阈值、S2-0 零读重复候选、S1-V 只撤回的幻数）
**共享同一个形状：它们只会让 Soul 少提议一件事，从不多提议一件事**——
这不是巧合，是同意契约在筛选算法；而动作轴上没有任何一条学习候选今天能被检验，
因为可遗忘的动作历史表（G17）还不存在，**而在它存在之前，唯一诚实的默认是沉默**。
