## 0.1 型词表（沿 C1R3 §0.1，新增一型）

| 型 | 含义 | 不过时的动作 |
|---|---|---|
| **主** | 主杀线（收益） | 该候选（或该配置）从 v0.2 默认轨**出局**，只保留墓碑 |
| **上** | 上界处决（**本轮新增**） | 不必实现候选就能算出它的天花板；天花板不够 ⇒ 同「主」处决。**只能向下杀，不能向上抬** |
| **门** | 结构门 | 该候选的**全部收益数字作废**（不是「差」，是「不可采信」）；修好再跑 |
| **降** | 降级线 | 降为对照 / 具名备选 / 默认关，不删 |
| **红** | 红灯 | 说明 harness 或实现有 bug。**先修工具，禁止记为战绩** |
| **晋** | 晋级线（**本轮新增**） | 用于默认状态已经是「关」的候选：不过不是出局，是**继续关着**。举证责任在提议开的人 |

「上」与「晋」是同一件事的两侧：**当默认是开，你要一条能把它关掉的线；当默认是关，你要一条能把它打开的线。**
把这两种线混写成一张表，是 R2 里多处争论说不清的根因——争的其实是默认值，不是判据。

**本轮新增的区分（R2 里被反复混用）**：

| 情形 | 判定 | 处置 |
|---|---|---|
| **阻塞** | 判据是好的，缺一个**可以被造出来**的前置件（访问器、needle 表、夹具修法） | 登记缺口，等前置件；不改判据 |
| **饥饿** | 判据是好的，缺的是**关于世界的量**（真实语料、真实事件数），且短期内拿不到 | 按不过（C2R2 opus-b `K6` 的死代码条款），**不许挂在待定上** |
| **坏杀线** | 判据本身在任何夹具上都不可能变红 | **换判据**，记进报告的「坏杀线」栏 |

三者的差别是可操作的：阻塞要人写代码，饥饿要人做决定，坏杀线要人重写判据。R2 把三者都写成「🚫」，
于是「等不到」变成了一个可以无限期停在那里的状态。§6 对本文件自己的每一行做了这个分类。

## 2. 本轮的三条源码级发现（每条都改了某张表）

### 2.1 `left_alone` 的理由进哈希，而理由的排序次键是死代码

实读 `crates/soul-fileplan/src/plan.rs`：

- `to_json`（`:164-192`）把 `left_alone` 的每一行编码成 `{"path": …, "reason": reason.as_str()}`（`:186-189`）。
  **理由字符串在被哈希的值里**——这是下一小节全部论证的地基。
- `left_alone.sort_by(|a, b| (&a.relative, a.reason).cmp(&(&b.relative, b.reason)))`（`:270`）。
- 但 `build()` 的循环里，每个条目走到任意一个 `continue` 之前**恰好 push 一行**（`:214-267` 的五个分支各一次），
  而扫描条目的 `relative` 互异（目录遍历的构造性质）。
  **⇒ `a.relative == b.relative` 永不发生 ⇒ `a.reason.cmp(&b.reason)` 永不被求值。**

后果两条：

1. R2 有两份文件（opus-a §3.3、fable-a §2.4）用「`Ord` 被当作排序次键」论证新变体必须追加在末尾。
   **这条论证今天是空的。** 结论仍然采纳（追加在末尾代价为零），但理由换掉——
   一条建立在死代码上的纪律，会在有人删掉那行 `sort_by` 的时候连带失效，而它本来就不该依赖它。
2. **真正该立的门是「一路径一行」**：一旦某条后继让同一路径出现两行（S2 的「它可能与另一份重复」注解是最直接的诱惑），
   那个次键立刻变活，`LeaveReason` 的**声明顺序**就成了哈希语义，
   于是 S1、S2、S3 三条后继的变体登记顺序开始互相耦合——一条后继改了自己的变体位置，另外两条的哈希跟着变。
   立成 `FS2-4`（门），并在 S1/S3 表里各引一次。

### 2.2 S1 必须排在 S3 之前，否则每个午夜产生一次纯假拒绝

**设定。** 一个文件 `f`：深度 1、扩展名可识别、目标未占用（即通过短路 1–4）、
它「太新」（S3 会抑制），**且**它的字节与扩展名的桶矛盾（S1 会撤回）。

| 次序 | 今天 `f` 的理由 | 明天（跨 UTC 零点，`f` 不再太新）的理由 | 哈希 | `f` 被移动过吗 |
|---|---|---|---|---|
| **S3 在前** | `recently_modified` | `kind_disputed` | **变** | 从来没有，两天都没有 |
| **S1 在前** | `kind_disputed` | `kind_disputed` | 不变 | 从来没有 |

「S3 在前」那一行**完全落在 opus-a R2 §1(b) 给的假拒绝定义里**：盘上快照相同、`moves`/`left_alone` 的**语义**相同
（这个文件两天都不动），`plan_hash` 不等。用户读到的是「计划在你批准之后变过了，请重新看一遍再决定」
（`execute.rs:52`），而计划的**后果**一字未变。

这正是 opus-a 那条排序规则要防的东西，他的表述是「吃 as_of 的理由排得越靠后，能在午夜改变输出的文件就越少」。
他只把 S3 与**今天已有的**四条理由比过。加进 S1 之后，规则的形式化版本是：

> **在短路链上，一个理由的位置必须晚于所有「比它更稳定」的理由。**
> 稳定序：`Directory/AlreadySorted/Nested`（拓扑，只随盘变）> `UnrecognisedKind`（名字）
> > `DestinationTaken`（同目录其他名字）> `KindDisputed`（自己的字节）> `RecentlyModified`（as_of）。

`KindDisputed` 比 `RecentlyModified` 稳定，因为字节不变则裁决不变，而 as_of 每天都在动。故 C2-2 的次序。

**代价，必须一并登记，且它是真的。** S1 排在 S3 之前，意味着 S1 会打开那些 S3 本来会抑制的文件——
**你开了它、读了它、然后不移动它，而不移动它的理由本来不需要读它。** 可数化：

- 新增计数 `opened_then_recent`：通过短路 1–4、被 S1 打开、且 S3 本来也会抑制的文件数。
- 立成 `FC-2b`（降）：若 `2·opened_then_recent > opened`（过半的开文件是白开的）⇒
  **两者不得同时默认开**，必须二选一。

**这个两难有没有第三条路？** 我找了三条，都不通，逐条记下免得下一轮重找：
(a) 「先算近因、只用来决定开不开，理由仍按 S1 优先」——做不到：不开就没有裁决，没有裁决就只能写 `recently_modified`。
(b) 「合并成一个理由 `withheld`」——破可解释性（`plan.rs:11-16` 的标准），且用户读不出两种完全不同的原因。
(c) 「把 as_of 也钉进 S1 的裁决缓存」——那是给一个纯函数加状态，`no_write_api.rs` 第二层与 §0.4 都不允许。

**实践上这个两难今天不咬人**：S1 默认关（C2-6）。所以 `FC-2b` 只对「主动开了 S1 的用户」生效。
把它写下来是因为**它是一条只在组合里存在的失败，逐条测永远测不到**，而 R2 的六份文件全部是逐条写的。

### 2.3 三条后继各自要求「模式进哈希」，合起来需要一个共享机制

`executable_in_this_version` 在被哈希的值里（`plan.rs:169`），三条后继都援引这个先例：
S1 要 `magic + rule_version + prefix_limit + budget`（gpt-sol-a R2 §8）、
S3 要 `recency.{mode, within_days, unknown_mtime}`（opus-a R2 §3.1）、
S2 若上预览也要 `mode`。合起来：

- 一个未动过的目录，**策略向量的每一次翻转都改哈希**。三个二值开关 ⇒ 同一个目录最多 8 个不同的 `plan_hash`。
- 这些跳变**都不是假拒绝**（策略变了，后果确实可能变，符合 opus-a §3.1 的准则），
  但它们会作废一切**未执行的批准**。
- 所以 opus-a 为 S3 设计的「层 C：把 as_of 钉进批准、执行时重放」**不能只钉 as_of**：
  必须钉**整个策略向量 + as_of**，作为一个东西随批准走。三条候选各自实现一次层 C = 三份会漂的实现。

立成 `FC-1`（门，见 §4.5）：**批准载荷里带的是 `(plan_hash, policy_vector, as_of_day)` 三元组，且执行器用带回来的
后两者重算。** 任一条后继单独落地时就要按这个形状做，不许先做一个只钉自己那一格的版本。

## 3. 上界处决的移植：三条能算，一条算不出

C2R2 opus-b 为 N2 发明的方法是：**基线一共才错这么几次，任何后继至多把这几次全改对；改对了也不到 5 点，那就别做。**
它的力量在于**不需要实现候选**。本轮试着把它移植到三条文件候选，结果不均匀，而这个不均匀本身是结论。

| 候选 | 天花板由什么决定 | 今天算得出吗 | 为什么 |
|---|---|---|---|
| **S3a** | `days_since ≤ within_days` 的散文件数 `S` | **能**，零读 | mtime 已在 `ScannedEntry`（`scan.rs:424-428`），只用元数据 |
| **S2-0** | 同 `(parent, size, ext)` 键的候选对数 / 有候选的根占比 | **能**，零读 | 只用目录项。gpt-sol-b R2 已经在两份语料上算过 |
| **N2B** | `\|C\|`（`n2` 开火的机会数）与 `b0` 的错误数 | **能**（阻塞 G21/G23 的判决效力，形状检查可跑） | 待决状态是进程内两个 `Option` |
| **S1** | 「扩展名撒谎且跨桶」的文件数 | **不能** | 这个量**必须读字节才知道**——而读字节正是 S1 要用户批准的那件事 |

**S1 的循环，写清楚**：要证明「开文件值得」，就得先开一批文件数一数。这不是懒，是结构：
S2-0 与 S3a 的普查只用元数据，同意成本与产品功能本身**不同级**；
S1 的普查与 S1 的功能**要的是同一份同意**。所以 §5 把语料缺口拆成 `G24a`（元数据普查）与 `G24b`（正文普查）两级。

**我试过给 S1 造一条零语料的上界，失败了，把失败记下来**：
最自然的构造是「69 项扩展名表 × 预注册规则表」的可裁决矩阵 `M[e][r] = (of_extension(e) ∉ C(r))`，
算 `D69 = |{e : ∃r, M[e][r]}|`。但只要规则表里有一条 JPEG，`.rs` 就与它矛盾，于是 `D69` 几乎必然 = 69，
**这条线永远绿 ⇒ 按 §0.5 它是坏杀线，不许写进表里。**
它测的是规则表的丰富度，不是 S1 的收益——收益是「撒谎频率」，那个数不在仓库里。

**S1 唯一的零语料结论是一条先验，不是判据，登记在此不作判据用**：
S1 最能发力的桶（Image / Audio / Video）恰是扩展名最少撒谎的桶（相机与系统写的名字）；
S1 完全瞎的地方（ZIP 家族横跨 `Archive/Document/Sheet/Slides` 四桶，gpt-sol-a R2 §2.2）
恰是撒谎最有后果的地方（一个其实是 zip 的 `.docx`）。
**这条先验支持 fable-a R2 §10 的自我怀疑「`MAGIC-RATE < 1%` 概率过半」，本轮背书这个判断。**

**S2 表的一条结构说明（本轮新增，纠正 fable-a R2 §9 的一格）**：
fable-a 把精确哈希去重记为「P1 内容局部性 ✓」。**严格说不对**：一个文件是不是「重复」，取决于别的文件的内容。
它过的是一条更弱的性质——**成对局部性**（裁决由**一对**文件自身决定，不由全目录分布决定）。
差别在 `FS2-3` 上是决定性的：成对局部性足以支持**注解**（「这两份一样」，两份都出现在句子里），
但不足以支持**移动**（「移走这一份」，句子里只有一份，另一份在句子外面决定了它的命运）。
**去重能活下来不是因为它局部，是因为它只说不做。**

## 9. 留给父代理 / Cycle 结束的争点（本轮不裁）

1. **G23 与门 `D4` 的边界**：一次性离线普查读审计链，算不算「拿审计当特征」？
   C2R2 opus-b 给的区分是「运行时输入 vs 一次性建造决策」，他自己说不认为这个区分是显然的。
   **我也不认为**，且本轮把它扩大了——G24a 是同型的东西（一次性读用户目录的元数据出聚合整数）。
   两条一起裁比分开裁便宜：**要么承认「一次性离线聚合普查」是一个有名字的、有同意流程的第三条轨道，要么两条都不做。**
2. **`FS1-1` 的循环有没有出路**：要证明开文件值得，得先开文件。
   本轮的处置是「默认关 + 死代码兜底」，但这等于把 S1 无限期挂起。
   另一条路是**影子研究**：用户自己的机器、一次性、只出一个整数（「你的 200 个待整理文件里，有 N 个的开头与扩展名不符」）、
   不出本机、不落库。它是不是一个可以出现在产品里的句子，是产品决策不是算法决策。
3. **`SUP-K` 与 S2 的关系**：两者都是「支持度太低就别提议」的形状（单件类别不建文件夹 / 只有一个候选就别说重复）。
   本轮把它们分开立项，但没检查它们会不会在同一批文件上打架。
4. **v0.1.1 的排期耦合**：`FS3-8`/`FS3-9`（层 C + `PlanTooOld`）、`FC-1`（三元组批准载荷）、
   以及 §4.4 末尾那条「执行面上线 ⇒ `n2B` 多一行 ⇒ 学习天花板降低」，是同一个依赖的三个面。
   **文件执行面上线这件事，同时改变了三条文件候选的判据形状和一条动作候选的天花板**，
   这一点在 Cycle 2 的六份 R1 与六份 R2 里都没有被当成一件事看。
5. **两个 Cycle 的面分离**：动作轴的学习被杀，**不影响** Cycle 1 的 next-app 轴与何时轴，反之亦然。
   任何跨面援引杀线的说法，先证明两个面的机会集是同一个（它们不是）。
