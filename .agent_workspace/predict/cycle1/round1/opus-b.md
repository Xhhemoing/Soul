## 0. 公共骨架（九个候选共享，不在各自小节里重复）

|---|---|---|---|
| S1 | 前台会话 | `app_id`（`notepad.exe` 级可执行名）、`start_unix`、`duration_s`、本机时区偏移 | P0–P4、P7、P8 |
| S2 | 人脉边（T4D 已冻结） | `band`、`direct_out/in`、`group_out/in`、`direct_active_day_count`、`last_contact`、`last_direct_contact`、`silent_days`、`as_of`、`locked_by_user`/`user_band`/`machine_band` | P5 |

**没有的**：窗口标题、键鼠、剪贴板、文件名、聊天正文、跨用户数据。任何候选一旦需要这些，不是调参问题，是出局。

### 0.2 会话流的规范化（P0–P4/P7/P8 的共同前处理，必须单源）

前台采集会因为焦点抖动产生碎片，不规范化的话一阶转移表会被 `a→b→a` 噪声灌满。

| 常量 | 值 | 含义 |
|---|---|---|
| `MERGE_GAP_S` | 5 | 同一 `app_id` 的两段前台间隔 ≤ 5 秒 → 合并为一段（去抖） |
| `MIN_SESSION_S` | 3 | 合并后仍 < 3 秒的段丢弃，不进任何计数 |
| `SESSION_GAP_S` | 1800 | 相邻两段间隔 ≥ 30 分钟 → **不构成转移**，记一个 `boundary`，转移链在此断开 |

`boundary` 不是废数据：P3 预测的正是「刚过 boundary 时开哪个 app」这一格，那恰好是 P1/P2 无上下文可用的格。

### 0.3 输出契约：token，不是分数

所有候选的输出是**闭集 token 的有序表**，附整数支持计数，供解释与手数。

- **禁止**：概率、百分比、归一化置信度、任何浮点、任何「分/百分位」（D22 的禁令在预测面同样生效，理由不同但结论相同：不可数的数字用户没法纠正）。
- **允许**：整数计数（`12 次里有 9 次`）、整数天数、桶名。用户复核一条预测只需要数事件条数，无乘法、无小数——沿用 T4D 的可数性判据。
- 排序用整数计数降序，**并列一律按 `app_id` 字典序升序**打破（否则输出随 HashMap 迭代顺序漂，测试 flaky）。
- 每个候选必须有弃权 token。共享弃权集：`abstain.consent_off`（采集没开）、`abstain.no_data`、`abstain.thin_support`、`abstain.axis_locked`（P6 加的）。
  **「猜」不是弃权的替代品**：证据不够时输出 `abstain.*`，不是输出一个低支持的 top-1。
- 每条 token 携带可解引用的 `evidence_ids`（或其等价物：能重建该计数的事件 id 集合的界定方式，见 0.5）。无证据不得落库这条在预测面照旧。

### 0.4 训练纪律：只有在线计数

对九个候选一律成立，写死：

1. 更新是 `update(event)`，摊销 O(1)，只做整数加减；**无梯度、无反向传播、无批量重训、无浮点权重、无随机初始化、无超参搜索**。
2. 状态是有界的整数计数表。表大小上限用 Misra-Gries / Space-Saving 式重击者计数：全局 `TOPK_APPS = 256`，行内 `TOPK_ROW = 32`，溢出进 `other` 桶。（长尾进 `other` 是有意的：一年只开一次的 app 不该占状态，也不该被预测。）
3. 判定是纯函数 `(counts, context, as_of_unix) -> tokens`。**禁读墙钟**，`as_of` 由调用方显式传入——与 T4D 同一条纪律，理由也一样：读墙钟的判定没法写不 flaky 的测试。
4. 计数表是**可重建的派生物**：从事件表单遍重放即可得到，自身不是存储层。

### 0.5 遗忘：减一必须等于重放（可测的不变式）

计数表的桶键（`app_id`、`(prev,cur)`、`(weekday_class, hour)`、时长桶、tick 桶）全都是事件字段的**纯函数**，所以删掉一条事件时能算出该减哪个桶，不需要额外存映射。

> **不变式 F**：`replay(events \ {e}) == decrement(replay(events), e)`，逐桶相等。

这条对 P0–P3、P5、P8 天然成立。**P4 会破坏它**（指数衰减累加器的右移不可逆），所以 P4 的规范里被迫改成环形桶重算——不是为了优雅，是为了这条不变式，见 §2.5。

遗忘一条事件后，引用它的预测输出立刻降为 orphaned/消失；这是 PRODUCT_LOCK「派生推断降为 orphaned」在预测面的落法。

### 0.6 评测协议（所有「证伪测试」共用；这些指标是内部评测量，不是用户看得到的输出）

- **预顺序（prequential / test-then-train）**：按时间序单遍，先预测再更新。**禁止打乱、禁止用未来数据**。
  评测器必须自带一个泄漏探针：把序列随机置换后，带上下文的候选（P1/P2）必须退化到 ≈ P0；没退化说明 harness 漏了未来，是评测的 bug 不是算法的功劳。
- **夹具三类**：
  - `SYN-*` 合成生成器（可控的马尔可夫源、可控的日节律源、可控的纯随机源）；
  - `REAL-*` 作者本机真实日志（不出网，本机评测；v0.2 才允许研究导出落盘）；
  - `ADV-*` 对抗夹具（刷屏、单 app、新装软件、跨 DST、跨时区、空日志、采集刚开启）。
- **指标**：top-1 命中率、top-3 命中率、弃权率、打扰次数（P4/P5/P8）。
- **通用门（九个都要过，过不了不用比命中率）**：确定性（同输入同输出）、`as_of` 平移不变、空日志→弃权、未同意→事件 0 →弃权、不变式 F、P6 门通过。

## 2. 规范

### 2.1 P0 — 全局频次基线（对照组）

**一句话**：不看任何上下文，只报你最常开的三个。存在的唯一理由是当所有人的杀线。

- `algorithm_id`：`p0.marginal_top_k.v1`
- **输入**：S1 的 `app_id` 序列（规范化后）。不读时间、不读时长、不读上下文。
- **输出**：`next_app(app_id)` × top-3，各带 `count`；无计数 → `abstain.no_data`；采集未同意 → `abstain.consent_off`。
- **训练（在线计数）**：`count[app] += 1`，Misra-Gries 上限 `TOPK_APPS`。
- **可数性**：用户数自己开过多少次某个 app，与 `count` 逐一对上。解释句：「过去 {N} 段前台里，{app} 出现 {c} 次，最多。」
- **锁冲突**：无轴亲和；仍须过 P6（防渲染层把「你最常开游戏」说成人格）。
- **证伪测试**：
  - F0-1（它的定义性作用）：对任一其它候选 `Px`，若在全部 `SYN-*` + `REAL-*` 上 `Px` 的 top-1 不高于 P0，**`Px` 出局**。P0 自己不可被证伪，因为它是对照。
  - F0-2：`ADV-single_app`（只用一个 app）上 top-1 必须 = 100%；不到说明规范化管道有 bug。
  - F0-3：并列 tie-break 稳定性——`SYN-tie`（两个 app 计数完全相同）跑 1000 次，输出顺序逐次相同。
- **已知缺陷**：对「刚开机」「刚从 boundary 回来」这类真正需要预测的时刻毫无信息量；它赢了只说明别人烂。

### 2.2 P1 — 一阶 Markov 下一个可执行文件

**一句话**：数「在 A 之后你开了几次 B」，报 top-3。

- `algorithm_id`：`p1.markov1_next_exe.v1`
- **输入**：规范化会话流的相邻对 `(prev_app, cur_app)`，跨 `boundary` 不计。当前上下文 = 当前前台 `app_id`。
- **输出**：`next_app(b)` × top-3 + 每个的 `count` 与该行总数；行总支持 < `MIN_ROW_SUPPORT = 5` → `abstain.thin_support`（**不降级去猜 P0，降级由 P7 统一做**，否则每个候选各降各的，评测就没法归因）。
- **训练**：`trans[a][b] += 1`；行内 `TOPK_ROW = 32` 重击者，溢出进 `other`（`other` 永不作为预测输出，只用于算行总数）。
- **可数性**：解释句「上一次你在 {a} 之后，12 次里有 9 次开了 {b}」——两个整数都能手数。
- **锁冲突**：无轴亲和。禁词表：转移模式不得被渲染成「注意力涣散 / 拖延 / 自律」等轴向措辞（这是 P6 R5 的禁词面）。
- **证伪测试**：
  - F1-1（主杀线）：预顺序 top-1 必须比 P0 高 **≥ 10 个百分点**，在 ≥ 2000 次转移、≥ 3 个独立日志上同时成立。达不到 → 出局（它的状态是 P0 的 `M` 倍，赢不够就不值）。
  - F1-2（反向，查评测泄漏）：`SYN-shuffle`（把真实序列随机置换，边缘分布不变）上 P1 必须退化到 P0 ± 2 点。**显著更高就是 harness 漏了未来**，先修 harness 再谈算法。
  - F1-3：`SYN-markov1`（已知转移矩阵生成）上 top-1 必须逼近该矩阵的贝叶斯上界（差距 ≤ 5 点），否则实现错了。
  - F1-4：不变式 F 逐桶。
  - F1-5：`ADV-flood`（一天 1000 次 5 秒切换）不得把状态表打爆，也不得让某一行独占预测；`MIN_SESSION_S` 应把大部分刷屏挡掉，实测挡掉多少要如实记录。
- **已知缺陷**：装新软件后冷启动期长；「同一个 app 内不同任务」它区分不了，而窗口标题永远不采，所以这个天花板 v0.2 打不破，别装作能打破。

### 2.3 P2 — 二阶 n-gram + 确定性回退

**一句话**：先看前两个 app，数据不够就退回一阶，再不够退 P0。回退是阶梯，不是加权插值。

- `algorithm_id`：`p2.ngram2_backoff.v1`
- **输入**：`(prev2, prev1)` → `cur`，跨 `boundary` 断开（跨 boundary 的三元组不计）。
- **输出**：同 P1 的 `next_app` × top-3，**额外带 `order_used ∈ {2,1,0}` token**，因为用户有权知道这一条是靠哪层数出来的。
- **训练**：`trans2[(a,b)][c] += 1`，同时**共享** P1 的 `trans` 表（不重复存）。
- **回退阶梯（确定性，无浮点）**：`trans2[(a,b)]` 行总 ≥ `MIN_ROW_SUPPORT_2 = 8` → 用二阶；否则用 P1（行总 ≥ 5）；否则 P0。
  这是 stupid backoff 的整数化：**不做 Katz 折扣、不做插值**，因为折扣量是浮点，会毁掉可数性。代价（诚实记）：理论上比插值差，差多少由 F2-1 实测。
- **可数性**：「你在 {a} 然后 {b} 之后，8 次里有 6 次开了 {c}」。
- **锁冲突**：同 P1。
- **证伪测试**：
  - F2-1（主杀线）：top-1 必须比 P1 高 **≥ 3 点**，**且**状态条目数不超过 P1 的 8 倍。任一条不满足 → 出局，留 P1。
  - F2-2（过拟合探针）：留出末 20% 时间段，二阶在留出段上不得比一阶差；差了说明阈值 8 太低。
  - F2-3：`SYN-markov1`（真源就是一阶）上 P2 必须 ≈ P1（差 ≤ 1 点）——回退阶梯不能自己制造噪声。
  - F2-4：`ADV-new_app`（第 100 天装一个新 app 并高频使用）下，`order_used` 必须在 8 次之内从 0 爬到 2；爬不上去说明冷启动不可接受。
- **已知缺陷**：状态爆炸风险最高的一个；`TOPK_ROW` 的裁剪会不均匀地伤害长尾用户，评测要分「app 数 < 20」和「> 60」两档看。

### 2.4 P3 — 时段桶最频

**一句话**：数「工作日上午 9 点你通常开什么」，不需要任何上下文。

- `algorithm_id`：`p3.hourbin_top.v1`
- **输入**：S1 的 `start_unix` + **本机时区偏移** + `app_id`。
- **分桶**：`bin = (weekday_class, local_hour)`，`weekday_class ∈ {工作日, 周末}` → **48 桶**。
  为什么不是 7×24=168：一年数据下 168 桶每桶太稀。`p3b.hourbin168.v1` 作为**具名备选**保留，不点名到不了，由 F3-4 决定要不要启用。
- **时区**：分桶必须用**本机墙钟小时**（作息是人的，不是 UTC 的），所以事件必须同时存 UTC 与当时的 tz offset。DST 与出差换时区是已知坑，由 F3-3 钉。
- **输出**：`hour_bin_top(app_id)` × top-3 + 桶计数；桶计数 < `MIN_BIN_SUPPORT = 10` → `abstain.thin_support`。
- **训练**：`bin_count[bin][app] += 1`。
- **可数性**：「工作日 9 点这一格，你开过 30 次，其中 {app} 18 次。」
- **锁冲突**：**轴亲和 orderliness（条理与执行）**。「你很规律」是人格话，P3 不许说；只许说「工作日 9 点你 30 次里 18 次开了它」。该轴锁定时，任何轴向渲染被 P6 挡掉，但 `hour_bin_top` 这个行为 token 照出（见 F6-2 的双向性）。
- **证伪测试**：
  - F3-1（主杀线）：在**无上下文格**（开机后第一段、`boundary` 之后第一段）上必须比 P0 高 **≥ 8 点**；这是它唯一有独立价值的地方，赢不了这里就没必要存在。
  - F3-2（节律是相对的）：把全部时间戳整体平移 +6 小时并同步平移 `as_of`，top-1 命中率必须**基本不变**（±1 点）。变了说明桶边界被过拟合。
  - F3-3：`ADV-dst`（跨一次 DST 切换）与 `ADV-tz_change`（时区从 +08 变 +01）下不得 panic、不得出现负桶号；命中率的跌幅必须被记录成已知代价，不许粉饰。
  - F3-4（决定 48 还是 168）：两种分桶在同一批夹具上跑，168 只有在 ≥ 6 个月数据的夹具上赢 ≥ 3 点才启用。
  - F3-5：不变式 F。
- **已知缺陷**：作息不规律的用户上它几乎等于 P0；失业/换班/放假会让它长期错，而它没有任何遗忘窗口（本轮**故意不加**滑动窗口——加了就要引入衰减权重，衰减权重要浮点，见 P4 为此付的代价）。

### 2.5 P4 — 整数化 Hawkes（会话起始的自激突发）

**一句话**：刚刚频繁开关的 app，短期内还会再开。用整数量化的自激过程判「热/温/冷」，**它不预测开哪个，它决定现在该不该打扰你**。

- `algorithm_id`：`p4.hawkes_burst_int.v1`
- **建模对象**：会话**起始点过程**。经典形式 λ(t) = μ + Σ_{t_i<t} α·e^{-β(t-t_i)}（Hawkes 自激）。μ 由 P3 的时段桶承担（基线强度），α/β 部分整数化如下。
- **整数化**：
  - `TICK = 300 s`（5 分钟），`tick(t) = t.div_euclid(300)`；
  - 半衰期 `HALFLIFE_TICKS = 12`（1 小时）；
  - `excite(now) = Σ_k start_count[k] >> ((tick(now) − k) / 12)`，右移即整除 2，等价于 α=1、β=ln2/半衰期 的量化 Hawkes。**全整数、无浮点、无 exp。**
- **为什么是环形桶而不是一个衰减累加器**：单个累加器每过半衰期右移一次，右移**不可逆**，删一条事件就没法精确回退——直接违反 §0.5 的不变式 F。所以状态是最近 `W = 288 ticks`（24 小时）的**起始计数环形缓冲**，每次求值 O(W) 重算，W 固定即摊销 O(1)，删事件 = 对应桶减一，不变式 F 保住。
  这是把「优雅的在线衰减」换成「可遗忘」的一次自觉交换，代价是求值常数变大（288 次移位加法）。
- **输出**：`burst.hot`（`excite ≥ HOT = 8`）/ `burst.warm`（`≥ WARM = 3`）/ `burst.cold`；可选 `restart_soon(app_id)`（该 app 自己的 `excite ≥ HOT` 且 P3 的同桶也支持它）。
- **训练**：`start_count[tick] += 1`（全局一条流 + 每个重击者 app 一条流）。
- **可数性**：「过去一小时你开了 9 次前台会话，上一小时 6 次」——用户数得清，移位是「一小时前的那些算一半」，一句话说得明白。
- **锁冲突**：**轴亲和 emotional_steadiness（情绪起伏）——这是九个里最危险的越界点。** `burst.hot` 极易被渲染成「你今天很焦躁 / 情绪起伏明显」，那是 A0 的轴，而且是 PRODUCT_LOCK 里最容易踩医疗声称的一条。硬规定：
  1. P4 的输出**永不**进入 `emotional_steadiness` 的证据链（源码级：predict 侧不得 import 轴写入 API，见 F6-3）；
  2. 该轴无论锁没锁，P4 都不许产生轴向 proposal（**比 P6 的一般规则更严**：一般规则是「未锁也只能提 proposal」，P4 是「连 proposal 都不许」）；
  3. 渲染禁词表：焦躁、烦躁、亢奋、情绪不稳、坐立不安。
- **证伪测试**：
  - F4-1（token 有没有意义——主杀线）：`burst.hot` 状态下「15 分钟内出现下一次会话起始」的实测频率必须 ≥ `burst.cold` 状态下的 **2 倍**，且两者的自助置信区间不重叠。达不到 → 这三个 token 不带信息 → 出局。
  - F4-2（自激是不是真的——反向）：把每天的会话起始时刻在当天内**随机重排**（保留每日总数），hot/cold 的区分度必须**塌到基线**。没塌 → 它读到的不是自激而是别的信号（多半是日节律，那 P3 已经有了），出局。
  - F4-3：不变式 F（这条是它改环形桶的理由，必须逐桶断言）。
  - F4-4：`as_of` 平移不变、置换不变（同一 tick 内事件顺序不影响 `excite`）。
  - F4-5：`ADV-flood` 下 `excite` 不得溢出 u32，且 `HOT` 不得对所有时刻恒真（恒真的 token = 无用 token）。
- **已知缺陷**：半衰期 1 小时是**猜的**，没有先验依据；F4-1 必须在 {30min, 1h, 4h} 三档上各跑一次并如实登记最优档，而不是事后把常数改成赢的那个再宣称设计如此。

### 2.6 P5 — T4D 沉寂提醒（把 silent_days 当行为，不当人格）

**一句话**：「你和 X 已经 {N} 天没一对一联系了，你们平时大约 {g} 天一次」——这是一条**行为提醒**，不是「你疏于维系关系」的人格判断。

- `algorithm_id`：`p5.contact_due_reminder.v1`
- **立场（这条是本候选的存在理由，不许在实现里稀释）**：输出的语义是「一个可核对的天数事实 + 一个可拒绝的建议」。它**不**推断勤勉、不推断社交倾向、不写任何轴。所有关于「你是什么样的人」的说法都属于 A0 的面，而 A0 的面上只有问卷与用户纠正两个写入者。
- **输入**（全部来自 T4D 已冻结字段，S2）：`band`、`silent_days`、`last_direct_contact`、`direct_active_day_count`、四计数、`as_of`、`locked_by_user`/`user_band`。外加从 direct 事件**日序列**算出的间隔直方图（derived 计数，不是正文）。
- **个人化门槛（不复用 180/360）**：180/360 是**判档**常量，不是提醒常量；把判档常量拿来当提醒阈值是常量串味，禁止。改用这条边自己的历史：
  - `g̃` = 该边 direct 接触**相邻日间隔**的中位数（整数天，直接从有序日序列取中位，无除法无小数）；
  - 触发条件：`band ∈ {Strong, Moderate}` **且** `direct_active_day_count ≥ 3`（有 `g̃` 可言）**且** `days_since_last_direct ≥ 2 × g̃`。
- **提醒的时钟取 `last_direct_contact`，判档的时钟仍取 `last_contact`**。这是本规范唯一与 T4D 取不同时钟的地方，而且**不改 T4D 一个字节**——`last_direct_contact` 已经是持久化字段（`fable-a-T4D_WIRING` §4），提醒层只是读了另一个已有列。理由：T4D D3 说「昨天在群里同场 = 这人没从你生活里消失」，那对**判档**成立；但「该不该一对一联系一下」问的正是一对一那条线。X2 夹具（direct 沉寂 200 天 + 昨天群里见过）因此**该发提醒**，话术是「你们最近只在群里说过话」。
- **输出（token）**：
  - `reminder.contact_due(contact_id, silent_direct_days, typical_gap_days)` — 两个整数都能手数；
  - `reminder.only_group_recently(contact_id)` — X2 形状的附加 token；
  - `reminder.none`；
  - `reminder.suppressed_edge_locked(contact_id)`；`reminder.suppressed_by_user(contact_id)`；`reminder.suppressed_cooldown(contact_id)`。
  - **token 里只有 `contact_id`，没有姓名**。姓名在本机由 `label_ref` 解引用；研究导出这一行的第三人计数恒 0。
- **频控（打扰预算，整数比较）**：每边 `COOLDOWN_DAYS = 14`；全天 `MAX_DAILY_REMINDERS = 3`，排序按 `silent_direct_days / g̃` 降序，**用交叉相乘 `a₁·g₂ > a₂·g₁` 比较，不做除法**。是否发还要过 P8（用户正在深度停留时不打扰）。
- **训练**：只有计数——间隔直方图随每条新 direct 事件 `+1`，遗忘则 `-1`。
- **锁冲突（四种，都要测）**：
  1. **边锁**：`locked_by_user = true` 时一律读 `user_band` 而非 `machine_band`。用户把边锁成 Weak = 用户已经说了这人不用惦记 → **永不提醒**。锁成 Strong → 照常走门槛。
  2. **A0 轴锁**：提醒不得附带任何 social_energy / accommodation 的说法，锁没锁都不行（P6 的轴亲和登记就是为它写的）。
  3. **用户拒绝**：用户对某边说「别提醒」是一次纠正，**永久尊重**，与 A0 的纠正锁同一形状（用户说了算，机器不覆盖）。
  4. **遗忘**：contact 被遗忘 → 提醒当场消失并 orphan，不留残影。
- **证伪测试**：
  - F5-1：`group_only_50`（只在群里说过话，`direct_active_day_count = 0`）→ 必须 `reminder.none`。对只同过群的人催联系是产品事故。
  - F5-2：`dormant_2019`（沉寂 2632 天，T4D = Weak）→ 必须 `reminder.none`。**Weak 不刨坟**是有意裁决，不是漏判。
  - F5-3：`X2 direct_strong_group_lifeline` → 必须发，且必须带 `reminder.only_group_recently`。这条钉住「提醒用 direct 时钟」这一裁决，防止有人事后把它改成 `last_contact` 而测试不红。
  - F5-4：`lilei_12`（12 次 direct / 6 天 / 沉寂 3 天，`g̃` 约 1–2 天）→ `3 ≥ 2×g̃` 是否成立随夹具而定；**该夹具的期望值必须先手算写死再实现**，防止实现出来之后倒填期望。
  - F5-5（锁）：把 `lilei_12` 的边锁成 Weak → `reminder.suppressed_edge_locked`，且**不得**因为 `machine_band = Strong` 而漏网。
  - F5-6（主杀线，上线后才测得）：本机计数的忽略/关闭率 ≥ **70%** → 出局。打扰型功能的唯一硬指标是用户没关掉它，这个数只在本机统计，不出网。
  - F5-7：`MAX_DAILY_REMINDERS` 与 `COOLDOWN_DAYS` 在「200 人图、全部到期」的夹具上必须真的把当天输出压到 3 条。
- **已知缺陷**：`g̃` 需要 ≥ 3 个 direct 活跃日才有意义，所以新关系上它永远沉默；这是有意的（宁可不提醒也不瞎提醒），但意味着它对「刚认识的重要的人」完全无效。

### 2.7 P6 — A0 锁门（强制包装，不是可选中间件）

**一句话**：任何预测在出口前都要过这道门；**锁定的轴一律不预测**。

- `algorithm_id`：`p6.lock_gate.v1`
- **输入**：任一候选的 token 列表 + 五条轴的 `(position, evidence_band, locked_by_user)`（只读）+ 相关边的 `locked_by_user`/`user_band`。
- **输出**：过滤后的 token 列表 + `abstain.axis_locked(axis_id)` + shadow 记录（进审计，**审计无正文**，只记「有一条轴向输出被锁挡下」这个事实与 axis_id）。
- **规则（R1–R5，全部要有测试）**：
  - **R1 面分离**：预测输出与档案输出是两张表、两个 schema。预测**永不**写 `trait_axis.*` 的 `statement_key`。
  - **R2 锁即静默**：候选声明了轴亲和、且该轴 `locked_by_user = true` → 该候选的轴向输出替换为 `abstain.axis_locked`，行为 token 照出。
  - **R3 未锁也不自动写**：轴未锁时，预测最多产生一条 `proposal`，必须人在回路确认；用户确认后写进去的是 `UserCorrection`（于是轴被锁上）——也就是说**预测唯一能改轴的路径，是用户自己点头**，走的还是 A0 的老路。
  - **R4 边锁**：锁定边上不得输出与 `user_band` 矛盾的提醒强度（P5 的锁冲突 1 的执法点）。
  - **R5 禁词**：轴向措辞表（自律/拖延/焦躁/外向/内向/敏感/迁就……）在渲染层拦截。**这条最弱，见已知缺陷。**
- **冻结的轴亲和表**（登记本身就是可测性的前提；不登记的门是空转的门）：

  | 候选 | 亲和轴 |
  |---|---|
  | P3、P8 | orderliness |
  | P4 | emotional_steadiness（且**连 proposal 都不许**，见 §2.5） |
  | P5 | social_energy、accommodation |
  | P0、P1、P2、P7 | 无 |

- **证伪测试**：
  - F6-1：五轴全锁夹具 → 任何输入下轴向输出为空。
  - F6-2（**双向，同等重要**）：同一个五轴全锁夹具下，`next_app`、`hour_bin_top`、`dwell.*` 这些**行为 token 必须照常输出**。门把有用的一起挡掉同样是失败——「锁的是人格结论，不是行为事实」这句话只有这条测试能证明。
  - F6-3（源码级）：predict crate 不得依赖 profile 的写入 API；对 predict crate 全量 grep，`trait_axis.` 出现次数为 0（测试自身的反向断言处需排除，这个坑 R2 的 fable-b 已经踩过一次）。
  - F6-4：轴未锁时，预测产生的是 `proposal` 而不是落库的 inference；`proposal` 未被确认前，档案读出来逐字节不变。
  - F6-5：锁一条轴不冻结其他轴（沿用 A0 的既有性质，在预测面重测一遍）。
- **已知缺陷（如实写）**：门只能挡**声明了亲和**的越界。没声明的靠 R5 禁词表 + 人工评审，**靠不住**。一个候选如果偷偷带上人格意味而没登记亲和，这道门不会响。缓解只有两条：亲和表进代码评审清单；新增候选必须同时提交亲和登记，否则不给合并。

### 2.8 P7 — 确定性仲裁（融合，不学权重）

**一句话**：按上下文可用性走阶梯选源，并把「用了哪一层」告诉用户。

- `algorithm_id`：`p7.deterministic_arbiter.v1`
- **输入**：P0/P1/P2/P3 的输出与各自的支持计数。
- **仲裁阶梯（确定性）**：
  1. 有 `prev2` 且 P2 二阶行支持 ≥ 8 → 用 P2；
  2. 否则有 `prev1` 且 P1 行支持 ≥ 5 → 用 P1；
  3. 否则时段桶支持 ≥ 10 → 用 P3；
  4. 否则 P0。
  **不学权重**：加权融合要浮点权重，浮点权重要训练，训练超出「只有在线计数」的纪律。
- **具名备选** `p7b.borda_vote.v1`：各源 top-3 的整数名次相加（1/2/3 分），并列按 `app_id` 字典序。整数、可数、可解释，但需要 F7-2 证明它比阶梯强才启用。
- **输出**：`next_app` × top-3 + `source(pN)` token + 该源的支持计数。用户看到的是「因为你上次在 {a} 之后，12 次里有 9 次开了 {b}」——**解释来自被选中的那个源**，这是阶梯优于加权的实际理由（加权融合没有一句可数的解释）。
- **锁冲突**：继承各源亲和之并（本轮为 orderliness，来自 P3）。
- **证伪测试**：
  - F7-1（主杀线）：top-1 必须 ≥ 全部单源的最大值，**且在每一个夹具上都不比最好的单源差超过 2 点**。做不到 → 仲裁没价值，直接留单源。
  - F7-2：`p7b` 只有在打赢阶梯 ≥ 2 点时才启用；否则永久留在备选位。
  - F7-3：`source` token 的分布必须随夹具变化（冷启动夹具上应大量出现 `source(p0)`/`source(p3)`）；若某个源从不被选中，把它从仲裁里删掉。
  - F7-4：确定性——同输入 1000 次同输出，含全部并列格。
- **已知缺陷**：阈值 8/5/10 是三个独立的猜；它们互相影响，单独调任何一个都会改变归因。要么三个一起在网格上扫一次并登记，要么承认它们是约定。

### 2.9 P8 — 停留时长风险桶（打扰门）

**一句话**：判断当前这段前台还会不会继续，用来决定「现在能不能弹 P4/P5 的提醒」。

- `algorithm_id`：`p8.dwell_hazard_bucket.v1`
- **输入**：当前 `app_id` + 当前已持续秒数 + 该 app 的历史时长分桶计数。
- **桶边界**（固定、整数、单源）：`[0,30) [30,120) [120,300) [300,900) [900,2700) [2700,7200) [7200,∞)`，7 桶。
- **离散风险（hazard）**：「已经进到桶 b，还结束在桶 b」的**计数比较**——`ends_in[b]` 与 `survives_past[b]` 两个整数比大小。**只比大小，不输出比值**（比值是分数，见 §0.3）。
- **输出**：`dwell.likely_ends_within(bucket)` / `dwell.likely_continues` / `abstain.thin_history`（该 app 历史段数 < 20）。
- **训练**：会话结束时 `ends_in[app][b] += 1`，并对所有 `b' < b` 的 `survives_past[app][b'] += 1`（7 次整数加，O(1)）。
- **可数性**：「你开 {app} 的 40 次里，有 28 次超过了 15 分钟；现在你已经在里面 20 分钟了。」
- **锁冲突**：轴亲和 orderliness。禁止「你专注力差 / 你很专注」这类措辞——**同一个数字既能被说成褒义也能被说成贬义，恰恰说明它不该被说成任何一种**。
- **证伪测试**：
  - F8-1（主杀线）：必须打赢「该 app 历史时长中位数」这个常数基线；赢不了就用中位数，删掉整张风险表。
  - F8-2：`ADV-flood`（1000 次 5 秒切换）下不得让所有 app 都 `likely_ends`（那样打扰门就恒开，等于没门）。
  - F8-3（它的实际用途）：接上 P5 后，「在 `dwell.likely_continues` 期间发出的提醒条数」必须比不接 P8 时**下降 ≥ 50%**，且提醒总量下降 ≤ 20%（只挪时机，不砍数量）。这条才是它值不值得存在的判据，命中率是次要的。
  - F8-4：不变式 F（注意 `survives_past` 的多桶累加也要能精确减回去）。
- **已知缺陷**：只看 `app_id` 与已停留时长，不看时段（看时段就要 `app × bin × bucket`，稀疏到没法数）。混合用途的 app（浏览器）上它会很平。

## 5. v0.2 默认否决（E0 与可数性），附 v0.4 复活条件

| 被否 | 否的理由（v0.2） | v0.4 可能形态与复活条件 |
|---|---|---|
| 深度序列模型（LSTM / Transformer next-app） | 需要批训练与浮点权重，违反「只有在线计数」；输出是分数不是可数 token；**遗忘破产**——权重里带着已删事件的痕迹，删一条事件要重训才干净，而「遗忘 = 销毁内容密钥 + 派生降 orphan」是产品锁的硬承诺 | v0.4 maybe。复活条件三条全要：(a) 本机可训、不出网；(b) 删一条事件后能**可证明地**回到「从未见过它」的状态（重训并给出等价性判据）；(c) 有可数的解释面，用户能复核。三条缺一不谈 |
| 联邦学习 / 跨用户协同过滤 | 需要非 E1 云通道；v0.1/v0.2 **E0 无代码路径**；且天然涉及跨用户数据 | v0.4 maybe（PRODUCT_LOCK 路线图正是在 v0.4 才第一次引入用户授权的非 E1 云）。复活条件：单独同意 + 只传 derived 聚合 + 可随时关 + 关掉后本机功能不降级 |
| LLM 推「下一步意图」 | 需要 key；无 key 时全部功能必须仍可用，所以它当不了默认；黑盒不可数、不可纠正 | 可作**已配 E1 时的可选增强**，但永不作默认，且不得反写档案 |
| 读窗口标题 / 正文做上下文预测 | 窗口标题是「不做」，不是「推迟」；正文与「第三人正文默认不出本机」冲突 | 无复活条件 |
| 时长加权 / 指数衰减权重（作为通用机制） | 一旦引入浮点权重，可数性与不变式 F 同时破掉 | 已在 P4 里以**整数量化 + 环形桶**的形式收编；除此之外不再开第二个衰减机制 |

## 6. 留给下一轮的未决问题（不在本轮裁）

1. **P4 的半衰期**（30min / 1h / 4h）没有先验依据，必须实测后登记，禁止事后倒填。
2. **P3 的 48 桶 vs 168 桶**由 F3-4 的数据裁，本轮只登记两个具名变体。
3. **P7 的三个阈值（8/5/10）互相耦合**：要么一起网格扫一次，要么承认是约定并写进常量表出处栏。
4. **预测输出进不进研究导出**：`app_id` 是本机身份不是第三人正文，但「某人开了什么软件」的敏感度不为零（例如医疗类 app）。导出前是否要过一层桶化/哈希，本轮不裁。
5. **P5 与 A2（人事分析渲染器）的话术边界**：两者都会说到同一条边的天数，措辞必须单源，否则用户会看到两句不一致的话。
6. **打扰预算是否要全局化**：P4/P5/P8 各自有门，但没有一个全局的「今天已经打扰过你几次」的账。缺这个账，三个门加起来仍可能吵。
